# Node.js 2026년 11월 보안 릴리스 대응 — 기준 버전을 22.23.5로 상향

> **작업 날짜**: 2026-11-13
> **브랜치**: `feature/1.62.7-node-security`

## 📋 작업 개요

**작업 유형**: 버그 수정 (핫픽스, 보안)
**담당**: jsg3121, Claude

## 🎯 작업 목표

프로젝트의 Node.js 기준 버전을 2026년 11월 보안 패치가 들어간 `22.23.5`로 올리고, EC2의 PM2 앱도 실제로 새 런타임에서 실행되게 한다.

<!-- truncate -->

## 📉 왜 필요했나

2026-11-11 Node.js가 22.x·24.x·26.x 전 라인에 보안 릴리스를 배포했다. 10월 릴리스(1.61.5, `22.23.4`)에 이은 후속 릴리스다. 22.x 기준으로 CVE 15건이 패치됐고, 그중 High 6건이 모두 HTTP/2·TLS 처리에 몰려 있다. 공식 우회책은 없고 패치 버전으로의 업그레이드만이 대응이다.

| CVE             | 영역      | 내용                                           | 심각도 |
| --------------- | --------- | ---------------------------------------------- | ------ |
| CVE-2026-123863 | http2     | 스트림 제거 시 헤더 미해제                     | High   |
| CVE-2026-123864 | tls, http | 빈 write로 파서가 중첩 실행됨                  | High   |
| CVE-2026-123865 | http2     | nghttp2가 버린 스트림 미감지                   | High   |
| CVE-2026-123866 | http2     | 소켓 write 완료 전 버퍼 해제                   | High   |
| CVE-2026-123872 | tls       | mTLS 세션 재개·재협상 시 SNI 변경 가능         | High   |
| CVE-2026-123874 | http2     | 대기 중인 write가 있는 스트림 조기 해제        | High   |
| CVE-2026-123877 | https     | Agent의 TLS 정책 키가 격리되지 않음            | Medium |
| CVE-2026-123867 | tls       | 인증서 없는 SNI 컨텍스트의 CA 미적용           | Medium |
| CVE-2026-123871 | http      | 잘못된 프록시 URL 에러에 프록시 자격 증명 노출 | Medium |

이 밖에 http2 Medium 3건, permission·zlib Low 3건이 있다.

Next.js 서버는 `fetch`(undici)로 GraphQL 백엔드 등에 HTTPS 요청을 보내므로 TLS·https Agent 관련 건의 영향 경로에 놓일 수 있다.

## ✨ 주요 변경사항

### 변경 1: `.nvmrc` 기준 버전 상향

**변경 전**:

```text
22.23.4
```

**변경 후**:

```text
22.23.5
```

### 변경 2: `package.json` `engines.node` 상향

**변경 전**:

```json
"engines": {
  "node": ">=22.23.4"
}
```

**변경 후**:

```json
"engines": {
  "node": ">=22.23.5"
}
```

`package-lock.json`은 `npm install --package-lock-only`로 갱신했다. 루트 패키지의 `engines` 한 줄만 바뀌었다.

## 🔍 검증

- 앱 코드 변경이 없어 빌드·런타임 동작은 바뀌지 않는다.
- `.npmrc`에 `engine-strict`가 없어 `engines`는 경고만 내고 설치를 막지 않는다.
- 서버 런타임은 `readlink /proc/<pid>/exe`로 PM2 데몬과 각 앱 프로세스가 실제로 `v22.23.5` 바이너리에서 도는 것을 확인했다.

## 📌 참고 사항

### `pm2 update`만으로는 앱이 새 Node로 바뀌지 않았다

이번 서버 전환에서 1.61.5에 적어 둔 절차(`nvm install` → `pm2 update`)를 따랐는데, **데몬만 22.23.5가 되고 앱 프로세스는 22.23.4로 남았다.** `pm2 describe`의 표시만으로는 알아채기 어려워 실행 바이너리를 직접 확인해서 발견했다.

PM2는 dump에 저장된 앱별 환경(인터프리터 경로·PATH)으로 앱을 되살린다. `pm2 update`는 이 dump를 그대로 재사용하므로 앱은 처음 등록 시점의 Node 경로를 계속 쓴다. 옛 버전 디렉터리가 남아 있으면 에러 없이 조용히 옛 런타임으로 돈다.

다음 업그레이드부터는 아래 순서를 따른다.

```bash
nvm install <버전> --reinstall-packages-from=current   # 전역 pm2 함께 이전
nvm alias default <버전>
nvm use default && hash -r                             # 현재 셸도 전환
pm2 update                                             # 데몬 전환
pm2 restart ecosystem.config.js --env production --update-env   # 앱 전환 (저장소별)
readlink /proc/$(pm2 pid poke-korea)/exe               # 실제 바이너리 확인
pm2 unstartup && pm2 startup                           # systemd 유닛 경로 갱신
pm2 save
nvm uninstall <옛 버전>                                # 저장 후 정리
```

- `--update-env`로도 바뀌지 않으면 `pm2 delete` 후 ecosystem 파일로 다시 `pm2 start`한다.
- `nvm uninstall` 전에 `nvm alias default`가 새 버전을 가리키는지 확인한다. 지운 버전을 가리키면 셸 시작 시 `N/A: version "N/A -> N/A" is not yet installed` 경고가 나고 PATH에 node가 잡히지 않는다.
- `deploy.sh`에는 여전히 Node 전환 단계가 없다. 이 PR을 배포해도 서버 Node는 바뀌지 않으며, 위 절차는 서버에서 따로 수행해야 한다.
