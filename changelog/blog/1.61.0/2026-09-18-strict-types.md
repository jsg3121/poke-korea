# 타입 엄격도 상향 (Phase 2-3)

> **작업 날짜**: 2026-09-18
> **브랜치**: `feature/1.61.0-strict-types`

## 📋 작업 개요

**작업 유형**: 리팩토링 (타입 엄격도) + 버그 수정
**담당**: jsg3121, claude

[컨벤션 개편](/convention-overhaul)이 규정한 TypeScript 엄격 옵션을 적용한다. [네이밍 정리](/naming-cleanup)에 이은 Phase 2의 세 번째 항목이다.

## 🎯 작업 목표

**`strict: true`가 잡지 못하는 구멍을 메운다.**

`strict`는 여러 옵션의 묶음이지만 전부를 포함하지는 않는다. 빠져 있는 것 중 이 코드베이스에 유효한 것을 켠다.

<!-- truncate -->

## 📉 왜 필요했나

`strict: true`만으로는 다음이 통과한다.

- 일부 경로에서만 `return`하는 함수
- `switch`의 의도치 않은 fallthrough
- 미사용 지역 변수·매개변수
- 빈 배열에서 `arr[0]`을 꺼내 쓰는 코드

앞의 세 가지는 **현재 코드에 위반이 없어** 켜기만 하면 된다. 마지막(`noUncheckedIndexedAccess`)은 45건이 걸린다.

## ✨ 주요 변경사항

### 변경 1: 엄격 옵션 4종 적용

측정 결과 네 옵션은 위반이 0건이었다. 수정 없이 켰다.

| 옵션                         | 에러 | 적용 |
| ---------------------------- | ---- | ---- |
| `noImplicitReturns`          | 0건  | ✅   |
| `noFallthroughCasesInSwitch` | 0건  | ✅   |
| `noUnusedLocals`             | 0건  | ✅   |
| `noUnusedParameters`         | 0건  | ✅   |

앞으로 들어올 코드만 규칙을 지키면 된다.

### 변경 2: 퀴즈 완료 판정을 실제 문항 수 기준으로

**이번 작업에서 발견한 가장 실질적인 결함이다.**

```ts
// 완료 판정은 상수
const isLastQuestion =
  quizState.currentQuestionIndex === QUIZ_CONSTANTS.TOTAL_QUESTIONS - 1  // 20

// 문항은 백엔드 응답
const questions = data?.getPokemonTypeQuiz?.map(...) || []
```

**판정 기준과 데이터 출처가 다르다.** 백엔드 응답 개수가 20이 아니면 어긋난다.

| 응답 개수 | 결과                                                      |
| --------- | --------------------------------------------------------- |
| 20개 미만 | 마지막 문항에 닿지 못해 **결과 화면이 열리지 않는다**     |
| 20개 초과 | 20번째에서 결과로 넘어가 **답이 빈 문항이 결과에 섞인다** |

후자는 결과 화면에서 `result.userAnswers[index]`가 `undefined`가 되어 선택지 조회가 깨진다.

`questions.length`를 기준으로 바꿔 응답 개수와 무관하게 정합해진다. 4개 퀴즈 컨텍스트에 동일하게 적용했고, `QuizHeader`의 "문제 N / 20" 표시도 같은 값을 받는다.

### 변경 3: 폼 인덱스 접근의 끊긴 옵셔널 체이닝

```ts
// 변경 전 — ?. 가 중간에서 끊긴다
return megaEvolutionData?.[activeIndex].types ?? []

// 변경 후
return megaEvolutionData?.[activeIndex]?.types ?? []
```

`?.`는 `megaEvolutionData`가 없을 때만 막아주고, **배열은 있는데 인덱스가 범위 밖인 경우는 통과**시킨다. 그 뒤 `.types`에서 크래시한다.

`?? []`라는 폴백이 이미 있다는 건 "데이터 없으면 빈 배열"이 원래 의도였다는 뜻이다. `?.` 하나가 빠져 절반만 보호된 상태였다. `Detail.context`의 6곳을 채웠다.

### 변경 4: 랜덤 선택을 헬퍼로

```ts
const pickRandom = <T>(list: ReadonlyArray<T>, fallback: T): T =>
  list[Math.floor(Math.random() * list.length)] ?? fallback
```

`Math.floor(Math.random() * arr.length)`는 인덱스가 항상 유효하지만 타입은 그걸 모른다. 호출부마다 폴백을 두면 실행되지 않는 분기가 늘어나므로 한 곳에서만 좁힌다.

옵션 섞기(Fisher–Yates)의 구조 분해 스왑도 명시적 형태로 바꿨다.

## 🔍 검증

### 실제 백엔드 데이터 조회

퀴즈 결과 화면의 위험을 코드만 보고 판단하지 않았다. GraphQL 서버에 직접 쿼리해 실측했다.

| 항목                      | 실측값             |
| ------------------------- | ------------------ |
| 문항 수                   | 20개 (상수와 일치) |
| 옵션 수                   | 전 문항 4개        |
| `correctAnswerIndex` 범위 | 0~3                |
| 범위 이탈                 | **0건**            |

**현재 데이터로는 문제가 발생하지 않는다.** 변경 2는 응답 개수가 바뀔 때를 위한 수정이다. 이 사실을 확인하지 않았다면 "위험하다"는 추측 위에 코드를 고쳤을 것이다.

### 정적 검사와 라우트

| 항목                       | 결과      |
| -------------------------- | --------- |
| `tsc --noEmit`             | 0건       |
| ESLint 에러                | 0건       |
| 라우트 8개 (퀴즈 4종 포함) | 전부 정상 |

`/quiz/ability`, `/quiz/silhouette`, `/quiz/pokemon-type`, `/quiz/type-effectiveness`를 각각 요청해 확인했다.

**확인하지 않은 것**: 퀴즈를 끝까지 풀어 결과 화면까지 도달하는 시나리오는 자동화로 검증하지 않았다. 완료 판정을 바꿨으므로 4종 모두 실제 플레이 확인이 필요하다.

## ⚠️ 구현 시 고려한 점

### `noUncheckedIndexedAccess`를 켜지 않은 이유

45건 중 19건을 처리해 26건이 남은 시점에 적용을 보류했다. 결정을 뒤집은 것이 아니라 **시점을 미룬 것**이다.

**이 옵션이 드러낸 실제 결함은 이미 고쳤다.** 위의 변경 2·3이 그것이고, 둘 다 옵션 없이도 유효한 수정이다. 옵션의 목적(숨은 `undefined` 접근 발견)은 달성한 셈이다.

**남은 26건은 형식적 처리에 가깝다.** 배열 리터럴 직후의 `[0]`·`[1]`처럼 값이 반드시 존재하는 접근이 다수다. 폴백을 넣으면 **실행되지 않는 분기**만 늘어난다.

```ts
const statEntries = [{ label: 'HP', ... }, /* 6개 */]
const sorted = [...statEntries].sort(...)
sorted[0]  // 6개 배열이므로 항상 존재하지만 타입은 모른다
```

### 어떻게 고칠지가 정리되면 켠다

재개 조건은 "실행되지 않는 폴백을 만들지 않으면서 타입을 만족시키는 방법"이다. 인덱스 접근을 구조 분해나 전용 헬퍼로 바꾸는 방식이 후보이며, 이번에 만든 `pickRandom`이 그 예다.

이 판단은 ADR-0018의 "적용 현황" 절에 기록했다. 근거 없이 미루면 다음 사람이 이유를 모른 채 켜서 26건을 다시 마주하거나, 반대로 영원히 방치된다.

### 가드가 동작을 바꾸는 경우는 제외했다

퀴즈 결과 화면의 인덱스 접근에 폴백을 넣는 안을 검토했으나 기각했다. `userAnswerIndex`를 `0`으로 폴백하면 **사용자가 고르지 않은 답을 골랐다고 표시**한다. 틀린 정보를 보여주느니 근본 원인(완료 판정)을 고치는 쪽을 택했다.
