# 전역 헤더 sticky 복구

> **작업 날짜**: 2026-09-21
> **브랜치**: `feature/1.61.0-sticky-header-fix`

## 📋 작업 개요

**작업 유형**: 버그 수정 (레이아웃)
**담당**: jsg3121, claude

[전역 크롬 layout 승격](/layout-chrome) 이후 드러난 회귀를 수정한다.

## 🎯 작업 목표

**스크롤을 아무리 내려도 헤더가 화면 위에 남아 있게 한다.**

<!-- truncate -->

## 📉 왜 필요했나

모바일 `/list`에서 스크롤을 내리면 어느 시점부터 헤더가 화면 위로 사라졌다. 그런데 필터바는 그대로 남아, **헤더가 있어야 할 48px 자리로 카드가 그대로 비쳐 지나갔다.**

두 요소 모두 `sticky`인데 한쪽만 동작을 멈춘 것이다.

| 요소     | 선언                       | 컨테이닝 블록            |
| -------- | -------------------------- | ------------------------ |
| 전역 헤더 | `sticky top-0` `z-[500]`   | `<body>`                 |
| 필터바   | `sticky top-12` `z-30`     | `<main class="min-h-screen">` |

### `sticky`는 부모를 벗어나지 못한다

`position: sticky`는 화면이 아니라 **컨테이닝 블록**을 기준으로 고정된다. 부모의 패딩 박스가 끝나면 거기서 함께 밀려 올라간다.

> The element is ... constrained within its containing block, which is the **padding box of its nearest block-level ancestor**.
> — [CSS Positioned Layout Level 3 — Sticky positioning](https://www.w3.org/TR/css-position-3/#sticky-pos)

그리고 전역 스타일에 이것이 있었다.

```css
html,
body {
  @apply w-full h-full; /* height: 100% */
}
```

**body 높이가 뷰포트 한 장으로 고정된다.** 콘텐츠는 `<main>`의 `min-h-screen` 위로 얼마든지 늘어나지만 body 자체는 늘지 않는다. 그래서 헤더는 첫 화면을 넘어가는 순간 고정을 멈추고, 필터바는 자기 부모(`<main>`)가 충분히 길어 계속 붙어 있었다.

증상이 "헤더만" 사라진 것처럼 보인 이유다.

### 왜 이제서야 나타났나

[layout 크롬 승격](/layout-chrome) 전에는 헤더와 필터바가 **같은 부모 안**에 있었다.

```tsx
// 변경 전 — page.tsx
<main className="w-full min-h-screen">
  <MobileHeader />   {/* sticky top-0 */}
  <List />           {/* 그 안에 sticky top-12 */}
</main>
```

둘 다 컨테이닝 블록이 `<main>`이었고, `min-h-screen`은 높이 하한만 정할 뿐 상한을 묶지 않는다. 그래서 문제가 드러나지 않았다.

크롬을 layout으로 올리며 헤더가 `<body>` 직속으로 옮겨졌고, 그때 비로소 `height: 100%`의 영향권에 들어왔다.

## ✨ 주요 변경사항

```diff
  html,
  body {
-   @apply w-full h-full;
+   @apply w-full;
  }

  body {
-   @apply relative w-full h-full;
+   @apply relative w-full;
  }
```

`h-full`이 `html, body` 공통 규칙과 `body` 단독 규칙 두 곳에 있어 둘 다 제거했다.

제거 근거를 주석으로 남겼다. 이 속성은 이름만 보면 "화면을 채우기 위한 것"으로 읽혀 다시 들어오기 쉽다.

## ⚠️ 구현 시 고려한 점

### 구조를 되돌리지 않은 이유

가장 빠른 해결은 헤더를 `<main>` 안으로 되돌리는 것이다. 하지만 layout 승격 커밋이 명시한 목적이 바로 그것이었다.

> layout이 크롬을 소유하면서 main이 헤더와 푸터 사이로 들어간다 — 기존에는 **main이 크롬을 감싸 시맨틱이 뒤집혀 있었다.**

`<main>`은 "이 문서의 주 콘텐츠"를 뜻하므로 전역 헤더·푸터는 그 **형제**여야 한다. 되돌리면 버그 하나를 고치려고 시맨틱 개선을 버리는 셈이다.

**바뀐 것은 헤더의 컨테이닝 블록이지 구조의 옳고 그름이 아니다.** 이동 자체는 맞았고, 그때 함께 검토되지 않은 height 제약이 남아 있던 것이다.

### 헤더를 `fixed`로 바꾸지 않은 이유

데스크톱 헤더가 이미 `fixed`라 일관성 면에서 후보였다. 그러나 이는 **증상 대응**이다. `fixed`는 컨테이닝 블록을 뷰포트로 바꿔 증상을 감출 뿐, body가 뷰포트에 묶여 있다는 사실은 그대로 남는다. 다음에 body 직속으로 무언가를 `sticky`로 두면 같은 문제가 반복된다.

또 `fixed`는 문서 흐름에서 빠지므로 가려지는 높이를 따로 보정해야 한다 — layout 승격이 없애려 했던 그 결합이다.

### `h-full` 제거의 영향 범위

전역 스타일이라 의존처를 먼저 확인했다.

| 확인 대상             | 결과                                      |
| --------------------- | ----------------------------------------- |
| `MobileTabBar`의 `h-full` | 자기 `<nav>` 기준 — 무관                  |
| `useBodyScrollLock`   | `overflow`만 제어, 높이 미사용            |
| 짧은 페이지의 배경    | `<main min-h-screen>`이 이미 담당         |

`h-full`은 Tailwind 도입 초기 커밋부터 있던 관성 코드로 요구사항 기록이 없다. `min-h-screen`과 역할이 겹치면서 상한까지 묶는 쪽이라 해로웠다.

## 📊 변경 결과

| 항목                  | 변경 전             | 변경 후          |
| --------------------- | ------------------- | ---------------- |
| body 높이             | `100%` (뷰포트 고정) | **제약 없음**    |
| 헤더 고정 지속 구간   | 첫 화면까지         | **문서 전체**    |
| 필터바 위 빈 48px     | 발생                | **해소**         |

## 📌 참고 사항

### 눈으로 확인이 필요하다

전역 스타일 변경이라 `/list` 외 페이지도 영향권이다. 특히 다음을 봐주시기 바란다.

- 모바일에서 스크롤 시 헤더·필터바가 함께 붙어 있는지
- 콘텐츠가 짧은 페이지에서 배경이 화면 아래까지 채워지는지
- 모달·팝업이 열렸을 때 배경 스크롤 잠금이 그대로 동작하는지

### 남은 점검거리

데스크톱 헤더는 `fixed`, 모바일 헤더는 `sticky`로 방식이 갈려 있다. 이번 수정으로 둘 다 정상 동작하지만, 고정 방식이 다르면 좌표 보정 규칙도 갈린다(`desktop:top-30`이 `top-12`와 다른 이유). 통일할지는 별도 판단이 필요하다.
