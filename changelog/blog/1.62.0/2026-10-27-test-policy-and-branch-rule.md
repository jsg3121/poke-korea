# 단위 테스트 도구 미도입 결정과 브랜치 생성 주체 정리

> **작업 날짜**: 2026-10-27
> **브랜치**: `feature/1.62.0-code-cleanup`

## 📋 작업 개요

**작업 유형**: 문서 (하네스)
**담당**: Claude Code

## 🎯 작업 목표

- 상세 능력치 탭 2단계(계산 함수)를 시작하기 전에 단위 테스트를 어떻게 다룰지 결정하고 기록한다.
- 브랜치를 누가 만드는지 workflow 지침과 실제 작업 흐름을 맞춘다.

<!-- truncate -->

## 📉 왜 필요했나

**단위 테스트.** 상세 능력치 탭 기획서는 2단계를 "계산 함수·단위 테스트 설계"로 잡았는데, 저장소에는 단위 테스트 도구가 없었다. Vitest·Jest·Node 내장 `node:test`를 비교하는 과정에서, 테스트 대상이 거의 바뀌지 않는 게임 공식 함수 하나뿐이라 상시 테스트의 이득(변경 방지)이 도구 유지 비용보다 작다는 결론이 나왔다.

**브랜치 생성.** `workflow.md`는 "브랜치는 사용자가 직접 생성"이라고 적고 있었지만, 실제로는 Claude가 이름을 제안하고 사용자 승인 후 만드는 흐름이 쓰였다. 문서와 실제가 달라 작업마다 생성 주체를 다시 확인해야 했다.

## ✨ 주요 변경사항

### ADR-0024: 단위 테스트 도구를 도입하지 않고 E2E만 유지

- 순수 계산 로직은 구현할 때 기대값과 한 번 대조한다. 임시 스크립트로 확인한 뒤 지우고, 결과는 changelog 검증 절에 남긴다.
- 재검토 조건: 상시 보호가 필요한 순수 로직이 여러 개 생기면 Vitest를 1순위로 다시 검토한다.
- 기각한 대안: Vitest 즉시 도입, Jest, `node:test` 상시 사용 (사유는 ADR 대안 표)

| 문서 | 변경 |
| --- | --- |
| `decisions/records/ADR-0024-no-unit-test-framework.md` | 신규 |
| `decisions/records/index.md` | 목록에 ADR-0024 추가 |
| `conventions/guides/testing.md` | "순수 계산 로직 확인" 절 추가 |
| `specs/features/detail-stats-real-value-tab-spec.md` | 9절 2단계를 "계산 함수·기대값 대조"로, 3-4·8절의 단위 테스트 언급을 기대값 대조로 수정 |

### workflow.md: 브랜치는 사용자 확인 후 Claude가 생성

| 위치 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 브랜치 네이밍 규칙 | 브랜치는 사용자가 직접 생성 | 이름·분기 원점을 제안하고 사용자 확인 후 Claude가 생성 (변경 이유·날짜 기록) |
| 기본 워크플로우 1·2 | 사용자가 루트·작업 브랜치 생성 | 사용자 확인 후 Claude가 생성 |
| 새 작업 체크리스트 | `feature/*`면 바로 진행 | 통합 브랜치면 서브 브랜치 생성 제안, 서브 브랜치면 바로 진행 |

운영 규칙이라 ADR 대상이 아니므로, `decisions/index.md`의 지침 변경 관리 절차에 따라 `workflow.md` 안에 이유와 날짜를 남겼다.

## 📌 참고 사항

- 계산 함수가 나중에 바뀌어도 자동으로 잡아 주는 테스트는 없다. 계산 로직을 고칠 때는 기획서 기대값으로 다시 대조해야 한다.
- 기대값 대조용 임시 스크립트를 Node로 직접 실행할 수 있는지는 2단계 착수 때 확인한다.
