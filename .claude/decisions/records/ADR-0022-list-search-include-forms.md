# ADR-0022: 도감 목록 이름 검색에 리전폼·메가진화 포함

- **상태**: 제안
- **날짜**: 2026-10-14
- **담당**: jsg3121

## 맥락

도감 목록(`/list`)은 필터 사용이 활발한 화면이다. 28일 동안 사용자 약 6,100명이 페이지뷰 84,727을 만들었다. 이 중 `/list` 자체는 23,324이고 나머지는 `?type=`, `?isMega=`, `?generation=` 같은 필터 조합이다. 필터를 바꾸면 `router.replace`로 URL이 바뀌고, GA4 향상된 측정이 이를 페이지뷰로 센다. 사용자가 이 화면에서 원하는 포켓몬을 적극적으로 좁혀 찾고 있다는 뜻이다.

그런데 이름 검색으로는 리전폼·메가진화를 찾을 수 없다. 운영 API(`getPokemonListPaginated`)로 확인한 결과는 다음과 같다(2026-10-14).

| 입력 | 결과 |
| --- | --- |
| 라이츄 | 1건 (기본 라이츄) |
| 알로라 라이츄 / 알로라 / 히스이 | 0건 |
| 메가리자몽 | 0건 |

원인은 세 가지다.

1. 백엔드 목록 서비스가 **기본 종 이름에만** `name: { contains }` 조건을 건다(`poke-korea-server/src/graphql/service/getPokemonListPaginated.service.ts`). 폼 이름은 `PokemonRegionForm`·`PokemonMegaEvolution`·`PokemonNormalForm` 테이블에 따로 있다.
2. 목록은 **종마다 한 행**이다. `isRegionForm: true`는 "리전폼이 있는 종"이라는 표시일 뿐이고, 응답의 타입·종족값은 기본 폼 기준이다.
3. 리전폼 이름이 `"라이츄 알로라의 모습"` 형식으로 저장돼 있다(로컬 DB 59건, 빈 값 0건). 사용자가 흔히 입력하는 `"알로라 라이츄"`와 어순이 달라서, 검색 대상을 폼 테이블까지 넓혀도 단순 `contains`로는 걸리지 않는다. 메가는 `"메가리자몽X"` 형식이라 `contains`로 걸린다.

참고로 헤더 검색이 쓰는 `searchPokemonWithAllForms`는 기본 종 이름으로 찾은 뒤 기본·메가·노말폼·리전폼을 펼쳐 돌려준다. 다만 이 응답에는 타입·종족값이 없다(`PokemonFormInfo`).

Search Console(2026-09-13 ~ 10-11)에서 메가 의도 질의는 노출 48,480, 리전폼 의도 질의는 4,434였다. 상성 계산기 이름 입력(1.62.0 후보)도 리전폼·메가를 지원하려면 같은 폼 데이터가 필요하다.

## 결정

**검색 매칭과 결과 표시를 모두 폼 단위로 확장하는 결합안(C)을 제안한다.**

- **매칭**: 기본 종 이름, 메가 이름, 리전폼 이름, 지역명(알로라·가라르·히스이·팔데아)을 검색 대상으로 삼는다. 입력을 공백으로 나눈 **모든 토큰이 해당 폼의 이름+지역명 어딘가에 포함**되면 매칭으로 본다. 그래야 "알로라 라이츄"와 "라이츄 알로라" 모두 "라이츄 알로라의 모습"에 매칭된다.
- **결과**: 매칭된 폼은 **그 폼의 카드**(폼 이름, 폼 타입, 폼 이미지, 폼 상세 링크)로 보여준다. 기본 종이 매칭되면 기본 카드 뒤에 연결된 폼 카드를 이어서 보여준다.
- **범위**: 이름 검색어가 있을 때만 폼 단위 결과를 쓴다. 검색어가 없는 기존 목록·필터 동작(종 단위 무한 스크롤)은 바꾸지 않는다.

최종 채택 여부와 백엔드 구현 방식(아래 결과 절의 미결 사항)은 백엔드 검토 후 확정하고, 확정 시 상태를 `승인`으로 바꾼다.

## 근거

- **사용자의 실제 입력 형태에 맞는 유일한 안이다.** 지역명이 앞에 오는 입력("알로라 라이츄")과 저장 형식("라이츄 알로라의 모습")의 어순 차이는 토큰 매칭이 아니면 풀리지 않는다.
- **검색 목적이 결과 화면에서 끝난다.** 리전폼은 타입이 기본 폼과 다른 경우가 많다(예: 알로라 라이츄는 전기·에스퍼). 기본 종 카드만 돌려주면 사용자가 상세까지 들어가야 원하는 정보를 본다.
- **기존 목록 동작을 건드리지 않는다.** 검색어가 있을 때만 결과 단위가 바뀌므로, 필터·무한 스크롤·페이지네이션 커서 로직의 회귀 위험이 검색 경로에 갇힌다.
- ~~**상성 계산기 이름 입력과 데이터를 공유한다.** 폼별 타입이 결과에 포함되면, 같은 쿼리를 상성 계산기의 리전폼·메가 지원에 재사용할 수 있다.~~ — 2026-10-15부터 유효하지 않다. 상성 계산기 이름 입력은 `searchPokemonWithAllForms`에 `types`를 추가하는 방식으로 폼 타입을 받기로 했다([이름 입력 기획서 5.2](../../specs/features/type-calculator-name-input-spec.md)). 이 ADR의 목록 쿼리와는 데이터를 공유하지 않는다.

## 대안

| 대안 | 장점 | 단점 | 불채택 사유 |
| --- | --- | --- | --- |
| A. 이름 조건만 폼 테이블까지 OR 확장 | 백엔드 변경이 가장 작다(Prisma 관계 필터 `some` 추가) | 결과가 여전히 기본 종 카드라 폼의 타입·모습을 보려면 상세로 가야 한다. "알로라 라이츄"는 어순 차이로 여전히 0건 | 사용자의 실제 입력에 응답하지 못한다 |
| B. 기본 종 이름 검색은 그대로, 결과에 연결된 폼 카드를 함께 노출 | 검색 결과에서 폼 정보를 바로 볼 수 있다 | "알로라", "히스이", "메가리자몽"처럼 폼·지역명으로 시작하는 검색은 여전히 0건 | 폼 이름으로 찾으려는 수요를 놓친다 |
| D. 프론트에서 `searchPokemonWithAllForms` 결과를 목록에 섞어 표시 | 백엔드 변경이 없다 | 응답에 타입·종족값이 없고, 매칭이 기본 종 이름뿐이라 A·B의 한계를 그대로 가진다. 목록 쿼리와 검색 쿼리를 둘 다 호출해야 한다 | 문제를 풀지 못하고 호출만 늘어난다 |
| E. 리전폼 이름 데이터를 "알로라 라이츄" 형식으로 일괄 변경 | 단순 `contains`로 해결된다 | 상세 페이지·메타데이터·JSON-LD 등 기존 표시명이 모두 바뀌어 SEO 회귀 위험이 크다 | 검색 문제를 풀기 위해 표시 데이터 전체를 바꾸는 것은 과하다 |

## 결과

### 예상 변화

- 백엔드: `getPokemonListPaginated`에 검색어 전용 경로가 생긴다. 응답에 폼 단위 항목(폼 구분, 폼 이름, 폼 타입, 이미지 경로, 상세 경로 식별자)을 담을 필드 또는 별도 쿼리가 필요하다.
- 프론트: 목록 카드가 폼 단위 항목을 받을 수 있어야 한다(폼 이름 표시, 폼 상세 링크). 카드 컴포넌트는 이미 폼 이름 표시를 지원하는지 착수 시 확인한다.
- 측정: 검색 결과 클릭 이벤트(GA4)를 함께 넣어, 폼 카드 클릭 비중으로 효과를 본다.

### 일정 (2026-10-19)

1.62.0 일정에서 분리해 **도감 검색 고도화** 별도 작업으로 진행한다. 버전과 착수 시점은 별도로 정한다. 근거는 [전략 문서 "별도 작업으로 분리"](../../research/strategy/2026-10-14-next-feature-priority.md)에 있다.

### 미결 사항 (백엔드 검토 필요)

1. **쿼리 형태**: 기존 `getPokemonListPaginated`의 응답을 확장할지, 검색 전용 쿼리를 새로 둘지. 커서 페이지네이션은 종 `id` 기준이라 폼 단위 결과와 섞이면 커서 정의가 바뀐다. 검색 결과는 건수가 작으므로(폼 포함 수십 건 이하 예상) 검색 경로만 페이지네이션 없이 반환하는 방안도 검토한다.
2. **어순 처리 방식 (2026-10-19 범위 확대)**: 위 결정의 토큰 매칭은 후보 중 하나이고 확정안이 아니다. 어순 처리를 토큰 매칭으로 할지 다른 방식으로 할지부터 다시 검토한다. 상성 계산기 이름 입력의 폼 이름 검색 확장(`searchPokemonWithAllForms`)도 같은 어순 문제를 가지므로 두 검색을 함께 본다. 토큰 매칭을 택하면 구현은 Prisma `AND` + 토큰별 `OR` 조건 조합과 PostgreSQL `pg_trgm` 등 DB 기능 중에서 고른다. 데이터 규모(종 약 1,025, 폼 약 430)를 생각하면 전자로 충분할 가능성이 높다.
3. **필터와 함께 쓸 때의 의미**: 검색어 + 타입 필터를 함께 쓰면 타입을 기본 폼 기준으로 볼지 폼 기준으로 볼지. 폼 단위 결과라면 폼 타입 기준이 자연스럽다.
