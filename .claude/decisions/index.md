# decisions/

아키텍처 의사결정 기록(ADR)을 관리하는 폴더입니다.

## 사용법

1. 새로운 기술적 의사결정이 필요할 때 `template.md`를 참고하여 ADR을 작성합니다.
2. 파일명: `records/ADR-{번호}-{제목}.md` (예: `ADR-0001-harness-engineering.md`)
3. 기존 지침과 충돌하는 결정은 ADR 기록 후 관련 문서를 동기화합니다.

## 작성 제안 시점

에이전트는 아래 신호가 감지되면 **논의가 끝나기를 기다리지 않고 그 시점에 ADR 작성을 제안**한다. 작성 여부는 사용자가 결정하며, 제안 없이 임의로 작성하지 않는다.

### 트리거 신호

| 신호 | 예시 |
| ------ | ------ |
| 해결 후보 2개 이상 비교 | "A는 1줄이지만 근본 원인이 남고, B는 범위가 큽니다" |
| 트레이드오프 판단 | 성능 vs 복잡도, SEO vs 구현 편의, 범위 vs 리스크 |
| 검토 후 기각 | "layout 승격은 하위 세그먼트 param을 못 읽어 기각" |
| 도입 효과·실효성 판단 | "이 최적화가 실측상 의미가 있는가" |
| 명세 제약에 따른 차선책 | "명세가 제공하지 않아 JS 판정 + CSS 위임으로 우회" |
| 기존 지침과 충돌 | 컨벤션·ADR을 바꿔야 하는 상황 |

### 대상이 아닌 경우

- 단순 버그 수정 (원인이 명확하고 해법이 하나)
- 스타일·문구 조정
- 이미 기록된 ADR의 반복 적용
- 되돌리기 쉽고 영향 범위가 파일 하나에 갇히는 변경

### 판단 기준

애매하면 **"6개월 뒤 다른 사람이 이 코드를 보고 '왜 이렇게 했지?'라고 물을까"** 를 묻는다. 코드와 주석만으로 답이 안 나오면 ADR 대상이다.

> **Why:** 트레이드오프 비교는 대화 중에 근거가 가장 선명하지만, 그 맥락은 코드 diff에 남지 않는다. 특히 **기각된 대안**은 흔적조차 없어, 나중에 같은 검토를 반복하거나 이미 기각된 방안을 다시 꺼내게 된다. 논의가 끝난 뒤 제안하면 근거를 되짚는 비용이 커지므로 신호가 보이는 시점에 제안한다.
