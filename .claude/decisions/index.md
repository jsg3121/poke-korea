# decisions/

아키텍처 의사결정 기록(ADR)을 관리하는 폴더입니다.

이 문서는 **ADR 규칙의 권위 있는 원본(single source of truth)** 입니다. CLAUDE.md에는 이 문서로 진입하는 포인터만 두고, 실제 규칙은 전부 여기에 둡니다.

> **Why:** 세션 시작 시 자동으로 로드되는 것은 CLAUDE.md뿐이고, 하위 문서는 참조돼야 읽힙니다. 규칙 본문이 CLAUDE.md에 흩어져 있으면 이 폴더만 복사해도 다른 프로젝트에서 동작하지 않습니다. 포인터와 내용을 분리해야 폴더 단위로 이식할 수 있습니다.

## 구성

| 파일 | 역할 |
| ------ | ------ |
| `index.md` | ADR 규칙 (이 문서) — 프로젝트 무관 |
| `template.md` | ADR 작성 템플릿 — 프로젝트 무관 |
| `records/index.md` | 이 프로젝트의 ADR 기록 목록 |
| `records/ADR-*.md` | 개별 ADR 문서 |

## 사용법

1. 새로운 기술적 의사결정이 필요할 때 `template.md`를 참고하여 ADR을 작성합니다.
2. 파일명: `records/ADR-{번호}-{제목}.md` (예: `ADR-0001-harness-engineering.md`). 번호는 4자리 zero-padding, 제목은 kebab-case.
3. 작성 후 `records/index.md`의 기록 목록 표에 한 줄을 추가합니다.
4. 반드시 참고 자료(공식 문서, 신뢰할 수 있는 블로그 등) 링크를 포함합니다.
5. 기존 지침과 충돌하는 결정은 ADR 기록 후 관련 문서를 동기화합니다(아래 "지침 변경 관리" 참조).

## 작성 제안 시점

**IMPORTANT**: 에이전트는 아래 신호가 감지되면 **논의가 끝나기를 기다리지 않고 그 시점에 ADR 작성을 제안**한다. 작성 여부는 사용자가 결정하며, 제안 없이 임의로 작성하지 않는다.

### 트리거 신호

| 신호 | 예시 |
| ------ | ------ |
| 해결 후보 2개 이상 비교 | "A는 1줄이지만 근본 원인이 남고, B는 범위가 큽니다" |
| 트레이드오프 판단 | 성능 vs 복잡도, SEO vs 구현 편의, 범위 vs 리스크 |
| 검토 후 기각 | "layout 승격은 하위 세그먼트 param을 못 읽어 기각" |
| 도입 효과·실효성 판단 | "이 최적화가 실측상 의미가 있는가" |
| 명세 제약에 따른 차선책 | "명세가 제공하지 않아 JS 판정 + CSS 위임으로 우회" |
| 기존 지침과 충돌 | 컨벤션·ADR을 바꿔야 하는 상황 |

### 대상이 아닌 경우

- 단순 버그 수정 (원인이 명확하고 해법이 하나)
- 스타일·문구 조정
- 이미 기록된 ADR의 반복 적용
- 되돌리기 쉽고 영향 범위가 파일 하나에 갇히는 변경

### 판단 기준

애매하면 **"6개월 뒤 다른 사람이 이 코드를 보고 '왜 이렇게 했지?'라고 물을까"** 를 묻는다. 코드와 주석만으로 답이 안 나오면 ADR 대상이다.

> **Why:** 트레이드오프 비교는 대화 중에 근거가 가장 선명하지만, 그 맥락은 코드 diff에 남지 않는다. 특히 **기각된 대안**은 흔적조차 없어, 나중에 같은 검토를 반복하거나 이미 기각된 방안을 다시 꺼내게 된다. 논의가 끝난 뒤 제안하면 근거를 되짚는 비용이 커지므로 신호가 보이는 시점에 제안한다.

## 지침 변경 관리

개발 진행이나 논의 과정에서 기존에 명시된 지침, 규칙, 계획과 어긋나는 상황이 발생할 수 있다. 이 경우 다음 절차를 따른다.

1. **기존 지침 확인**: 변경하려는 영역의 관련 ADR, 컨벤션, 가이드라인을 먼저 읽고 현재 규칙이 무엇인지 파악한다
2. **충돌 지점 명시**: 기존 지침의 어떤 부분이 현재 상황과 맞지 않는지 구체적으로 식별한다
3. **변경 논의**: 왜 변경이 필요한지 근거를 제시하고, 사용자와 합의한다
4. **ADR 기록**: 변경 사항을 새로운 ADR로 작성한다. 기존 ADR을 대체하는 경우, 기존 ADR의 상태를 `대체됨`으로 변경하고 새 ADR 번호를 명시한다
5. **관련 문서 동기화**: 변경이 반영되어야 하는 모든 문서(CLAUDE.md, 컨벤션, 가이드라인 등)를 함께 업데이트한다

### 상태 값

| 상태 | 의미 |
| ------ | ------ |
| 제안 | 논의 중이며 아직 확정되지 않음 |
| 승인 | 채택되어 현재 유효함 |
| 폐기 | 더 이상 적용하지 않으며 대체 ADR도 없음 |
| 대체됨 | 다른 ADR로 대체됨 — 반드시 대체 ADR 번호를 본문에 명시 |

> **Why:** 기각·대체된 결정을 삭제하지 않고 상태만 바꾸는 이유는, "왜 이 방안을 버렸는가"가 새 결정의 근거이기 때문이다. 삭제하면 같은 방안이 다시 후보로 올라온다.

## 근거 기반 논의

의사결정이나 기술 논의 시, 반드시 공식 문서나 신뢰도 높은 자료를 근거로 제시한다. 근거 없는 주장이나 추측만으로 의사결정을 유도하지 않는다.

- 기술 비교/추천 시: 공식 문서, 벤치마크, 신뢰할 수 있는 기술 블로그 등의 링크를 함께 제시한다
- ADR 작성 시: 참고 자료(References) 섹션에 근거 링크를 반드시 포함한다
- 컨벤션/가이드라인 작성 시: 해당 규칙의 출처(공식 스타일 가이드, RFC 등)를 명시한다
