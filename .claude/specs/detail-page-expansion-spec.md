## 1. 배경 — 왜 상세 페이지인가

### 1-1. 문제: 유입이 단일 페이지에 극단적으로 의존

서치콘솔 실측(최근 3개월, 봇 무관)상 검색 클릭이 상성표 한 페이지에 쏠려 있다.

| 페이지 | 검색 클릭 | 클릭 점유율 |
| --- | ---: | ---: |
| `/type-effectiveness` (상성표) | 33,895 | **57.7%** |
| `/` (홈) | 5,117 | 8.7% |
| `/champions/tier` | 1,622 | 2.8% |
| `/moves` | 1,223 | 2.1% |
| **상세 페이지(`/detail/`) 717개 합계** | **10,592** | **18.0%** |

> **Why 문제인가:** 검색 클릭의 57.7%가 상성표 한 페이지다. 이는 단일 장애점(SPOF)이다 — 구글이 상성표 랭킹을 한 번 떨어뜨리면 전체 유입의 절반이 사라진다. 유입 채널의 83%가 검색(SEO 사실상 유일 채널, `service-overview.md`)이므로 이 리스크는 서비스 존속과 직결된다.

### 1-2. 기회: 상세 페이지는 "노출은 거대한데 전환이 막혀 있다"

| 구분 | 노출 | 클릭 | CTR |
| --- | ---: | ---: | ---: |
| 전체 사이트 | 1,798,401 | 58,715 | 3.26% |
| **상세 페이지(`/detail/`) 합계** | **881,909 (전체의 49%)** | 10,592 (18%) | **1.20%** |

> **Why 기회인가:** 상세 페이지는 이미 **전체 검색 노출의 49%(88만 회)**를 확보했으나 CTR은 전체 평균의 약 1/3(1.20%)에 불과하다. 즉 구글은 이미 상세 페이지를 대량 노출시키는데, **콘텐츠가 얇아 클릭으로 전환되지 않는다.** 신규 페이지를 만들어 새 랭킹을 얻는 장기전이 아니라, **이미 랭크된 페이지의 전환율을 올리는** 작업이므로 유입 ROI가 가장 확실하다.

### 1-3. 상세 페이지 내 수요는 이로치·메가진화에 집중 (단, 이미 처리 완료)

- 상세 페이지 노출의 **54%가 shiny(이로치) URL**, **18%가 mega 폼**이다. 둘을 합치면 상세 노출의 **약 72%**.
- 검색어에서도 "마스카나 이로치"(364클릭)가 TOP 30에 진입. `metrics-baseline.md`의 "이로치 키워드 강세" 관찰이 실측으로 재확인됨.

> **코드 검증 결과 — 이로치·메가는 이미 메타/폼 처리가 완료되어 추가 작업 대상이 아니다.** 초기 가설은 "이로치·메가 완성도가 CTR 지렛대"였으나, 코드 조사로 다음이 확인됐다:
> - **메타/title/canonical은 폼·이로치별로 이미 정상 분기**된다. `generateMetadata`가 `searchParams`를 읽어(`src/app/detail/[pokemonId]/(form)/page.tsx:34-47`) `isShiny`를 판정하고, `src/module/generateDetailSeoMetaData.ts:85`에서 title에 "이로치"를 붙인다. 즉 "이로치 title 누락" 같은 메타 문제는 존재하지 않는다.
> - **폼별 콘텐츠 차별화(이로치 색상 설명 등)는 과거에 "이미지만 다르고 내부 정보는 동일"하다는 판단으로 별도 구현하지 않기로 결정**했다. 이 결정을 유지한다.
>
> 따라서 이로치·메가는 본 기획의 **신규 작업 항목에서 제외**한다. 상세 페이지 CTR 기여는 이로치·메가 완성도가 아니라, **정보 확장 항목(진화조건·습득법·도감설명) 자체의 콘텐츠 두께**에서 나온다.

## 2. 목표와 기대 효과 (정량)

**North Star**: MAU 상승 (기준 23,047, `metrics-baseline.md`)
**직접 KPI**: 상세 페이지 검색 CTR (현재 1.20% → 목표 2.0%+)
**부수 효과**: 상성표 클릭 점유율 자연 하락 (의존도 완화)

아래는 **노출 불변 가정 하의 이론적 상한**이다. 상세 페이지 노출(881,909)을 고정하고 CTR만 개선했을 때의 계산이며, 실제로는 콘텐츠 추가로 새 키워드가 색인되어 노출·순위가 함께 변하므로 아래 증분은 **낙관적 상한**으로 읽어야 한다.

| 상세 CTR | 상세 클릭 | 증분(이론적 상한) | 상성표 점유율 |
| --- | ---: | ---: | ---: |
| 1.20% (현재) | 10,592 | — | 57.7% |
| **2.0%** (1차 목표) | 17,638 | **+7,046** | 51.5% |
| 2.5% | 22,047 | +11,455 | 48.3% |
| 3.26% (사이트 평균) | 28,750 | +18,158 | 44.1% |

> **Why 이 목표가 타당한가:** 상세 CTR을 사이트 평균(3.26%)까지만 끌어올려도 상세 클릭이 약 2.7배(+18,000/3개월)가 되고, 상성표 의존도는 57.7% → 44%로 **새 페이지 없이** 자연 하락한다. 다만 검색어 TOP은 여전히 상성·타입 계산기이므로(개별 포켓몬명 검색은 소수), 본 작업의 기대치는 "폭발적 신규 유입"이 아니라 **"저평가된 대형 자산(상세 49% 노출)의 전환"**으로 현실적으로 잡는다.

### 2-1. 측정 방법 — 전체 CTR이 아니라 대표 코호트로 인과 측정

전체 상세 CTR은 상성표 등 외생 변수에 휘둘려 **개별 작업의 인과 효과를 분리하기 어렵다.** 따라서 각 항목 착수 시 **개선 대상 페이지 코호트를 미리 지정**하고, 해당 코호트의 before/after CTR을 서치콘솔에서 측정한다.

- **코호트 지정 예**: ③-b(진화조건) 적용 시, 진화조건이 붙는 대표 포켓몬 20종을 코호트로 고정 → 적용 전후 4주 서치콘솔 CTR 비교.
- **측정 기준**: 전체 CTR은 참고 지표로만 보고, **판정은 코호트 before/after**로 한다.
- **주의**: 서치콘솔 데이터에 텐센트 봇은 섞이지 않으나(8절 참조), 계절성·신작 이슈(Z-A 등)가 노출을 흔들 수 있으므로 동일 기간의 비개선 대조군 코호트와 함께 본다.

## 3. 통합 우선순위 (백엔드 데이터 + 프론트 공수 + 유입 효과)

백엔드 팀 우선순위는 **데이터 확보 난이도** 축이다. 여기에 두 축을 겹쳐 재정렬한다.

| 순위 | 항목 | 배포 | 상태 | 프론트 공수 | CTR/유입 효과 | 백엔드 선행 의존 |
| :---: | --- | :---: | :---: | :---: | :---: | --- |
| **1** | ⑤ 전용기 표시 | 1.55.0 | **완료** | 낮음 | 낮음(완결성) | 없음 (플래그 이미 내려옴) |
| **2** | ③-b 진화 방법/조건 | 1.55.0 | **완료** | 중 | **높음** | 폼별 groups 스키마(백엔드 재구축 완료) |
| **3** | ④ 습득법 확장(알·가르침) | 1.56.0 | **완료** | 낮음 | 중(체류·완결성) | EGG는 스키마 有, TUTOR 신규(백엔드 재설계 완료) |
| 후속 | **타입 하위 페이지(별도 문서)** | **1.57.0** | **다음 착수** | - | - | **없음**(백엔드 무의존 검증 완료) |
| **4** | ② 버전별 도감 설명 | **1.58.0** | 대기 | 중 | **높음**(텍스트 색인) | 스키마 확장 필요 — **대기 장기화** |
| **5** | ⑥ 기본 제원(몸무게·키 등) | **1.58.0** | 대기 | **낮음** | 낮음(완결성) | 필드 존재 여부 확인 필요 |
| 보류 | ① 서식지 도감 | 미정 | 보류 | 중 | 낮음(개념 모호) | 스키마 확장 + 기획 정의 |

> **재배정(2026-08-20, 사용자 결정):** ②의 백엔드 스키마 확장이 **타입 상성 개선 작업 전체를 수행해도 끝나지 않을 만큼** 길어질 전망이라(백엔드 확인), **1.56.0을 ④로 마감**하고 순서를 뒤집는다. ②·⑥은 **1.58.0**으로 이동하고, 백엔드 의존이 없는 **타입 하위 페이지 작업을 1.57.0으로 당겨** 대기 시간을 채운다. ⑥도 함께 미루는 이유는, ⑥ 하나(경량 작업)를 위해 스키마 필드 실측을 기다리면 이미 완료된 ④의 배포가 늦어지기 때문이다. 상세 근거는 [type-effectiveness-seo-expansion-spec.md](./type-effectiveness-seo-expansion-spec.md) **§26.9**.

> **릴리즈 분할(2026-08-09, 사용자 결정):** ③-b 진화 조건이 착수 시 예상(단순 조건 표시)보다 크게 확장됐다 — 백엔드가 진화 정보를 폼별 `groups` 구조로 재구축했고, 프론트도 폼별 그룹 섹션·다단계 리전 계통·버전 탭·폼별 상세 링크까지 구현하며 스프린트 하나 분량이 됐다. 이에 **1.55.0은 ⑤전용기 + ③-b진화까지로 배포**하고, 남은 실작업 항목(④②⑥)은 **1.56.0으로 이관**한다. ①(서식지)은 여전히 보류. 1.56.0 착수 순서는 아래 우선순위(④→②→⑥)를 유지한다.

> **⑥ 기본 제원(몸무게·키 등)의 배치 근거(사용자 결정):** 몸무게·키·분류 등은 포켓몬당 값이 하나로 고정된 짧은 텍스트라 CTR 지렛대는 작으나(완결성 보강), **기존 "기본 정보" 카드에 `dt/dd` 행을 추가**하는 경량 작업이라 공수가 가장 낮다. 유입 효과가 낮으므로 **실작업 가능한 항목 중 맨 끝(5순위)**에 둔다. ①(서식지)은 기획 정의가 선행돼야 하는 "보류(작업 불가)" 상태라 순위 밖으로 분리했다 — 제원은 ① 앞(실작업 가능 항목의 마지막)에 위치한다. 착수 전 `PokemonDetail` 스키마에 몸무게·키 필드가 이미 있는지 확인이 필요하며, 없으면 백엔드 요청 대상이 된다.

<!-- -->

> **③의 분리 (검토 반영):** 초기 기획의 "③ 진화조건 + 메가·이로치 완성도" 묶음은 성격이 다른 두 작업이 섞여 있어 분리했다.
>
> - **③-a 이로치·메가 완성도 → 작업 제외.** 코드 검증 결과 메타/폼 처리는 이미 완료돼 있고(1-3절), 폼별 콘텐츠 차별화는 과거에 "이미지만 다르고 내부 정보는 동일"하다는 판단으로 하지 않기로 결정했다. 이 결정을 유지하므로 신규 작업 대상이 아니다.
> - **③-b 진화조건만 남겨 2순위**로 둔다. 아래 근거의 ③은 ③-b(진화조건)를 가리킨다.

### 우선순위 근거

- **⑤가 1순위인 이유(백엔드와 일치, 근거 강화)**: `signatureMoves: Boolean` 플래그가 이미 `getPokemonDetail` 쿼리로 내려온다(`src/gql/query.graphql:116,132`). 현재 UI가 소비하지 않을 뿐(스토리 파일에서만 사용). **백엔드 작업 0, 프론트 표시만 추가**하면 되므로, 백엔드 대기 없이 이번 스프린트에 단독 착수 가능한 **유일한 항목**이다.
- **③-b(진화조건)가 2순위인 이유**: 백엔드는 "데이터가 쉬워서" 2순위로 뒀으나, 프론트/유입 관점의 근거는 **"○○ 진화" 검색 수요 + 상세 노출 전환**이다. 진화조건은 진화 체인에 "레벨 20 이상", "천둥의돌 사용" 같은 고유 텍스트 콘텐츠를 더해 페이지 두께를 키우므로 CTR 기여가 크다. (초기 기획의 "이로치·메가 완성도" 근거는 위 ③ 분리 설명대로 제외됨.)
- **②가 ④보다 서비스 가치는 높다(순서 미세 조정)**: 버전별 도감 설명은 **텍스트 콘텐츠 = 색인 강화 + CTR 개선** 효과가 크다. 다만 Z-A 신규 포켓몬의 한글 설명 확보 리스크 때문에 실행 순서는 ④ 뒤에 둔다.
- **⑥(기본 제원)이 5순위(실작업 항목 중 맨 끝)인 이유**: 공수는 가장 낮으나(기존 카드에 행 추가), 값이 고정된 짧은 텍스트라 새 키워드 색인·CTR 기여가 작다. 유입 효과 기준으로는 ② 다음에 두는 게 맞고, ①(보류)보다는 앞이다. 즉 **"실제로 착수 가능한 항목 중 마지막"**에 배치한다.
- **①이 보류(순위 밖)인 이유**: Z-A는 뤼미에르 시티 단일 무대라 전통적 "서식지" 개념과 맞지 않고, 검색 수요 근거도 없다. 기획 정의(야생 조우 구역/출현 지역 등)가 선행돼야 하며, 유입 기여도 불확실하다. 착수 조건(기획 정의)이 미충족이라 순위 번호를 부여하지 않고 "보류"로 둔다 — 제원(⑥)보다 뒤가 아니라, **작업 가능 여부 자체가 다른 별도 트랙**이다.

### Phase 4 — ② 버전별 도감 설명 (**1.58.0**)

> **배정 변경(2026-08-20):** 백엔드 스키마 확장 대기가 길어져 **1.56.0 → 1.58.0으로 이동**했다(3절 재배정 참조). 아래 설계는 그대로 유효하며, 백엔드 응답이 준비되는 시점에 착수한다.

- 아이템 설명 UI 패턴 재활용. 한글 미확보 종은 조건부 렌더로 숨김(4-1 정책 참조).
- **표시 방식(사용자 결정) — 대표 1개 본문 + 버전 셀렉터.** 버전마다 flavor text가 다르나 문장이 대부분 유사(예: 같은 포켓몬의 여러 버전 설명이 거의 동일)해, **전 버전을 통째로 나열하면 중복 콘텐츠로 취급**되어 페이지 품질 점수에 마이너스가 된다([중복/저가치 콘텐츠](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)). 따라서 기본은 **대표 설명 1개만 본문에 노출(크롤 대상)**하고, 나머지 버전은 셀렉터(탭)로 사용자 인터랙션 시 확인하게 한다.
- **셀렉터의 SEO 처리 — 전환분은 클라이언트 렌더.** 초기 HTML에 전 버전 텍스트를 모두 넣고 CSS로 접으면 크롤러가 전부 읽어 중복 회피 목적이 무너진다. 셀렉터 전환으로 노출되는 비대표 버전 설명은 **클라이언트에서만 렌더**해, 색인 대상은 대표 1개로 유지한다.
- **대표 버전 선정 규칙 — 착수 시 확정.** 대표를 무엇으로 고를지(최신 버전 / 서술이 가장 풍부한 버전 / 세대 대표 고정 규칙)는 백엔드 데이터 상태를 보고 정한다. 최신 버전은 신작(Z-A) 한글 미확보 리스크가 있으므로 5-1 정책(미확보 시 조건부 숨김)과 함께 판단한다.

### Phase 7 — 타입 하위 페이지 구축 (**1.57.0**, 별도 문서)

**1.56.0(④)이 배포되면 곧바로** `/type-effectiveness` 메인 보강 + `/type-effectiveness/[type]` 타입별 상세 페이지 구축에 착수하며, **1.57.0으로 배정**됐다(2026-08-20 재확정 — ②·⑥보다 앞선다). 상세 기획과 배정 근거는 [type-effectiveness-seo-expansion-spec.md](./type-effectiveness-seo-expansion-spec.md) **§26.9**에 있으며, 이 문서의 범위 밖이다.

**1.57.0 범위 한정:** 메인 title·H1 재설계(2-a) + 1차 3~4개 타입(독·악·격투) MVP(2-b)까지다. **두 작업은 함께 배포**하며, 효과는 개별 기여도가 아닌 **트랙 합산**으로 판정한다(§26.9.3). 18개 타입 전체 확장은 4주 관찰 후 별도 버전으로 배정한다.

> **Why 두 작업이 이어지는가:** 본 문서의 목표는 "상성표 단일 의존 탈피"(§1-1의 SPOF 리스크)이고, 타입 하위 페이지 문서의 목표는 "상성표가 잃은 롱테일 노출 회복"이다. 상반돼 보이나 실제로는 **같은 리스크의 양면**이다 — 2026년 7월 말 `/type-effectiveness` 노출이 7일 만에 -51.9% 빠진 사건이 §1-1이 경고한 SPOF가 현실화한 사례다. 상세 페이지 강화(본 문서)로 의존도를 낮추고, 타입 하위 페이지(별도 문서)로 상성표가 담당하던 검색 커버리지를 분산한다.

**Why 순서가 이러한가:** `/detail/`은 이미 전체 노출의 49%(88만)를 확보해 **전환율만 올리면 되는** 자산이라 효과가 빠르다. 반면 `[type]` 페이지는 노출 0에서 시작해 색인·순위 획득에 최소 4~8주가 걸린다. 1.56.0을 먼저 돌리면 그 대기 시간이 낭비되지 않는다. 순서를 뒤집으면 4~8주가 통째로 빈다.

**1.56.0 작업 중 유의할 연결 지점:** 상세 페이지의 타입 배지를 `/type-effectiveness/[type]`으로 연결하는 내부 링크는 **링크 대상이 생긴 뒤**(Phase 7) 적용한다. 1.56.0 시점에 미리 걸면 404를 가리키게 된다.

### 5-1. "한글 설명 미확보 시" 정책 — **미표시(조건부 렌더)**

②·①에서 신규 포켓몬 한글 설명이 위키에 없을 경우, **수기 보완이 아니라 해당 섹션을 숨긴다(조건부 렌더).**

> **Why:** 빈 값이나 기계번역 티가 나는 저품질 텍스트를 색인시키면 페이지 품질 점수에 마이너스로 작용해 CTR 개선 목표와 정면으로 배치된다. 없는 종은 섹션을 숨기고 있는 종만 노출하는 것이 SEO상 안전하다.
