## 1. 문서 목적

이 문서는 `/type-effectiveness` 페이지의 최근 검색 노출 감소를 분석하고, 다음 목표를 동시에 달성하기 위한 개선안을 정리한다.

1. 기존 `포켓몬 상성`, `포켓몬 상성표`, `포켓몬 상성 계산기` 검색 유입 보호
2. 감소한 `물타입 약점`, `악타입 약점`, `페어리 상성` 등의 롱테일 검색 노출 회복
3. 계산기와 정보형 콘텐츠의 역할 구분
4. 중복 페이지를 만들지 않으면서 검색엔진이 이해하기 쉬운 URL 구조 구축
5. Next.js 기반에서 정적 생성, 메타데이터, 사이트맵, 내부 링크를 일관되게 적용
6. 모바일 사용성과 광고 수익을 해치지 않는 단계적 배포

> **읽는 순서 주의:** §2~§25는 2026-08-06 시점의 원본 분석이다. 이후 코드 검증으로 일부 진단이 뒤집혔고 실행 순서가 조정됐다. **실제 착수 전에는 §26(실행 순서 조정)을 먼저 읽는다.**

## 2. 논의 배경

2026년 7월 29일 전후 `/type-effectiveness` 페이지의 Search Console 노출이 급격하게 감소했다.

초기에는 다음 가능성을 검토했다.

- UI 개편으로 인한 본문 의미 변화
- H1, title, canonical 또는 robots 설정 오류
- 클라이언트 렌더링으로 인한 본문 미노출
- 광고 재삽입에 따른 사용자 경험 저하
- 배포 실패 또는 캐시 문제
- Google이 일시적으로 확장하던 검색어 노출 범위를 회수한 현상

소스코드와 GitHub 변경 이력을 검토한 결과, 다음과 같은 명백한 원인 장애는 확인되지 않았다.

- `noindex` 적용
- canonical 제거 또는 잘못된 canonical
- H1 제거
- 전체 상성표 본문 제거
- Googlebot 접근 차단
- 빈 HTML만 제공하는 완전한 CSR 전환

또한 Search Console URL 검사에서 최근까지 Googlebot이 페이지를 다시 크롤링한 것이 확인된다.

따라서 현재 문제는 **페이지가 검색에서 완전히 제외된 현상**이 아니라, **어떤 검색어에서 얼마나 자주 노출되는지가 재조정된 현상**으로 보는 것이 타당하다.

CTR 상승은 페이지 성과가 실제로 개선됐다는 의미가 아니다. 노출 감소폭이 클릭 감소폭보다 훨씬 컸기 때문에 발생한 **검색어 구성 변화**다.

### 핵심 발견 1: 노출 감소의 중심은 타입별 롱테일이다

검색어 CSV에서 확인할 수 있는 노출 감소는 총 30,706회다.

그중 다음 두 검색어군이 24,296회를 차지한다.

- 타입 약점·카운터: -20,450회
- 개별·복합 타입 상성: -3,846회

두 검색어군은 **표시된 검색어 노출 감소의 약 79.1%**를 차지한다.

페이지 전체 노출 감소 기준으로는 약 **61.9%**다.

Search Console 검색어 목록에 표시되지 않는 익명·저빈도 검색어에서도 8,523회의 노출 감소가 발생했다. 이 구간에도 롱테일 검색어가 상당수 포함됐을 가능성이 높지만, 검색어를 직접 확인할 수 없으므로 확정할 수는 없다.

### 핵심 발견 2: 실제 클릭 손실은 핵심 검색어에서 더 크게 발생했다

노출 감소의 대부분은 타입별 약점 검색어지만, 실제 클릭 감소의 대부분은 다음 검색어군에서 발생했다.

- 일반 상성·타입: -296클릭
- 상성표: -88클릭

두 그룹은 검색어 CSV에서 확인되는 클릭 감소 436회의 약 88%를 차지한다.

따라서 타입별 상세 페이지를 추가하는 것만으로 현재 손실된 클릭 전체가 바로 회복되지는 않는다.

> 타입별 상세 페이지는 검색어 커버리지와 미래 유입을 넓히는 전략이며, 기존 `/type-effectiveness`의 핵심 검색어 CTR과 순위를 보호하는 작업도 반드시 병행해야 한다.

## 6. 검색어가 완전히 사라진 것인가

비교 파일에는 총 1,234개의 검색어가 포함된다.

- 이전 기간 노출 검색어: 1,159개
- 이후 기간 노출 검색어: 1,086개
- 이전에는 있었지만 이후 0회로 표시된 검색어: 148개
- 이후 새로 표시된 검색어: 75개

그러나 완전히 사라진 148개 검색어의 이전 노출 합계는 987회, 클릭은 13회에 불과하다.

즉, 이번 노출 감소는 주로 검색어가 완전히 삭제된 현상이 아니다.

> 기존에 계속 노출되던 다수의 타입별 검색어에서 노출 빈도가 동시에 크게 줄어든 현상이다.

따라서 "사라진 키워드 목록"을 복원하는 접근보다 **검색어군별 노출 빈도 회복과 검색 의도별 대표 URL 구축**이 더 중요하다.

## 9. 배포와 하락 시점의 관계

동일한 주간 비교 결과는 배포 전후의 변화가 존재한다는 점은 더 명확하게 보여준다.

다만 다음 이유로 배포가 직접 원인이라고 확정할 수는 없다.

1. 이후 기간이 7월 28일부터 시작해 배포 이전 데이터가 일부 포함된다.
2. Search Console 일별 날짜는 서비스 집계 기준에 따라 한국 시간의 배포 시각과 정확히 일치하지 않을 수 있다.
3. 같은 시기에 Google의 검색 결과 제공 범위 조정이나 검색 수요 변화가 함께 발생할 수 있다.
4. 코드에서는 noindex, canonical 오류, 본문 제거 등의 직접적인 장애가 발견되지 않았다.
5. 페이지는 최근에도 Googlebot에 정상적으로 크롤링된다.

현재 가장 합리적인 결론은 다음과 같다.

> 대규모 UI·DOM 개편이 Google의 페이지 재평가를 유발했을 가능성은 남아 있다. 그러나 실제 감소 형태는 기술적 색인 실패나 전체 순위 붕괴보다, 기존 페이지가 담당하던 타입별 롱테일 검색 범위가 축소된 패턴에 더 가깝다.

배포와 노출 감소의 시간적 상관관계는 강하지만, 코드적 증거만으로 단일 인과관계를 확정할 수는 없다.

> **2026-08-10 갱신:** 이후 코드 검증에서 위 5개 항목에 더해 **CSR 전환 가설과 캐시 정책 변경 가설이 모두 배제**됐다. §26.1 참조.

## 10. 권장 정보 구조

### 10.1 최종 권장 URL

```text
/type-effectiveness
/type-effectiveness/normal
/type-effectiveness/fire
/type-effectiveness/water
/type-effectiveness/electric
...
/type-effectiveness/fairy
```

별도의 `/type` 허브는 현재 단계에서는 만들지 않는다.

`/type-effectiveness`가 다음 역할을 동시에 수행한다.

- 전체 타입 상성표
- 단일·복합 타입 상성 계산기
- 타입별 상세 페이지 허브

## 12. 타입별 상세 페이지 역할

타입별 페이지는 계산기에서 타입을 미리 선택한 복제 페이지가 되어서는 안 된다.

### 잘못된 예

`/type-effectiveness/water`가 다음만 제공하는 경우:

- 기존 계산기에 물 타입이 미리 선택됨
- 동일한 전체 상성표
- 동일한 설명
- 제목만 물 타입으로 변경

이 경우 주요 콘텐츠가 `/type-effectiveness`와 거의 동일하므로 중복 또는 유사 페이지로 묶일 가능성이 높다.

### 권장 콘텐츠 구조

예시: `/type-effectiveness/water`

#### H1

```text
물 타입 약점과 상성
```

#### 첫 화면 요약

- 방어 약점: 전기, 풀
- 방어 반감: 불꽃, 물, 얼음, 강철
- 방어 무효: 없음
- 공격시 유리: 불꽃, 땅, 바위
- 공격시 불리: 물, 풀, 드래곤

#### 본문 섹션

1. 물 타입 방어 상성
2. 물 타입 공격 상성
3. 2배, 0.5배, 0배 배율 설명
4. 대표 복합 타입 사례
   - 물/땅
   - 물/비행
   - 물/드래곤
5. 4배 약점과 약점 없음 사례
6. 물 타입의 고유 효과
7. 대표 물 타입 포켓몬
8. 물 타입 포켓몬 전체 보기
9. 대표 물 타입 기술
10. 물 타입 기술 전체 보기
11. 물 타입으로 상성 계산하기
12. 자주 묻는 질문

### 중복을 피하는 핵심 기준

공통 상성 데이터는 공유해도 문제가 없다.

그러나 각 상세 페이지는 계산 결과 이상의 추가 가치를 제공해야 한다.

- 타입 고유 면역 또는 효과
- 대표 복합 타입
- 4배 약점 사례
- 타입별 포켓몬과 기술
- 세대별 변경 사항
- 타입에 특화된 질문과 설명

## 13. 계산 상태 URL 정책

사용자가 타입을 선택한 상태를 공유할 필요가 있다면 다음과 같은 방식이 가능하다.

```text
/type-effectiveness?defense=water
/type-effectiveness?attack=fire&defense=water
```

이 URL은 사용자 편의용 상태 URL로만 사용한다.

권장 정책:

- canonical: `/type-effectiveness`
- 사이트맵에서 제외
- 검색엔진용 상세 페이지로 사용하지 않음
- 가능한 경우 프래그먼트 또는 클라이언트 상태 사용
- 타입 상세 정보 링크는 파라미터 URL이 아닌 `/type-effectiveness/[type]`으로 연결

타입 조합을 모두 색인하면 유사 URL이 대량 생성될 수 있다. 18개 단일 타입 상세 페이지부터 운영하고, 복합 타입 페이지는 실제 검색 수요와 고유 콘텐츠가 충분한 조합만 선별한다.

## 14. 메타데이터 권장안

### 14.1 메인 페이지

#### title 후보

```text
포켓몬 타입 상성표·상성 계산기 | 포케코리아
```

#### H1 후보

```text
포켓몬 타입 상성표·상성 계산기
```

단, 현재 변동 구간에서 제목·H1·UI를 동시에 변경하지 않는다.

타입별 상세 페이지 출시와 별도로 테스트하고, 변경 후 최소 2~4주간 개선 여부를 기준으로 관찰한다.

> **2026-08-10 갱신:** 현재 메타는 `포켓몬 상성 계산기`로 **`상성표` 키워드가 title에 없다**(`src/app/type-effectiveness/_metadata/typeEffectivenessMetadata.ts`). 클릭 손실의 88%가 `포켓몬 상성`·`상성표` 계열에서 났으므로 이 조정은 유효한 지렛대다. 다만 단독 선행하지 않고 **Phase 2(타입 상세 페이지 출시)에서 하위 페이지와 키워드 분담을 함께 설계**한다. 근거는 §26.3 참조.

### 14.2 타입 상세 페이지

예시: 물 타입

```text
title: 물 타입 약점·상성 정리 | 포케코리아
description: 포켓몬 물 타입의 약점, 반감, 공격 상성과 방어 상성을 확인하세요. 복합 타입에 따른 4배 약점과 대표 물 타입 포켓몬·기술도 함께 제공합니다.
H1: 물 타입 약점과 상성
canonical: https://poke-korea.com/type-effectiveness/water
```

각 타입 페이지는 반드시 고유한 title, description, H1, canonical을 가져야 한다.

타입 상세 페이지의 canonical을 `/type-effectiveness`로 지정하면 독립 색인 목적과 충돌하므로 자기 자신의 canonical로 지정한다.

## 16. Next.js 구현 방향

권장 라우트 구조:

```text
src/app/type-effectiveness/page.tsx
src/app/type-effectiveness/[type]/page.tsx
```

### 권장 기능

- `generateStaticParams`
  - 18개 타입 경로를 빌드 시 정적 생성
- `generateMetadata`
  - 타입별 고유 title, description, canonical 생성

- 타입 페이지별 고유 OG 이미지 생성 또는 공통 템플릿 기반 동적 이미지 사용

- 타입 상성 핵심 정보는 초기 HTML에 포함
- 상성 계산 인터랙션만 Client Component로 제한
- 상세 페이지 전체를 불필요하게 Client Component로 만들지 않음
- 타입 데이터와 설명은 Server Component에서 렌더링
- 광고 영역은 최소 높이를 확보해 CLS 방지

> **2026-08-10 갱신:** 현재 메인 페이지는 이 원칙에 **이미 부합**한다. 데이터가 전부 정적 상수라 초기 HTML에 상성표 324셀이 포함되고, 설명 섹션은 순수 Server Component다. `'use client'`는 열 하이라이트·배율 필터 등 인터랙션에만 걸려 있다. 신규 `[type]` 페이지도 같은 구조를 따른다. §26.1 참조.

## 23. 최종 결론

이번 동일 기간 비교로 다음이 더 명확해졌다.

1. 노출 감소는 실제이며 약 51.9%다.
2. 전면적인 순위 붕괴나 색인 실패는 아니다.
3. 표시된 검색어 노출 감소의 약 79%가 타입별 약점·상성 롱테일에서 발생했다.
4. 그러나 실제 클릭 감소의 대부분은 `포켓몬 상성`, `포켓몬 상성표` 등 핵심 검색어에서 발생했다.
5. `포켓몬 상성 계산기` 검색 의도는 매우 안정적으로 유지되고 있다.
6. 따라서 해결책은 기존 페이지를 상세 페이지로 대체하는 것이 아니다.
7. `/type-effectiveness`는 계산기·전체 상성표·허브로 유지한다.
8. `/type-effectiveness/[type]`은 개별 타입 질문을 해결하는 독립 정보 페이지로 구축한다.
9. 타입 상세 페이지 확장과 기존 메인 페이지의 핵심 검색어 CTR 회복을 병행한다.
10. 첫 단계는 검색량과 감소량이 큰 8개 타입으로 검증하는 것이 안전하다.

## 25. 데이터 해석상의 한계

- Search Console은 개인정보 보호와 표시 제한 때문에 모든 검색어를 제공하지 않는다.
- 검색어 목록의 합은 노출을 개별 키워드 수준으로 복원할 수 없다.
- 평균 순위는 검색 위치, 기기, 국가, 검색 결과 형태를 합친 평균값이다.
- 동일한 7일 비교라도 검색 수요와 외부 검색 결과 변화가 완전히 동일하다고 보장할 수 없다.
- 이번 데이터는 배포 시점과 하락의 상관관계를 강화하지만 인과관계를 확정하지 않는다.
- 상세 페이지 출시 효과는 최소 2~4주 이상, 가능하면 28일 단위로 판단한다.

## 26. 실행 순서 조정 (2026-08-10)

원본 분석(§2~§25) 이후 코드 검증을 거치며 진단 2건이 뒤집혔고, 그 결과 실행 순서를 재배치했다. **착수 전 이 절을 우선한다.**

### 26.1 기술적 장애 후보 2건 추가 배제

§9는 "noindex·canonical·본문 제거 등 직접적인 장애가 발견되지 않았다"까지만 확인했다. 이후 코드 검증에서 남아 있던 두 가설도 배제됐다.

| 가설                      | 판정     | 근거                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CSR 전환으로 본문 미노출  | **배제** | 데이터가 전부 정적 상수(`~/constants/typeEffectivenessChart`)라 GraphQL 페칭·지연 로딩이 없다. 18×18 = 324셀이 서버 렌더 시점에 확정되어 초기 HTML에 포함된다. 설명 섹션(`TypeEffectivenessDescription.container.tsx`)은 `'use client'`가 없는 **순수 Server Component**다. `'use client'`는 하이드레이션 대상 선언이지 CSR 전환 선언이 아니며, 이 페이지에서는 열 하이라이트·배율 필터·타입 선택 등 **인터랙션에만** 걸려 있다 |
| 캐시 정책 변경(`4e03f94`) | **배제** | ① **시점 불일치** — 커밋은 7/31, 노출 급감은 7/29로 원인이 결과보다 이틀 늦다. ② **변경 방향이 반대** — 이 커밋은 `/type-effectiveness`에만 붙어 있던 `immutable`을 **제거**했다(재검증 요청조차 막는 가장 강한 캐시 지시자를 뺀 것이므로 크롤러 접근성은 개선). ③ `s-maxage`는 공유 캐시(CDN) 전용이라 봇에게 다른 HTML을 주는 성격이 아니다                                                                                   |

현재 `/type-effectiveness`의 캐시 헤더는 다른 페이지 17곳과 동일하다(`next.config.js`).

```text
public, max-age=10800, s-maxage=31536000, stale-while-revalidate=60
```

> **결론:** 기술적 장애 후보가 모두 소진됐다. 남는 설명은 §9의 결론 — **Google이 이 페이지의 롱테일 노출 범위를 축소한 것**이며, 이는 코드로 고칠 대상이 아니다. 따라서 "긴급 수리" 성격의 작업은 존재하지 않고, 이 문서의 작업은 전부 **중장기 커버리지 확장**으로 성격이 확정된다.

### 26.2 선행 작업이 1.56.0인 이유

이 문서의 작업과 [detail-page-expansion-spec.md](./detail-page-expansion-spec.md)의 1.56.0(④습득법·②도감설명·⑥제원)은 얼핏 상반돼 보인다. 전자는 "상성표를 지키고 하위 페이지를 키우자"이고, 후자의 목표는 "상성표 단일 의존 탈피"다. 그러나 실제로는 ROI가 다른 두 트랙이다.

|           | 1.56.0 (④②⑥)                                         | 이 문서 (`[type]` 페이지)                          |
| --------- | ---------------------------------------------------- | -------------------------------------------------- |
| 대상      | `/detail/` — **이미 노출 49%(88만) 확보, CTR 1.20%** | `/type-effectiveness/[type]` — **노출 0에서 시작** |
| 성격      | 랭크된 자산의 **전환율 개선**                        | 신규 랭킹 획득(**장기전**)                         |
| 효과 발현 | 빠름(색인 이미 완료)                                 | 느림(최소 4~8주 색인 대기)                         |
| 리스크    | 낮음(기존 페이지 보강)                               | 중(18개 유사 페이지 = 중복 리스크)                 |

§4의 핵심 발견 2가 이 배치의 직접 근거다 — **클릭 손실의 88%는 핵심 검색어에서 났고, `[type]` 페이지는 그 부위를 치료하지 않는다.** 타입별 롱테일은 노출을 크게 잃었지만 원래 CTR이 매우 낮아(해당 구간 클릭은 39 → 54회로 오히려 증가) 클릭 회복 기여가 작다.

또한 `[type]` 페이지가 색인·순위를 얻는 4~8주 대기 시간 동안 1.56.0을 돌리면 그 기간이 낭비되지 않는다. 순서를 뒤집으면 그 시간이 통째로 빈다.

### 26.3 메인 title·H1 조정을 선행하지 않는 이유

§14.1의 title 후보(`포켓몬 타입 상성표·상성 계산기`)는 유효하다. 현재 메타에 `상성표` 키워드가 없고, 잃은 클릭 대부분이 그 계열이기 때문이다. 그럼에도 **단독 선행하지 않고 Phase 2에서 하위 페이지와 함께 설계**한다.

1. **두 번 바꾸게 된다.** `[type]` 페이지가 생기면 §10대로 메인의 역할이 "계산기 + 전체 상성표 + 허브"로 재정의되고, title도 그에 맞춰 다시 설계된다. title 변경은 각각 2~4주 평가가 필요하므로 두 번 바꾸면 관찰 기간이 겹쳐 **어느 변경의 효과인지 분리할 수 없다.**
2. **문서 자체가 금지한다.** §14.1은 "현재 변동 구간에서 제목·H1·UI를 동시에 변경하지 않는다"고 명시하고, §19는 title 조정을 3단계(상세 페이지 색인 확인 후)에 배치했다.
3. **관찰이 오염된 구간이다.** 노출이 -51.9% 흔들린 직후라 기준선이 불안정하다. 지금 바꾸면 이후 회복이 title 덕인지 Google 조정의 자연 복귀인지 구분할 수 없다(§19 1단계의 "원복 금지·대규모 변경 금지"와 같은 취지).

### 26.4 1차 출시 규모를 8개에서 3~4개로 축소

§17은 8개 타입 동시 출시를 제안하나, **독·악·격투 3~4개로 축소**한다.

> **Why:** §12가 경고한 "복제 페이지 함정"을 피하려면 타입당 고유 콘텐츠(대표 복합 타입·4배 약점·해당 타입 포켓몬/기술·세대별 차이)를 실제로 채워야 한다. 8개를 동시에 만들면 타입당 투입이 얇아져 오히려 유사 페이지로 묶일 위험이 커진다. 이는 §22의 "타입명과 배율만 바꾼 얇은 페이지 대량 생성"에 해당한다. 3~4개로 색인·순위 반응을 4주 관찰한 뒤 확장하는 편이 안전하다.

### 26.5 확정된 Phase 배치

```text
Phase 0 — 관찰 (지금 ~ 2주, 코드 변경 없음)
  · /type-effectiveness 코드·메타·UI 일절 변경 금지
  · Search Console 7일 단위 비교 축적, 노출 자연 회복 여부 확인
  · 판단 시점: 2026년 8월 말

Phase 1 — 1.56.0 상세 페이지 확장 (선행 작업, 본 문서 범위 밖)
  · ④ 습득법 → ② 도감설명 → ⑥ 제원
  · detail-page-expansion-spec.md 참조

Phase 2 — 타입 하위 페이지 + 메인 재설계 (1.56.0 배포 후)
  · /type-effectiveness/[type] 라우트 구축 (§16)
  · 3~4개 타입 우선 출시 — 독·악·격투 (§26.4)
  · self-canonical, 고유 title/description/H1 (§14.2)
  · 메인 title·H1을 이때 함께 재설계 (§26.3)
  · 상세·기술 페이지 타입 배지 → 하위 페이지 내부 링크 (§15)
  · 사이트맵 등록, Breadcrumb JSON-LD
  · 4주 관찰 후 나머지 타입 확장 (§17 평가 항목)
```

Phase 0은 **적극적 무행동**이다. 기술적 장애가 없음이 확인된 이상 손대는 것 자체가 측정을 망친다.
