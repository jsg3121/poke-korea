# specs/

기획서·계획서·현황 문서를 관리하는 폴더입니다.

성격이 다른 문서가 섞이지 않도록 하위 폴더로 나눕니다. 배치 규칙은 [`../conventions/guides/structure.md`](../conventions/guides/structure.md)가 권위 원본입니다.

## 하위 구조

| 폴더         | 담는 것              | 특징                                        |
| ------------ | -------------------- | ------------------------------------------- |
| `service/`   | 타겟·경쟁사          | **지속 갱신** — 최신 상태를 유지한다        |
| `features/`  | 기능별 기획서(SPEC)  | 기능 단위, 완료 후에도 설계 근거로 남는다   |
| `plans/`     | 실행 계획서 (보관본) | **신규 작성하지 않는다** — 기존 문서만 보존 |
| `incidents/` | 장애·사고 기록       | 재발 방지 근거                              |

> **Why 나누는가:** 분류 없이 쌓으면 "지금도 유효한 현황"과 "이미 끝난 일회성 계획"이 섞여, 어느 것을 믿어야 할지 알 수 없다.

## 문서 성격 구분

**`service/`** — 누구를 위한 서비스이고 누구와 경쟁하는가. **지표(트래픽·검색·수익)는 두지 않는다** — 필요할 때 [`/metrics-analysis`](../skills/metrics-analysis/SKILL.md)로 그 시점 값을 조회한다.

> **Why 지표를 두지 않는가:** 2026-05 측정값을 담은 `metrics-baseline.md`·`service-overview.md`가 갱신되지 않은 채 10월 분석까지 "현재 지표"로 읽혔다. API로 언제든 조회할 수 있는 수치를 문서에 옮겨 적으면 반드시 낡는다.

**`features/`** — 이 기능을 왜, 어떻게 만들기로 했는가. 구현이 끝나도 판단 근거로 남는다.

**`plans/`** — 2026-11-28까지 작성한 실행 계획서 보관본. 새로 쓰거나 진행 상황을 갱신하지 않는다. 당시 판단 근거로만 읽는다.

## 진행 상황은 문서에 두지 않는다

진행 상황은 이미 자동으로 남는 기록에서 확인한다.

| 알고 싶은 것     | 보는 곳                                                                                   |
| ---------------- | ----------------------------------------------------------------------------------------- |
| 무엇을 했는가    | 머지된 PR, `changelog/blog/`, 커밋 이력                                                   |
| 무엇이 남았는가  | GitHub Issues — 남은 작업이 생긴 시점에 이슈로 등록하고, PR 본문의 `Closes #N`으로 닫는다 |
| 왜 그렇게 했는가 | `features/` 기획서, `../decisions/architecture.md`, PR 본문                               |

- 기획서·계획서에 `상태` 항목이나 진행 체크박스(`- [ ]`)를 두지 않는다.
- 기존 문서에 남아 있는 `상태`·체크박스는 작성 당시 값이다. **현재 진행 상황의 근거로 쓰지 않는다** — 남은 작업 여부는 코드와 위 기록으로 판단한다.

> **Why (2026-11-28):** `plans/` 문서 7개는 작성 후 진행 상황이 거의 갱신되지 않았다(문서당 커밋 1~2개, 대부분 폴더 이동). 챔피언스 계획서는 페이지가 모두 배포된 뒤에도 "계획 — Phase 0부터 순차 진행"과 미체크 38개로 남아, 남은 작업을 코드로 다시 대조해야 했다. 완료 기록은 PR·changelog에 이미 남으므로 문서 진행 상황은 이중 기록이고, 문서를 고치려면 매번 브랜치가 필요해 갱신이 밀린다. 이슈는 파일이 아니라 브랜치 없이 열고 닫을 수 있다. 운영 규칙이라 이 절에 기록한다.

## 작성 규칙

- 기획서는 `product-planner` 에이전트가 담당한다. 정의는 [`../agents/product-planner.md`](../agents/product-planner.md).
- 구조 결정은 기획서에 다시 적지 않고 [`../decisions/architecture.md`](../decisions/architecture.md)의 절을 링크한다 — 기록 방법은 [`../decisions/index.md`](../decisions/index.md).
- 백엔드 등 **다른 저장소가 대상인 문서는 두지 않는다.** 이 폴더는 이 저장소의 작업을 다룬다.
