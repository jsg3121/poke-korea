## 1. 배경 (Why)

### 1.1 지금의 문제

상대 포켓몬을 상대하려는 사용자는 "리자몽이 약한 타입"을 알고 싶다. 그런데 계산기는 **타입 칩 최대 2개를 직접 고르게 한다.** 상대의 타입 조합을 이미 알고 있어야 쓸 수 있다.

- 사용자가 아는 것은 포켓몬 이름이고, 타입 조합은 모르거나 헷갈린다. 리전폼·메가처럼 기본 종과 타입이 다른 폼은 더 헷갈린다.
- 조합이 틀리면 결과도 틀린다. 틀렸다는 사실도 알 수 없다.
- 이 변환 단계를 서비스가 대신하면 입력이 "칩 2번 탭"에서 "이름 몇 글자 + 1번 탭"으로 바뀐다.

### 1.2 이 기능을 지금 하는 이유 (근거)

| 근거 | 수치 (GA4 28일 / Search Console 2026-09-13~10-11) |
| --- | --- |
| 상성은 가장 확실한 검색 자산이다 | 타입 상성 랜딩 세션 12,837(전체 2위, 14.5%), 구글 클릭 6,143 |
| 도구형 질의에서 이미 이기고 있다 | "포켓몬 상성 계산기" 1.2위, CTR 56.9% / "포켓몬 상성" 2.9위, CTR 11.9% |
| 랜딩 참여가 낮다 | 참여율 0.48(홈 0.86, 목록 0.70), 세션당 PV 3.6(홈 15.2) |
| 재방문 비중이 크다 | 타입 상성 PV 25,493 중 재방문 16,835(71.4%) |
| 모바일이 다수다 | 활성 사용자 mobile 28,872 / desktop 16,484 / tablet 1,542 |

**해석 주의.** 참여율 0.48이 "불만 이탈"이라는 근거는 없다. 재방문 71.4%는 답만 보고 닫는 "빠른 조회" 패턴일 수 있다(전략 문서의 가설). 그래서 이 기능은 체류를 늘리는 것이 아니라 **조회를 더 빠르고 정확하게 만드는 것**을 목표로 하고, 성공 지표도 참여율이 아니라 "계산 실행 수"와 "이름 입력 사용"으로 본다. 광고가 PV 모델이므로 PV 하락 여부는 가드레일로 함께 본다.

### 1.3 왜 별도 페이지가 아닌가

- 상성 계산기 검색 유입(위 표)이 이미 이 URL에 모인다. 입력을 같은 페이지에 두면 새 URL, 새 메타데이터, 새 색인 부담이 없다.
- 결과 영역(약점·저항·무효 목록)은 그대로 재사용한다. 입력 방식만 늘어난다.

### 1.4 레퍼런스

- 이름 선택형 계산 도구: [Pokemon Showdown Damage Calculator](https://calc.pokemonshowdown.com/) — 포켓몬을 이름으로 골라 계산한다(방식 참고용).
- 타입 선택형 상성표: [Pokemon Database — Dual type chart](https://pokemondb.net/type/dual) — 타입 조합을 직접 고르는 방식. 현재 포케코리아 계산기와 같은 계열이다.
- 접근성 패턴: [WAI-ARIA APG — Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [List autocomplete 예시](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-autocomplete-list/)

## 2. 목표와 비목표

### 2.1 목표

1. 이름 입력 → 자동완성 목록 → 선택하면, 그 포켓몬(폼)의 타입이 칩에 자동 선택되고 **아래 결과가 지금과 똑같이** 나온다.
2. 기본 종뿐 아니라 **메가진화·리전폼·폼체인지도 각 폼의 실제 타입으로** 계산한다.
3. 입력 컴포넌트는 props로만 동작하고, 계산기 상태(Context)는 컨테이너가 읽는다(`structure.md` 계층 규칙, 7).
4. **URL을 바꾸지 않는다.** (제약 4.1)
5. GA4 이벤트로 이름 입력 사용, 포켓몬 선택, 계산 실행을 측정한다.

### 2.2 비목표 (이번 범위 밖)

| 항목 | 이유 |
| --- | --- |
| 결과 영역(약점·저항 목록)의 디자인·구성 변경 | "지금과 똑같이" 나오는 것이 요구사항이다. 변경하면 효과 귀속이 섞인다 |
| 특성·지닌 도구 효과 반영(예: 부유 → 땅 무효) | 현재 계산기는 타입만 본다. 도입하면 별도 데이터·UI가 필요하다. 대신 안내 문구로 기대를 맞춘다(5.6) |
| 초성 검색("ㄹㅈㅁ") | 서버 `contains` 검색으로 불가능. 백엔드 검색 확장이 필요하다 |
| URL·공유 링크에 선택 상태 저장 | URL 변경 금지 제약. 상태는 메모리에만 둔다 |
| `/type-effectiveness` 메타데이터·H1·PageHeader 설명 변경 | 배포 후 2주 동결(4.2) |
| 헤더 검색 UI 변경 | 별개 기능. 같은 쿼리를 쓰지만 헤더 검색의 화면은 바꾸지 않는다 |
| 파티 타입 커버리지 | 보류. 착수 시점은 별도로 정한다 |
| 최근 본 포켓몬 | 전략 4단계의 별도 기능 |

## 4. 제약

### 4.1 URL을 바꾸지 않는다

이 사이트는 `router.replace`로 URL이 바뀌면 GA4 향상된 측정의 history 기반 page_view가 발생해 지표가 부풀려지는 문제가 확인됐다(도감 목록 `/list` 84,727 PV 중 필터 변경분이 대부분 — 트래픽 스냅샷 정정). 이름 입력과 선택 상태는 컴포넌트 메모리에만 둔다. 참고: [GA4 향상된 측정 — 브라우저 기록 기반 페이지 변경](https://support.google.com/analytics/answer/9216061).

> **Why:** 이 기능의 성공 여부를 GA4로 판정해야 한다. 측정 자체가 오염되면 판정이 불가능하다.

### 4.2 메타데이터 2주 동결

효과 귀속을 위해 `/type-effectiveness` 메인의 title, description, canonical, JSON-LD, H1, PageHeader description은 **배포 후 2주(14일) 동안 변경하지 않는다.** 별도 SEO 트랙(전략 2단계)은 이 기간 이후에 착수한다. 계산기 섹션 안의 가이드 문구는 상황에 맞게 바꿀 수 있다(6.1).

### 4.3 백엔드 선행 변경 (상용 배포 완료)

`searchPokemonWithAllForms`의 `types` 추가와 폼 이름 검색 고도화(8)는 2026-10-19 상용에 배포됐다. 이 기능을 위해 백엔드를 더 바꾸지 않는다(5.2).

### 4.4 모바일 우선, 브레이크포인트 2종

- [ADR-0020](../../decisions/records/ADR-0020-breakpoint-two-only.md): `mobile`·`desktop` 2종만 쓴다. 새 브레이크포인트를 만들지 않고, 레이아웃은 한 값으로 전 구간을 커버하게 만든다.
- [ADR-0011](../../decisions/records/ADR-0011-tab-touch-target-24px.md): `SearchInput`은 디바이스 무관 44px 유지. 탭·칩만 슬림 예외다. 따라서 이름 입력창은 44px이고, **자동완성 목록의 각 행은 칩이 아니므로 44px(`min-h-touch`)을 유지**한다. 선택 해제는 "선택 초기화"(44px)로 하며 별도 지우기 버튼은 없다(5.1). 근거: [WCAG 2.2 — 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

## 5. 기능 정의

### 5.1 사용자 흐름과 선택 규칙

1. 사용자가 계산기 섹션에서 "포켓몬 이름으로 찾기" 입력창을 본다(타입 칩 위).
2. 글자를 입력하고 멈추면(디바운스 500ms) 자동완성 목록이 뜬다. 기본 종과 그 폼이 함께 나온다(예: "라이츄" → 라이츄, 메가라이츄X·Y, 라이츄 알로라의 모습).
3. 목록에서 항목을 탭하면 입력창에 이름이 채워지고 목록이 닫힌다. **칩이 그 폼의 타입으로만 선택**되고 결과가 갱신된다.

**선택 규칙 (2026-10-15 사용자 결정)**

| 상황 | 동작 |
| --- | --- |
| 포켓몬을 고른다 | 기존 칩 선택과 관계없이 **그 포켓몬 타입으로만** 칩을 바꾼다(합치지 않음). 결과는 "상대 한 마리"의 약점이기 때문이다 |
| 이름으로 설정된 상태의 다른 칩 | **비활성화**한다. 포켓몬 타입이 1개여도 나머지 칩은 모두 비활성이다(2026-10-19 사용자 결정). 다른 타입을 고르려면 "선택 초기화"로 먼저 해제한다 |
| 이름으로 설정된 상태에서 켜진 칩을 누른다 | **모두 해제**한다. 칩, 이름 입력, 선택 표시줄이 비워져 아무것도 선택되지 않은 상태가 된다(2026-10-19 사용자 결정). 토글 직관과 맞춘다 |
| 다른 포켓몬을 다시 고른다 | 첫 줄과 같다(통째로 교체). 새 포켓몬을 고르기 전까지는 이전 선택이 유지된다(5.4) |
| "선택 초기화" | 칩과 이름 입력, 선택 표시줄을 모두 비운다. **선택을 지우는 버튼은 이것 하나만 둔다**(선택 표시줄에 지우기 버튼 없음, 2026-10-19 사용자 결정). 이름 선택 상태의 주 해제 수단이므로 터치 타겟 44px를 지킨다 |

- **칩 비활성화**: 지금은 칩으로 2개를 고르면 나머지 칩을 비활성화한다(`TypeCalculator.container.tsx`의 `disabled = isMaxSelectType && !active`). 이 동작은 유지하고, **선택 출처가 이름이면 선택된 타입 수와 관계없이 켜진 칩 외의 칩을 모두 비활성화**한다. 선택 출처(`chip` / `name`)는 Context가 가진다(7).
- **결과로 이동**: 이름을 선택하면 결과 제목이 보이도록 스크롤한다(6.3).

### 5.2 데이터 로딩

**결정(2026-10-15, 사용자 결정): 헤더 검색과 같은 `searchPokemonWithAllForms`를 쓰고, 백엔드가 응답에 `types`를 추가한다.** 프론트는 검색 한 번으로 이름과 타입을 함께 받는다.

- **백엔드 선행 작업**: `PokemonFormInfo`에 `types: [PokemonType!]!` 필드 추가, 폼 4종(기본·메가·폼체인지·리전폼)을 결과에 넣을 때 각 행의 `types`를 담는다. 서비스는 이미 행 전체를 읽고 있어 추가 조회가 없다.
- **프론트**: 이 기능 전용 쿼리를 정의해 필요한 필드(`name`, `number`, `index`, `formType`, `types`, `imagePath`)만 고른다. `imagePath`는 헤더 검색 쿼리가 이미 받는 필수 필드이며, 목록·선택 표시의 썸네일에 쓴다(6.2). 백엔드 반영 후 `npm run codegen`.
- **디바운스**: 헤더 포켓몬 검색(`useSearchPokemon`)과 같은 `src/hooks/useDebounce.ts`의 `useDebounce`와 기본 간격(500ms)을 쓴다. 디바운스된 값을 쿼리 변수로 쓰는 경우라서다. 검색어를 URL에 쓰는 도감·기술·특성 목록 검색은 `useSearchParamInput`을 쓴다([ADR-0023](../../decisions/records/ADR-0023-search-input-url-sync.md)).
- **캐시**: 헤더 검색(`useSearchPokemon`, `cache-and-network`)의 방식을 따른다.
- **`id`는 받지 않는다**(2026-10-20 사용자 결정). 백엔드 `id`는 폼을 가리키는 고정값이 아니다(3). 받으면 Apollo가 `__typename + id`로 정규화해 같은 폼이 서로 다른 객체로 저장되고, 서버 캐시가 비워질 때마다 쓰이지 않는 객체가 쌓인다. 빼도 같은 검색어 결과는 그 검색어의 응답 단위로 캐시되므로 캐싱 효과는 같다. 폼은 `number` + `formType` + `index`로 식별한다(목록 `key` 포함).

**검토 후 채택하지 않은 방식**

| 방식 | 불채택 사유 |
| --- | --- |
| `getPokemonList(filter: { name })` 이름 필터 | 타입은 주지만 **기본 종만** 반환한다. 리전폼·메가를 고를 수 없어 "기본 폼 기준" 배지와 안내가 필요해진다 |
| 검색 후 선택 시점에 폼별 쿼리로 타입을 한 번 더 조회(백엔드 무변경) | 동작은 확인했다(`getPokemonMegaEvolution`·`getPokemonRegionForm`·`getPokemonNormalForm`, 각 0.04~0.07초). 그러나 요청이 두 번이고, ID 체계가 달라(검색은 UUID, 폼은 숫자) **폼 이름으로 짝지어야** 한다. 리전폼 순서도 검색 결과와 폼 쿼리가 서로 달라(나옹: 가라르→알로라 / 알로라→가라르) 순번 매칭은 틀린다. 백엔드에 필드 하나를 더하는 편이 단순하다 |
| 페이지에 전체 목록 포함 / 첫 포커스에 전체 목록 조회 | 이름 입력을 쓰지 않는 방문자에게도 데이터를 보내고(전체 105KB), 폼 타입도 없다 |
| 목록을 저장소에 정적 파일로 보관 | 신규 포켓몬·폼 추가 시 소스와 DB가 어긋난다 |

### 5.3 이름 매칭 규칙

매칭은 서버가 한다. 기본 종 이름으로 찾으면 그 종의 폼을 펼쳐 주고, 폼 이름·지역명으로도 찾으며 어순과 무관하다("알로라 라이츄"·"라이츄 알로라" → "라이츄 알로라의 모습", "히스이" → 히스이 리전폼 전체, 2026-10-20 운영 API 확인). 화면은 디바운스가 끝난 검색어로 받은 결과를 표시한다.

- 검색어 상한: 서버는 30자 또는 5단어를 넘는 검색어에 GraphQL 에러를 반환한다(1.61.4). 입력창에 `maxLength={30}`을 두고, 5단어를 넘으면 요청하지 않고 0건으로 처리한다. 오류 상태(서버 장애 안내)로 보이지 않게 하기 위해서다.

- 정규화: 앞뒤 공백을 제거한 뒤 요청한다. 빈 문자열이면 요청하지 않고 목록을 닫는다(서버도 빈 검색어를 오류로 처리한다). 특수문자가 들어가는 이름(예: 니드런♀, 타입:널 — 실제 데이터 표기는 구현 시 확인)이 입력 가능해야 한다.
- 정렬: 서버가 준 순서(도감 번호순, 같은 번호 안에서는 기본 → 메가 → 폼체인지 → 리전폼)를 그대로 쓴다. 화면에서 다시 정렬하지 않는다(2026-10-20, 폼 이름 검색까지 서버가 처리하게 되어 재정렬 필요가 약해짐).
- 결과 개수: 쿼리는 페이지 없이 결과를 한 번에 모두 준다. **개수를 자르지 않고 전부 보여주며, 높이가 제한된 목록 안에서 스크롤한다**(헤더 검색과 같은 방식, 2026-10-19 사용자 결정). 상한을 두면 잘린 뒤쪽 결과에 도달할 수 없기 때문이다. 최소 입력 글자 수는 두지 않는다("뮤"처럼 한 글자 이름이 있다).
- 한글 IME: 조합 중에도 `onChange`가 발생하지만, 디바운스(500ms)가 끝난 값으로만 요청하므로 조합 중간 값 요청은 대부분 걸러진다. 조합 중 Enter로 선택이 일어나지 않게 한다.
- 응답 순서: 이전 검색어의 늦은 응답이 최신 결과를 덮어쓰지 않게 한다(헤더 검색과 같은 처리 방식을 따른다).

### 5.4 선택 후 표시

- 선택된 포켓몬을 표시한다(썸네일·폼 이름·타입 태그). 모바일은 입력창 아래, 데스크톱은 입력창 오른쪽(입력창이 최대 폭이라 남는 공간)에 둔다(2026-10-19 사용자 결정). 이 표시는 "지금 결과가 어떤 포켓몬 기준인지"를 알려준다. 지우기 버튼은 두지 않고, 해제는 "선택 초기화"로 한다(5.1).
- 선택 후 입력 텍스트를 고치더라도 새로 고르기 전까지 선택과 칩은 바꾸지 않는다. 포커스가 빠져도 입력 텍스트를 되돌리지 않는다 — 기준 포켓몬은 선택 표시줄·칩·가이드 문구가 보여준다(2026-10-20).
- 결과 영역의 제목은 바꾸지 않는다(현재 `selectTypeListKo` 기준). 포켓몬 이름을 결과 제목에 반영하는 것은 후속 개선 후보로만 둔다.

### 5.5 폼 표시와 검색 안내

- 폼은 각자의 실제 타입으로 계산하므로 **"기본 폼 기준" 배지는 두지 않는다**(2026-10-15 사용자 결정).
- 목록에서 같은 종의 폼끼리 구분되도록 폼 이름을 그대로 보여준다(예: "라이츄 알로라의 모습", "메가리자몽X").
- 결과가 0건이면 안내한다: "'{검색어}'와 맞는 포켓몬이 없어요" / "이름을 다시 확인하거나 타입을 직접 선택해 주세요." (2026-10-20 사용자 결정. 폼 이름으로도 검색되므로 "기본 이름으로 검색하라"는 이전 안내는 쓰지 않는다)

### 5.6 특성·도구 효과 안내

이름을 입력하면 사용자는 그 포켓몬의 **특성(예: 부유)** 까지 반영되리라 기대하기 쉽다. 현재 계산은 타입만 본다. 입력 근처 또는 결과 위에 한 줄 안내를 둔다: "특성·지닌 도구 효과는 반영하지 않고 타입만 계산해요."

## 6. UX 요구사항

> 상세 설계는 `ux-designer`에 위임했다(2026-10-19). 아래는 기획 요구사항에 설계 결과 중 사용자가 확정한 사항을 반영한 것이다. 세부 시각 표현은 시안(C3)에서 확정한다.

### 6.1 배치와 가이드 문구

- `TypeCalculator` 섹션 안, 칩 그룹 위에 입력창을 둔다. 순서는 가이드 문구 → 레이블·입력창·도움말(5.6 문구) → 선택 표시줄(선택 시, 모바일) → "선택 초기화"(기존 위치) → 칩 그룹이다. 이름 입력이 새 주 경로라 칩 위에 둔다. "또는 타입을 직접 선택" 같은 구분 줄은 두지 않는다(2026-10-19 사용자 결정).
- 입력창 레이블은 화면에 보이는 레이블 "포켓몬 이름으로 찾기"(`visuallyHiddenLabel={false}` 형태)를 쓴다. placeholder 예시는 흔한 이름 1개.
- 데스크톱은 입력창 오른쪽에 선택 표시줄을 둔다(5.4). 이 빈 공간에 광고는 넣지 않는다(2026-10-19 검토 후 기각): 자동완성 목록이 열리는 입력창 옆은 AdSense가 실수 클릭을 경고하는 위치("드롭다운 메뉴 근처", [광고 게재 위치 정책](https://support.google.com/adsense/answer/1346295))이고, 선택할 때마다 광고를 숨겼다 다시 띄워야 해 "사용자가 요청하지 않은 요소 새로고침" 금지와 레이아웃 이동 문제가 생긴다. 계산기 바로 아래에 이미 상단 배너가 있다.
- **가이드 문구는 상황에 따라 바꾼다**(2026-10-15 사용자 결정). 아무것도 고르지 않았거나 칩으로만 골랐을 때 "포켓몬 이름을 입력하거나 타입을 직접 선택해주세요. 타입은 최대 2개까지 고를 수 있어요.", 이름으로 골랐을 때 "○○ 기준으로 계산했어요. 다른 타입을 고르려면 선택 초기화를 눌러주세요." 바뀌는 것은 계산기 섹션의 가이드 텍스트뿐이고, 메타 정보·H1·PageHeader 설명은 건드리지 않는다(4.2).

### 6.2 자동완성 목록

- **절대 위치 오버레이**로 띄운다. 문서 흐름에 넣으면 아래의 광고 슬롯(`TypeEffectivenessTopBanner`)과 칩 영역이 밀려 레이아웃 이동(CLS)과 광고 위치 변화가 생긴다.
- 헤더 검색 결과 목록이 모바일에서 `z-[600]`를 쓰고 있다. 같은 화면에 두 목록이 겹치지 않도록 z-index와 열림 상태 충돌을 확인한다(헤더 검색을 열면 이쪽을 닫는 등).
- 각 행에 **썸네일(32px)**, 폼 이름, 타입 태그(`Tag` 재사용)를 함께 보여준다. 고르기 전에 타입을 확인할 수 있고, 이름이 비슷한 메가·리전폼은 이미지로 빠르게 구분한다(2026-10-19 사용자 결정).
- 같은 종의 폼은 서버 순서(기본 → 메가 → 폼체인지 → 리전폼)대로 이어서 보여준다. **들여쓰기·종 사이 구분선 같은 묶음 표시는 두지 않는다**(2026-10-19 사용자 결정). 폼 이름에 종 이름이 들어 있어 평평한 목록으로도 구분된다.
- 결과는 전부 보여주고 목록 영역 안에서 스크롤한다(5.3). 목록 끝에서 스크롤이 페이지로 넘어가지 않게 한다.
- 행 높이 44px 이상(4.4). 행 간격은 오탭이 없게 한다.
- 로딩(검색 중), 결과 없음, 조회 실패 상태를 각각 정의한다. 조회 실패 시에도 **타입 칩으로 계속 쓸 수 있어야 한다**.

### 6.3 모바일

- 입력창 폭은 전체 폭. 자동 포커스는 하지 않는다. 키보드가 올라오면 칩과 광고를 가리는데, 재방문 사용자 중 칩만 쓰는 층에게 불편을 주지 않기 위해서다.
- **입력창에 포커스할 때 페이지를 스크롤하지 않는다**(2026-10-19 사용자 결정). 가상 키보드가 목록 일부를 가릴 수 있으며, 실기기에서 확인한다(C5).
- 입력 글자는 **16px**로 한다. `SearchInput`의 `text-sm`(14px)과 모바일 `text-base`(14px)로는 iOS Safari가 포커스 시 화면을 확대하는 경향이 있다. 임의값 대신 `tailwind.config.js`에 16px 토큰(`text-md`)을 추가한다(2026-10-19 승인). 공식 규격이 아니라 알려진 브라우저 동작이므로 실기기에서 확인하고(C5), 확대되지 않으면 되돌린다.
- **이름을 선택하면 결과 제목이 보이도록 스크롤한다**(2026-10-19 사용자 결정). 현재 화면 순서가 계산기 → 광고 → 빠른 보기 → 결과라서, 선택해도 결과가 화면 밖에 있다. 결과 제목이 화면에 걸쳐 보이더라도 항상 화면 위쪽으로 부드럽게(smooth) 옮긴다. 순간 이동하면 입력창이 사라진 것처럼 보이기 때문이다. 모션 줄이기 설정 대응은 WCAG 2.3.3(AAA)이라 이 사이트 기준(AA) 밖이고, JS로 확인하려면 `matchMedia`가 필요해 적용하지 않는다(2026-10-20: "이미 보이면 이동하지 않음" 조건은 빠른 보기 영역이 사라져 제목이 화면 하단에 걸치는 경우가 많아 스크롤이 거의 일어나지 않아 제거). 칩 선택에는 적용하지 않는다(칩을 보며 연속으로 조작하기 때문). 화면 순서(광고 위치)는 바꾸지 않는다.

### 6.4 데스크톱

- 입력창은 전체 폭이 아니라 적정 최대 폭을 둔다. 조정은 `desktop:` 한 값으로만 한다(ADR-0020).

### 6.5 접근성

- **결과 행은 버튼 목록**이다. Tab으로 행을 이동하고 Enter·Space로 고른다. **방향키 탐색(ARIA 콤보박스 패턴)은 지원하지 않는다**(2026-10-20 사용자 결정). WCAG 2.1.1은 키보드로 모든 기능을 쓸 수 있으면 충족하고 방향키를 요구하지 않는다([WCAG 2.1.1 Keyboard](https://www.w3.org/WAI/WCAG21/Understanding/keyboard.html)). 사이트의 다른 검색(헤더 검색)도 Tab 이동 방식이며, 활성 사용자 다수가 방향키가 없는 모바일이다. 결과가 많을 때 Tab을 여러 번 눌러야 하는 비용은 감수한다.
- `SearchInput`은 ref와 나머지 input 속성을 전달하도록 확장했다(1.62.0).
- 선택 결과 안내는 결과 영역의 기존 낭독("{타입} 타입 상성 결과가 표시되었습니다")으로 대신한다. 별도 선택 안내는 두지 않는다(중복).

### 6.6 같은 화면의 두 검색창

헤더 검색(상세 페이지로 이동)과 이 입력(타입 자동 선택)은 같은 쿼리를 쓰지만 목적이 다르다. 사용자가 혼동하지 않도록 레이블·placeholder로 구분하고, 필요하면 ux-designer가 시각적 위계를 정한다.

## 7. 구현 구조

지금 필요한 범위만 만든다. 파티 점검 등 보류된 기능을 위한 옵션(제외 목록, 선택 후 입력 비우기 등)은 두지 않는다. 다른 기능이 실제로 쓰기 시작할 때 그 범위로 승격한다(`structure.md` "승격은 실적으로 한다", 2026-10-20).

| 구조 | 근거 |
| --- | --- |
| 입력 컴포넌트는 props로만 동작하고 선택 결과를 콜백(`onSelect`)으로 내보낸다. Context는 컨테이너가 읽는다 | `structure.md` 계층 규칙(`components/`는 props 기반 UI) |
| 항목은 `{ number, name, index, formType, imagePath, types }`이고, 폼은 `number` + `formType` + `index`로 식별한다 | 폼 단위로 선택한다. 백엔드 `id`는 고정값이 아니라 쓰지 않는다(5.2) |
| 이름 입력 연결 컨테이너를 새로 둔다(`containers/typeEffectiveness/TypePokemonNameSearch.container.tsx`). Context를 읽고, 입력·키보드·선택을 처리하고, 자동완성 패널·선택 표시줄을 렌더한다. 검색(디바운스·쿼리·상태)은 같은 위치의 `hooks/usePokemonNameSearch.ts`로 분리한다 | 컴포넌트 파일에는 컴포넌트 하나만 두고, 그 컴포넌트만 쓰는 훅은 위치의 `hooks/`에 둔다(`structure.md`). 기존 `TypeCalculator`에 넣으면 칩·가이드·검색이 한 파일에 몰려 연결부를 따로 둔다 |
| 자동완성 패널·선택 표시줄은 `components/typeEffectiveness/`에 두고 Storybook story를 함께 쓴다 | UI라 `components/` 계층이고, 사용 도메인이 하나다. 새 컴포넌트는 story로 등록한다(ADR-0008) |

계산기 연결에 필요한 상태 변경은 두 가지다. **Context에 "타입 목록을 한 번에 지정하는 액션"**과 **"현재 칩이 이름으로 설정됐는지"를 구분하는 상태**가 필요하다(5.1의 칩 해제 규칙).

## 8. 폼 이름으로 시작하는 검색 (1단계에 포함)

처음에는 확장 단계로 두었으나, 백엔드가 `searchPokemonWithAllForms` 검색을 고도화해 2026-10-19 상용에 배포했다(1.61.4 핫픽스와 함께). 이 기능의 1단계에 그대로 포함된다.

- "알로라 라이츄", "메가리자몽", "히스이"처럼 폼 이름·지역명으로 시작하는 입력도 결과를 갖는다. 어순과 무관하다("알로라 라이츄"·"라이츄 알로라" 모두 "라이츄 알로라의 모습").
- 응답 형태는 같아 입력 컴포넌트에 별도 처리가 필요 없다.
- 도감 목록 검색(`getPokemonListPaginated`)은 바뀌지 않았다("알로라 라이츄"·"메가리자몽" 0건, 2026-10-20 운영 API 확인). 이 개선은 [ADR-0022](../../decisions/records/ADR-0022-list-search-include-forms.md) 별도 작업으로 남는다.

## 9. 측정 (GA4)

### 9.1 이벤트 정의

이벤트 이름·파라미터 이름·파라미터 값은 모두 소문자 스네이크 케이스로 쓰고, 전송은 [`coding.md` "분석 이벤트 전송"](../../conventions/guides/coding.md) 규칙을 따른다. **확정(2026-10-19, C2).**

| 이벤트 | 발생 시점 | 파라미터 | 쓰임 |
| --- | --- | --- | --- |
| `use_name_search` | 자동완성 목록에서 포켓몬을 **선택할 때마다** | `source`, `query`, `pokemon_number`, `form_type`, `is_first_search` | 이름 입력 사용률, 검색어 패턴, 어떤 포켓몬·폼을 찾는지, 재검색 여부 |
| `use_type_calc` | 계산 결과가 확정될 때(아래 정의) | `input_method`, `types` | **계산 실행 수**(주 성공 지표), 입력 방식별 비교 |

이벤트 이름에는 페이지를 넣지 않는다. gtag가 모든 이벤트에 `page_location`을 자동으로 붙이므로 페이지는 보고서에서 나눠 본다([GA4 자동 수집 이벤트](https://support.google.com/analytics/answer/9234069)).

#### 파라미터 값

| 파라미터 | 값 | 비고 |
| --- | --- | --- |
| `source` | `type_calc` | 입력 기능을 구분하는 값. 이벤트는 출시 시점부터 쌓이므로, 같은 페이지에 다른 입력 기능이 생겨도 이전 데이터와 같은 기준으로 나눠 볼 수 있게 처음부터 보낸다(URL로는 구분되지 않는다, 2026-10-20 유지 결정) |
| `query` | 선택 시점의 입력 문자열, **20자까지** 자름 | 자유 입력이라 길이를 제한한다(9.2) |
| `pokemon_number` | 도감 번호 | |
| `form_type` | `default` / `mega` / `form` / `region` | 백엔드 `formType`(`BASE` / `MEGA` / `NORMAL_FORM` / `REGION_FORM`)을 바꿔 보낸다. 상세 능력치 탭과 같은 값 집합을 쓴다 |
| `is_first_search` | `true` / `false` (문자열) | 한 페이지 로드에서 첫 선택이면 `true`. 한 번만 찾고 나갔는지, 바꿔 가며 여러 번 찾았는지 본다 |
| `input_method` | `chip` / `name` | |
| `types` | 영문 소문자 타입을 알파벳순으로 정렬해 쉼표로 연결(예: `fire,flying`) | 선택 순서와 무관하게 같은 조합이 한 값으로 모인다. 타입 수는 이 값에서 구한다 |

**"계산 실행"의 정의 (2026-10-15 확정, 2026-10-19 칩 집계 변경).**

- **이름 선택**: 선택 1회 = 1회, 즉시 보낸다. 선택 규칙(5.1)상 타입이 한 번에 정해져 중간 상태가 없다. 이름 선택으로 칩이 바뀐 것은 칩 집계에 넣지 않는다.
- **칩 선택**: 칩 변경이 멈추고 **약 1.5초 동안 선택이 그대로일 때** 그 조합으로 1회 보낸다. 노말 → 고스트를 이어서 누르면 `normal,ghost` 1회만 남는다. 선택이 비어 있으면 보내지 않고, **같은 페이지 로드 안에서 같은 타입 조합은 1회만** 센다.
  - 기존 정의(결과가 생기는 변경마다 1회)는 계산기가 타입 1개만 골라도 결과를 보여 주므로, 이중 타입을 찾는 사용자를 2회로 셌다. 이름 선택(항상 1회)과 비교가 어긋나 바꿨다.
  - 결과만 보고 1.5초 안에 페이지를 떠나면 누락된다. 비교 기준을 맞추기 위해 이 누락을 감수한다.

#### 검토 후 채택하지 않은 이벤트 (2026-10-19)

| 이벤트(가칭) | 사유 |
| --- | --- |
| `type_name_search_use`(입력 시작 시 1회) | `use_name_search`에 통합했다. 사용률은 이벤트가 있는 세션 수로 구하고, 첫 검색 여부는 `is_first_search`로 본다 |
| `type_name_search_no_result`(0건 검색어) | 폼 이름·어순까지 서버가 처리해(8) 0건 검색어로 확인하려던 폼 이름 검색 수요는 이미 해소됐다. 우선 `use_name_search`의 `query` 패턴을 보고, 필요해지면 추가한다. 선택하지 못한 검색은 남지 않는다는 한계가 있다 |
| 파라미터 `rank`·`query_length`·`type_count` | 예정 기능을 고려하면 자동완성 순위 분석이 필요 없다. 타입 수는 폼 정보와 `types`에서 알 수 있다 |

### 9.2 구현 요구

- 현재 GA4 이벤트 전송 헬퍼가 코드에 없다(`layout.tsx`의 기본 설정뿐). 전송은 `coding.md` 규칙(`modules/`의 공통 유틸 + 이벤트 타입 정의)을 따른다. 1.62.0의 첫 이벤트 기능이 유틸을 만들고 다른 기능은 이를 쓴다.
- 커스텀 파라미터를 보고서에서 쓰려면 GA4에서 **맞춤 측정기준으로 등록**해야 한다([GA4 맞춤 측정기준](https://support.google.com/analytics/answer/14240153)). 등록은 사용자가 콘솔에서 한다(C6).
- 개인 식별 정보를 보내지 않는다([GA4 PII 정책](https://support.google.com/analytics/answer/6366371)). 입력 원문은 `use_name_search`의 `query`에서만, 20자로 잘라 보낸다.
- 이름 입력과 선택은 URL을 바꾸지 않으므로 페이지뷰가 늘지 않는다(4.1). 이벤트로만 측정한다.

기준값은 트래픽 스냅샷(GA4 28일)이다. 새 이벤트는 측정 전이므로 **출시 4주 후를 베이스라인**으로 삼는다.

## 11. 결정 사항 (2026-10-15 정리)

1. **데이터 로딩**: `searchPokemonWithAllForms` + 백엔드 `types` 추가(5.2).
