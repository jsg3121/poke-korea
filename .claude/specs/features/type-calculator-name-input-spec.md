> **범위**: `/type-effectiveness` 메인 페이지의 계산기(`TypeCalculator`)에 "포켓몬 이름으로 찾기" 입력 추가. 첫 배포는 기본 종만 지원

## 1. 배경 (Why)

### 1.1 지금의 문제

상대 포켓몬을 상대하려는 사용자는 "리자몽이 약한 타입"을 알고 싶다. 그런데 계산기는 **타입 칩 최대 2개를 직접 고르게 한다.** 상대의 타입 조합을 이미 알고 있어야 쓸 수 있다.

- 사용자가 아는 것은 포켓몬 이름이고, 타입 조합은 모르거나 헷갈린다. 이름 → 타입 변환을 사용자가 머릿속으로 해야 한다.
- 조합이 틀리면 결과도 틀린다. 틀렸다는 사실도 알 수 없다.
- 이 변환 단계를 서비스가 대신하면 입력이 "칩 2번 탭"에서 "이름 몇 글자 + 1번 탭"으로 바뀐다. 타입을 아는 사용자도 이름이 더 빠를 수 있다.

### 1.2 이 기능을 지금 하는 이유 (근거)

| 근거 | 수치 (GA4 28일 / Search Console 2026-09-13~10-11) |
| --- | --- |
| 상성은 가장 확실한 검색 자산이다 | 타입 상성 랜딩 세션 12,837(전체 2위, 14.5%), 구글 클릭 6,143 |
| 도구형 질의에서 이미 이기고 있다 | "포켓몬 상성 계산기" 1.2위, CTR 56.9% / "포켓몬 상성" 2.9위, CTR 11.9% |
| 랜딩 참여가 낮다 | 참여율 0.48(홈 0.86, 목록 0.70), 세션당 PV 3.6(홈 15.2) |
| 재방문 비중이 크다 | 타입 상성 PV 25,493 중 재방문 16,835(71.4%) |
| 모바일이 다수다 | 활성 사용자 mobile 28,872 / desktop 16,484 / tablet 1,542 |

**해석 주의.** 참여율 0.48이 "불만 이탈"이라는 근거는 없다. 재방문 71.4%는 답만 보고 닫는 "빠른 조회" 패턴일 수 있다(전략 문서의 가설). 그래서 이 기능은 체류를 늘리는 것이 아니라 **조회를 더 빠르고 정확하게 만드는 것**을 목표로 하고, 성공 지표도 참여율이 아니라 "계산 실행 수"와 "이름 입력 사용"으로 본다. 광고가 PV 모델이므로 PV 하락 여부는 가드레일로 함께 본다.

### 1.3 왜 별도 페이지가 아닌가

- 상성 계산기 검색 유입(위 표)이 이미 이 URL에 모인다. 입력을 같은 페이지에 두면 새 URL, 새 메타데이터, 새 색인 부담이 없다.
- 결과 영역(약점·저항·무효 목록)은 그대로 재사용한다. 입력 방식만 늘어난다.
- 후속 "파티 점검" 모드도 같은 페이지에 들어갈 예정이라, 입력 컴포넌트를 먼저 만들어 두는 것이 순서에 맞다.

### 1.4 레퍼런스

- 이름 선택형 계산 도구: [Pokemon Showdown Damage Calculator](https://calc.pokemonshowdown.com/) — 포켓몬을 이름으로 골라 계산한다(방식 참고용).
- 타입 선택형 상성표: [Pokemon Database — Dual type chart](https://pokemondb.net/type/dual) — 타입 조합을 직접 고르는 방식. 현재 포케코리아 계산기와 같은 계열이다.
- 접근성 패턴: [WAI-ARIA APG — Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [List autocomplete 예시](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-autocomplete-list/)

## 2. 목표와 비목표

### 2.1 목표

1. 이름 입력 → 자동완성 목록 → 선택하면, 그 포켓몬의 타입이 칩에 자동 선택되고 **아래 결과가 지금과 똑같이** 나온다.
2. 첫 배포는 **기본 종만** 지원한다. 리전폼·메가는 지원 시점을 명시하고, 지원하지 않는다는 사실을 사용자에게 숨기지 않는다.
3. 입력 컴포넌트는 계산기 상태(Context)에 의존하지 않게 만들어 **파티 점검에서 그대로 재사용**한다.
4. **URL을 바꾸지 않는다.** (제약 4.1)
5. GA4 이벤트로 이름 입력 사용, 포켓몬 선택, 계산 실행을 측정한다.

### 2.2 비목표 (이번 범위 밖)

| 항목 | 이유 |
| --- | --- |
| 결과 영역(약점·저항 목록)의 디자인·구성 변경 | "지금과 똑같이" 나오는 것이 요구사항이다. 변경하면 효과 귀속이 섞인다 |
| 특성·지닌 도구 효과 반영(예: 부유 → 땅 무효) | 현재 계산기는 타입만 본다. 도입하면 별도 데이터·UI가 필요하다. 대신 안내 문구로 기대를 맞춘다(6.5) |
| 리전폼·메가진화 이름 지원 | 백엔드 폼 타입 데이터 필요(ADR-0022). 확장 단계(8) |
| URL·공유 링크에 선택 상태 저장 | URL 변경 금지 제약. 상태는 메모리에만 둔다 |

| 헤더 검색 변경 | 별개 기능. 이 페이지에는 헤더 검색과 새 입력이 함께 보이므로 혼동은 UX에서 확인(6.6) |
| 최근 본 포켓몬 | 전략 4단계의 별도 기능 |

## 4. 제약

### 4.1 URL을 바꾸지 않는다

이 사이트는 `router.replace`로 URL이 바뀌면 GA4 향상된 측정의 history 기반 page_view가 발생해 지표가 부풀려지는 문제가 확인됐다(도감 목록 `/list` 84,727 PV 중 필터 변경분이 대부분 — 트래픽 스냅샷 정정). 이름 입력과 선택 상태는 컴포넌트 메모리에만 둔다. 참고: [GA4 향상된 측정 — 브라우저 기록 기반 페이지 변경](https://support.google.com/analytics/answer/9216061).

> **Why:** 이 기능의 성공 여부를 GA4로 판정해야 한다. 측정 자체가 오염되면 판정이 불가능하다.

### 4.2 메타데이터 2주 동결

효과 귀속을 위해 `/type-effectiveness` 메인의 title, description, canonical, JSON-LD, H1, PageHeader description은 **배포 후 2주(14일) 동안 변경하지 않는다.** 별도 SEO 트랙(전략 2단계)은 이 기간 이후에 착수한다. 계산기 섹션 안의 안내 문구 수정은 허용하되, 메타데이터와 H1은 건드리지 않는다.

### 4.3 백엔드 변경 없음

현재 스키마로 가능한 범위만 한다. 필요한 데이터는 `getPokemonList`의 이름 필터와 필드 선택으로 받는다(5.2).

### 4.4 모바일 우선, 브레이크포인트 2종

- [ADR-0020](../../decisions/records/ADR-0020-breakpoint-two-only.md): `mobile`·`desktop` 2종만 쓴다. 새 브레이크포인트를 만들지 않고, 레이아웃은 한 값으로 전 구간을 커버하게 만든다.
- [ADR-0011](../../decisions/records/ADR-0011-tab-touch-target-24px.md): `SearchInput`은 디바이스 무관 44px 유지. 탭·칩만 슬림 예외다. 따라서 이름 입력창은 44px이고, **자동완성 목록의 각 행은 칩이 아니므로 44px(`min-h-touch`)을 유지**한다. 선택된 포켓몬을 지우는 아이콘 버튼은 `CloseIconButton`(모바일 44px, 데스크톱 36px) 규칙을 따른다. 근거: [WCAG 2.2 — 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

## 5. 기능 정의

### 5.1 사용자 흐름

1. 사용자가 계산기 섹션에서 "포켓몬 이름으로 찾기" 입력창을 본다(타입 칩 위).
2. 입력창에 포커스하거나 글자를 입력한다. 입력할 때마다 즉시 자동완성 목록이 갱신된다.
3. 목록에서 포켓몬을 탭하면 입력창에 이름이 채워지고 목록이 닫힌다. **타입 칩 1~2개가 자동 선택**되고 결과가 갱신된다.
4. 이후 선택은 자유롭다.
   - 칩을 직접 눌러 바꾸면 "이름으로 선택된 포켓몬" 표시는 해제된다(타입이 더 이상 그 포켓몬과 같지 않기 때문).
   - "선택 초기화"는 칩과 이름 입력을 모두 비운다.
   - 다른 포켓몬을 다시 고르면 **선택 타입을 합치지 않고 통째로 교체**한다. 결과는 "상대 한 마리"의 약점이기 때문이다.

### 5.2 데이터 로딩

**결정(2026-10-14, 사용자 결정): 입력할 때마다 디바운스를 걸어 이름 필터 쿼리를 요청한다.** ADR은 작성하지 않는다. 기존 검색 입력과 같은 패턴이고 범위가 이 입력 하나에 갇히기 때문이다.

- 쿼리: `getPokemonList(filter: { name })`를 쓰고 필드는 `number`, `name`, `types`(필요 시 `isRegionForm`, `isMegaEvolution`)만 고른 전용 쿼리를 프론트에 정의한다. 스키마 변경은 없다(`npm run codegen`은 로컬 GraphQL 서버 필요).
  - 헤더 검색의 `SearchPokemonWithAllForms`는 응답에 타입이 없어 쓰지 않는다.
- 디바운스: 기존 검색 입력과 같은 `src/hooks/useDebounce.ts`의 훅과 기본 간격(500ms)을 쓴다. 현재 헤더 포켓몬 검색(`useSearchPokemon`), 모바일 도감 검색(`ListSearch`), 기술·특성 검색이 모두 이 훅을 쓴다.
- 캐시: 같은 검색어 재입력은 Apollo 캐시를 쓴다. 헤더 검색(`useSearchPokemon`, `cache-and-network`)의 방식을 따른다.

**운영 API 실측(2026-10-14)**

| 검색어 | 결과 | 응답 시간 | 크기 |
| --- | --- | --- | --- |
| 리자 | 리자드, 리자몽(불꽃·비행), 일레도리자드, 블리자포스 | 0.06초 | 266B |
| 피카 | 피카츄 | 0.04초 | 84B |

**검토 후 채택하지 않은 방식**

| 방식 | 불채택 사유 |
| --- | --- |
| 페이지에 전체 목록 포함 | 이름 입력을 쓰지 않는 방문자(상성 PV의 71.4%가 재방문, 칩만 쓰는 층 포함)에게도 105KB를 보낸다 |
| 입력창 첫 포커스에 전체 목록 1회 조회 | 동작은 하지만 기존 검색 패턴과 다른 방식이 하나 더 생긴다. 리전폼·메가 확장 때 전체 목록 쿼리를 따로 바꿔야 한다 |
| 목록을 저장소에 정적 파일로 보관 | 신규 포켓몬·폼 추가 시 소스와 DB가 어긋난다 |

**이 방식의 이점**: [ADR-0022](../../decisions/records/ADR-0022-list-search-include-forms.md)로 백엔드 이름 검색이 리전폼·메가까지 찾게 되면, 같은 쿼리 결과에 폼이 따라오므로 이 입력은 응답 처리만 바꾸면 된다(8절).

### 5.3 이름 매칭 규칙

매칭(포함 검색)은 서버의 이름 필터(`contains`)가 한다. 화면은 디바운스가 끝난 검색어로 받은 결과를 정렬·표시한다.

- 정규화: 앞뒤 공백을 제거한 뒤 요청한다. 빈 문자열이면 요청하지 않고 목록을 닫는다. 특수문자가 들어가는 이름(예: 니드런♀, 타입:널 — 실제 데이터 표기는 구현 시 확인)이 입력 가능해야 한다.
- 정렬: 서버는 도감 번호순으로 준다. 화면에서 "이름이 입력으로 시작" → "이름에 입력 포함" → 도감 번호순으로 다시 정렬한다. 결과가 작아 부담이 없다.
- 한 글자 입력: 쿼리에 개수 제한 인자가 없어 "이"처럼 한 글자는 결과가 많을 수 있다. 응답은 받되 화면 노출은 상한(8건 안팎)으로 자르고 목록 영역은 스크롤한다(수치는 UX에서 확정). 최소 입력 글자 수를 둘지는 UX에서 정한다.
- 한글 IME: 조합 중에도 `onChange`가 발생하지만, 디바운스(500ms)가 끝난 값으로만 요청하므로 조합 중간 값 요청은 대부분 걸러진다. 조합 중 Enter로 선택이 일어나지 않게 한다.
- 응답 순서: 이전 검색어의 늦은 응답이 최신 결과를 덮어쓰지 않게 한다(헤더 검색과 같은 처리 방식을 따른다).
- 초성 검색("ㄹㅈㅁ")은 서버 `contains` 검색으로 불가능하다. 하려면 백엔드 검색 확장이 필요하므로 이번 범위에서 제외한다(11).

### 5.4 선택 후 표시

- 선택된 포켓몬을 입력창 아래 한 줄로 표시한다(예: 도감 번호·이름·타입 태그 + 지우기 버튼). 이 표시는 "지금 결과가 어떤 포켓몬 기준인지"를 알려주는 역할이다.
- 결과 영역의 제목은 바꾸지 않는다(현재 `selectTypeListKo` 기준). 포켓몬 이름을 결과 제목에 반영하는 것은 후속 개선 후보로만 둔다.

### 5.5 기본 폼 기준 안내

`GetPokemonList`는 기본 폼 타입만 준다. 리전폼·메가에서 타입이 달라지는 종이 있으므로:

- 목록 항목에 `isRegionForm` 또는 `isMegaEvolution`이 참인 종은 "기본 폼 기준" 배지를 붙인다. (두 플래그 모두 "해당 폼이 있는 종"이라는 뜻이다. 2026-10-14 운영 API에서 리자몽·라이츄(Z-A DLC 메가라이츄)가 `isMegaEvolution: true`로 확인됐다.)
- 입력에 "메가", "알로라", "가라르", "히스이", "팔데아"가 들어 있어 결과가 0건이면 안내한다: "리전폼·메가진화 이름은 아직 지원하지 않아요. 기본 포켓몬 이름을 입력하거나 타입을 직접 골라주세요."
- **기본 종의 타입을 폼의 타입으로 대신 보여주지 않는다.** 예: 메가리자몽X(불꽃·드래곤)를 리자몽(불꽃·비행)으로 계산하면 틀린 정보가 정답처럼 나간다. 없다고 알리는 편이 낫다.

### 5.6 특성·도구 효과 안내

이름을 입력하면 사용자는 그 포켓몬의 **특성(예: 부유)** 까지 반영되리라 기대하기 쉽다. 현재 계산은 타입만 본다. 입력 근처 또는 결과 위에 한 줄 안내를 둔다: "특성·지닌 도구 효과는 반영하지 않고 타입만 계산해요."

## 6. UX 요구사항

> 상세 설계는 `ux-designer`에 위임한다(파이프라인: product-planner → ux-designer). 아래는 기획 단계의 요구사항이다.

### 6.1 배치

- `TypeCalculator` 섹션 안, 헤더 설명 문구와 "선택 초기화" 버튼 사이 또는 칩 그룹 바로 위에 입력창을 둔다.
- 입력창 레이블은 화면에 보이는 레이블 "포켓몬 이름으로 찾기"(`visuallyHiddenLabel={false}` 형태)를 쓴다. placeholder 예시는 흔한 이름 1개.
- 섹션 헤더 아래 설명 문구는 "이름을 입력하거나 타입을 직접 선택" 취지로 조정할 수 있다. 단 H1·PageHeader 설명은 건드리지 않는다(4.2).

### 6.2 자동완성 목록

- **절대 위치 오버레이**로 띄운다. 문서 흐름에 넣으면 아래의 광고 슬롯(`TypeEffectivenessTopBanner`)과 칩 영역이 밀려 레이아웃 이동(CLS)과 광고 위치 변화가 생긴다.
- 헤더 검색 결과 목록이 모바일에서 `z-[600]`를 쓰고 있다. 같은 화면에 두 목록이 겹치지 않도록 z-index와 열림 상태 충돌을 확인한다(헤더 검색을 열면 이쪽을 닫는 등).
- 행 높이 44px 이상(4.4). 행 간격은 오탭이 없게 한다.
- 로딩(검색 중), 결과 없음, 조회 실패 상태를 각각 정의한다. 조회 실패 시에도 **타입 칩으로 계속 쓸 수 있어야 한다**(기능 저하가 계산기 전체 중단이 되지 않는다).

### 6.3 모바일

- 입력창 폭은 전체 폭. 자동 포커스는 하지 않는다. 키보드가 올라오면 칩과 광고를 가리는데, 재방문 사용자 중 칩만 쓰는 층에게 불편을 주지 않기 위해서다.
- `SearchInput`의 글자 크기가 `text-sm`(14px)이다. iOS Safari는 16px 미만 입력에 포커스하면 화면을 확대하는 경향이 있다. **실기기에서 확인**하고, 확대된다면 이 입력에 한해 16px 이상으로 한다(확인 지점 C5). 이는 공식 규격이 아니라 알려진 브라우저 동작이므로 단정하지 않고 확인 항목으로 둔다.
- 입력창과 선택 표시가 한 화면(스크롤 없이)에서 결과의 첫 부분과 이어지도록 한다.

### 6.4 데스크톱

- 입력창은 전체 폭이 아니라 적정 최대 폭을 둔다. 조정은 `desktop:` 한 값으로만 한다(ADR-0020).

### 6.5 접근성

- ARIA 콤보박스 패턴(입력 `role="combobox"`, 목록 `role="listbox"`, 항목 `role="option"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`)과 키보드(위/아래 이동, Enter 선택, Esc 닫기)를 따른다. 근거: [WAI-ARIA APG — Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/).
- 현재 `SearchInput`은 이 속성들과 ref를 받지 못한다. **DS 원자 확장(또는 래퍼)이 필요**하다. 방식은 구현 착수 시 `structure.md`·ADR-0010(원자 우선)에 따라 확정한다.
- 선택 결과를 스크린리더에 알린다(예: "리자몽 선택, 불꽃·비행 타입이 선택되었습니다" — `aria-live`).

### 6.6 같은 화면의 두 검색창

헤더 검색(상세 페이지로 이동)과 이 입력(타입 자동 선택)은 목적이 다르다. 사용자가 혼동하지 않도록 레이블·placeholder로 구분하고, 필요하면 ux-designer가 시각적 위계를 정한다.

## 7. 재사용 설계 (파티 타입 커버리지 대비)

후속 "내 파티 점검"은 같은 입력을 최대 6회 쓴다. 이 기능을 만들 때 아래를 **요구사항**으로 둔다.

| 요구 | 이유 |
| --- | --- |
| 입력 컴포넌트는 `TypeEffectivenessContext`를 직접 읽지 않는다. 선택 결과를 콜백(`onSelect`)으로만 내보낸다 | 파티 모드는 다른 상태(파티 구성원 목록)를 쓴다. 계산기 전용 Context에 묶이면 재사용이 불가능하다 |
| 항목 데이터 형태는 `{ number, name, types, ... }`에 **폼을 식별할 수 있는 확장 자리**를 둔다 | ADR-0022 이후 리전폼·메가를 같은 목록에 넣어도 컴포넌트가 바뀌지 않게 한다 |
| 제외·비활성 목록(이미 고른 포켓몬) 지정 가능 | 파티에 같은 포켓몬 중복 방지 |
| 선택 후 입력창을 비울지 여부 옵션 | 계산기는 이름을 남기고, 파티는 비우고 다음 입력을 받는다 |
| 이벤트용 `source` 값을 주입받는다 | 같은 컴포넌트의 이벤트를 계산기/파티로 구분해 집계 |
| 데이터 훅(검색 요청·디바운스·캐시)을 컴포넌트와 분리 | 파티 모드에서 같은 훅과 Apollo 캐시를 그대로 쓴다 |
| 계산기 쪽 동작은 별도 연결 코드에 둔다 | 컴포넌트 재사용 시 계산기 규칙(타입 교체, 칩 수동 변경 시 해제)이 따라오지 않게 한다 |

계산기 연결에 필요한 상태 변경은 하나다. **Context에 "타입 목록을 한 번에 지정하는 액션"이 없으므로 추가가 필요**하다(현재는 토글·초기화뿐). 배치(어느 계층에 둘지)는 `.claude/conventions/guides/structure.md`에 따라 구현 단계에서 확정한다.

## 8. 확장 단계: 리전폼·메가

### 8.1 선행 조건

[ADR-0022](../../decisions/records/ADR-0022-list-search-include-forms.md)(상태 제안)가 승인되고 백엔드가 **폼 단위 타입을 포함한 응답**을 내려주는 것. 현재는 폼에 타입 정보가 있는 쿼리가 없다.

### 8.2 확장 범위

- 목록 항목이 폼 단위가 된다(예: "라이츄 알로라의 모습"). 표시 이름은 "알로라 라이츄" 어순으로 입력해도 찾아지도록 **ADR-0022의 토큰 매칭 규칙**을 따른다(공백으로 나눈 모든 토큰이 이름+지역명에 포함).
- 5.5의 "기본 폼 기준" 배지와 0건 안내는 폼 지원과 함께 제거 또는 축소한다.
- 7의 확장 자리를 사용하므로 입력 컴포넌트는 바뀌지 않는 것이 목표다.

### 8.3 이 단계를 앞당기는 신호

첫 배포의 "결과 없음" 이벤트(9)에서 메가·지역명을 포함한 입력 비율이 높으면 확장 우선순위를 올린다. (참고: 메가 의도 Search Console 노출 48,480, 리전폼 의도 4,434 — ADR-0022 맥락.)

## 9. 측정 (GA4)

### 9.1 이벤트 정의 (요구사항)

최종 이름·파라미터는 전략 0단계의 "GA4 이벤트 설계"에서 확정한다. 아래는 이 기능이 반드시 포함해야 할 **의미 요구**다. 이벤트 이름은 소문자 스네이크 케이스 40자 이내, 파라미터 규칙은 [GA4 이벤트 수집 가이드](https://developers.google.com/analytics/devguides/collection/ga4/events?client_type=gtag)를 따른다.

| 이벤트(가칭) | 발생 시점 | 핵심 파라미터(가칭) | 쓰임 |
| --- | --- | --- | --- |
| `type_name_search_use` | 한 페이지 로드에서 **처음으로** 이름 입력이 시작될 때 1회 | `source`(계산기/파티) | 이름 입력 사용률(사용 세션 / 상성 랜딩 세션) |
| `type_name_search_select` | 자동완성 목록에서 포켓몬을 선택했을 때 | `source`, `pokemon_number`, `type_count`, `query_length`, `rank`(목록 내 위치) | 선택 성공 여부, 어떤 포켓몬이 많이 찾히는지, 자동완성 품질(랭크) |
| `type_name_search_no_result` | 결과 0건 상태가 일정 시간(예: 입력 멈춤 후 약 1초) 유지될 때 | `source`, `query`(길이 제한) | 폼 지원 수요 확인(8.3), 이름 데이터 점검 |
| `type_calc_run` | 결과가 비어 있지 않은 선택 상태가 **새로** 만들어질 때 | `input_method`(chip / name), `type_count`, `types` | **계산 실행 수**(주 성공 지표), 입력 방식별 비교 |

**"계산 실행"의 정의(제안, 확정 필요).** 결과 영역이 비어 있지 않게 되는 선택 변경을 1회로 센다. 단 칩을 연속으로 눌러 만든 중간 상태(1개 선택 후 2개 선택)가 부풀리는 것을 막기 위해 **같은 페이지 로드 안에서 같은 타입 조합은 1회만** 센다. 이 정의로 칩 사용자와 이름 사용자를 같은 척도로 비교할 수 있다.

### 9.2 구현 요구

- 현재 GA4 이벤트 전송 헬퍼가 코드에 없다(`layout.tsx`의 기본 설정뿐). 얇은 전송 래퍼가 필요하다. 위치·형태는 구현 단계에서 확정한다.
- 커스텀 파라미터를 보고서에서 쓰려면 GA4에서 **맞춤 측정기준으로 등록**해야 한다([GA4 맞춤 측정기준](https://support.google.com/analytics/answer/14240153)). 등록은 사용자가 콘솔에서 해야 하므로 확인 지점이다(C6).
- 개인 식별 정보를 보내지 않는다([GA4 PII 정책](https://support.google.com/analytics/answer/6366371)). 입력 원문은 `no_result`에서만, 길이를 제한해 보낸다. 포켓몬 이름 입력은 PII가 아니지만 자유 입력 칸이라 사용자가 다른 문자열을 넣을 수 있다.
- 이름 입력과 선택은 URL을 바꾸지 않으므로 페이지뷰가 늘지 않는다(4.1). 이벤트로만 측정한다.

### 9.3 성공 지표와 가드레일

기준값은 트래픽 스냅샷(GA4 28일)이다. 새 이벤트는 측정 전이므로 **출시 4주 후를 베이스라인**으로 삼는다(전략 KPI와 동일).

| 계산 실행 수 / 상성 세션 | 측정 전 | 배포 전후 비교(칩만 쓰던 시기 대비) | 주 성공 지표. 입력 방식별로 분리해 본다 |

## 11. 미결 사항 (사용자 결정 필요)

1. ~~데이터 로딩 방식~~ → **확정(2026-10-14)**: 입력마다 디바운스(500ms) + 이름 필터 쿼리. ADR 없음(5.2).
2. ~~초성 검색~~ → **이번 범위 제외**: 서버 `contains` 검색으로 불가능해 백엔드 확장이 필요하다. 필요하면 ADR-0022 백엔드 작업과 함께 검토한다.
3. **"계산 실행" 이벤트 정의**(같은 조합 1회 제한)가 맞는지.
4. **파티 점검 착수 게이트 수치**: 이름 입력 사용 비율 몇 %를 기준으로 할지. 현재 근거가 되는 사전 데이터가 없어 기획서가 임의 수치를 정하지 않았다. 4주 베이스라인을 본 뒤 정해도 되는지.
5. **섹션 문구 변경 허용 범위**: 계산기 섹션의 설명 문구를 바꾸는 것까지 허용하는지(H1·메타는 동결).
6. **"기본 폼 기준" 배지** 노출 방식(항상 vs 해당 종만). 기획은 해당 종만 권고.
