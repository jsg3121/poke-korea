> **작성일**: 2026-10-14
> **버전**: 1.62.0
> **상태**: 승인됨
> **범위**: `/type-effectiveness` 메인 페이지의 계산기(`TypeCalculator`)에 "포켓몬 이름으로 찾기" 입력 추가. 기본 종·메가진화·리전폼·폼체인지를 모두 지원한다

## 1. 배경 (Why)

### 1.1 지금의 문제

상대 포켓몬을 상대하려는 사용자는 "리자몽이 약한 타입"을 알고 싶다. 그런데 계산기는 **타입 칩 최대 2개를 직접 고르게 한다.** 상대의 타입 조합을 이미 알고 있어야 쓸 수 있다.

- 사용자가 아는 것은 포켓몬 이름이고, 타입 조합은 모르거나 헷갈린다. 리전폼·메가처럼 기본 종과 타입이 다른 폼은 더 헷갈린다.
- 조합이 틀리면 결과도 틀린다. 틀렸다는 사실도 알 수 없다.
- 이 변환 단계를 서비스가 대신하면 입력이 "칩 2번 탭"에서 "이름 몇 글자 + 1번 탭"으로 바뀐다.

### 1.2 이 기능을 지금 하는 이유 (근거)

| 근거 | 수치 (GA4 28일 / Search Console 2026-09-13~10-11) |
| --- | --- |
| 상성은 가장 확실한 검색 자산이다 | 타입 상성 랜딩 세션 12,837(전체 2위, 14.5%), 구글 클릭 6,143 |
| 도구형 질의에서 이미 이기고 있다 | "포켓몬 상성 계산기" 1.2위, CTR 56.9% / "포켓몬 상성" 2.9위, CTR 11.9% |
| 랜딩 참여가 낮다 | 참여율 0.48(홈 0.86, 목록 0.70), 세션당 PV 3.6(홈 15.2) |
| 재방문 비중이 크다 | 타입 상성 PV 25,493 중 재방문 16,835(71.4%) |
| 모바일이 다수다 | 활성 사용자 mobile 28,872 / desktop 16,484 / tablet 1,542 |

**해석 주의.** 참여율 0.48이 "불만 이탈"이라는 근거는 없다. 재방문 71.4%는 답만 보고 닫는 "빠른 조회" 패턴일 수 있다(전략 문서의 가설). 그래서 이 기능은 체류를 늘리는 것이 아니라 **조회를 더 빠르고 정확하게 만드는 것**을 목표로 하고, 성공 지표도 참여율이 아니라 "계산 실행 수"와 "이름 입력 사용"으로 본다. 광고가 PV 모델이므로 PV 하락 여부는 가드레일로 함께 본다.

### 1.3 왜 별도 페이지가 아닌가

- 상성 계산기 검색 유입(위 표)이 이미 이 URL에 모인다. 입력을 같은 페이지에 두면 새 URL, 새 메타데이터, 새 색인 부담이 없다.
- 결과 영역(약점·저항·무효 목록)은 그대로 재사용한다. 입력 방식만 늘어난다.
- 후속 "파티 점검" 모드도 같은 페이지에 들어갈 수 있어, 입력 컴포넌트를 먼저 만들어 두는 것이 순서에 맞다.

### 1.4 레퍼런스

- 이름 선택형 계산 도구: [Pokemon Showdown Damage Calculator](https://calc.pokemonshowdown.com/) — 포켓몬을 이름으로 골라 계산한다(방식 참고용).
- 타입 선택형 상성표: [Pokemon Database — Dual type chart](https://pokemondb.net/type/dual) — 타입 조합을 직접 고르는 방식. 현재 포케코리아 계산기와 같은 계열이다.
- 접근성 패턴: [WAI-ARIA APG — Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [List autocomplete 예시](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-autocomplete-list/)

## 2. 목표와 비목표

### 2.1 목표

1. 이름 입력 → 자동완성 목록 → 선택하면, 그 포켓몬(폼)의 타입이 칩에 자동 선택되고 **아래 결과가 지금과 똑같이** 나온다.
2. 기본 종뿐 아니라 **메가진화·리전폼·폼체인지도 각 폼의 실제 타입으로** 계산한다.
3. 입력 컴포넌트는 계산기 상태(Context)에 의존하지 않게 만들어 **파티 점검에서 그대로 재사용**할 수 있게 한다.
4. **URL을 바꾸지 않는다.** (제약 4.1)
5. GA4 이벤트로 이름 입력 사용, 포켓몬 선택, 계산 실행을 측정한다.

### 2.2 비목표 (이번 범위 밖)

| 항목 | 이유 |
| --- | --- |
| 결과 영역(약점·저항 목록)의 디자인·구성 변경 | "지금과 똑같이" 나오는 것이 요구사항이다. 변경하면 효과 귀속이 섞인다 |
| 특성·지닌 도구 효과 반영(예: 부유 → 땅 무효) | 현재 계산기는 타입만 본다. 도입하면 별도 데이터·UI가 필요하다. 대신 안내 문구로 기대를 맞춘다(5.6) |
| 폼 이름·지역명으로 시작하는 검색("알로라 라이츄", "메가리자몽", "히스이") | 백엔드 검색이 기본 종 이름으로만 매칭한다. ADR-0022 이후(8). 기본 종 이름("라이츄")으로 검색하면 폼이 목록에 함께 나오므로 폼 자체는 지원된다 |
| 초성 검색("ㄹㅈㅁ") | 서버 `contains` 검색으로 불가능. 백엔드 검색 확장이 필요하다 |
| URL·공유 링크에 선택 상태 저장 | URL 변경 금지 제약. 상태는 메모리에만 둔다 |
| `/type-effectiveness` 메타데이터·H1·PageHeader 설명 변경 | 배포 후 2주 동결(4.2) |
| 헤더 검색 UI 변경 | 별개 기능. 같은 쿼리를 쓰지만 헤더 검색의 화면은 바꾸지 않는다 |
| 파티 타입 커버리지 | 보류. 착수 시점은 별도로 정한다 |
| 최근 본 포켓몬 | 전략 4단계의 별도 기능 |

## 4. 제약

### 4.1 URL을 바꾸지 않는다

이 사이트는 `router.replace`로 URL이 바뀌면 GA4 향상된 측정의 history 기반 page_view가 발생해 지표가 부풀려지는 문제가 확인됐다(도감 목록 `/list` 84,727 PV 중 필터 변경분이 대부분 — 트래픽 스냅샷 정정). 이름 입력과 선택 상태는 컴포넌트 메모리에만 둔다. 참고: [GA4 향상된 측정 — 브라우저 기록 기반 페이지 변경](https://support.google.com/analytics/answer/9216061).

> **Why:** 이 기능의 성공 여부를 GA4로 판정해야 한다. 측정 자체가 오염되면 판정이 불가능하다.

### 4.2 메타데이터 2주 동결

효과 귀속을 위해 `/type-effectiveness` 메인의 title, description, canonical, JSON-LD, H1, PageHeader description은 **배포 후 2주(14일) 동안 변경하지 않는다.** 별도 SEO 트랙(전략 2단계)은 이 기간 이후에 착수한다. 계산기 섹션 안의 가이드 문구는 상황에 맞게 바꿀 수 있다(6.1).

### 4.3 백엔드 선행 변경 1건

`searchPokemonWithAllForms` 응답에 `types`를 추가하는 것 외에는 백엔드를 바꾸지 않는다(5.2).

### 4.4 모바일 우선, 브레이크포인트 2종

- [ADR-0020](../../decisions/records/ADR-0020-breakpoint-two-only.md): `mobile`·`desktop` 2종만 쓴다. 새 브레이크포인트를 만들지 않고, 레이아웃은 한 값으로 전 구간을 커버하게 만든다.
- [ADR-0011](../../decisions/records/ADR-0011-tab-touch-target-24px.md): `SearchInput`은 디바이스 무관 44px 유지. 탭·칩만 슬림 예외다. 따라서 이름 입력창은 44px이고, **자동완성 목록의 각 행은 칩이 아니므로 44px(`min-h-touch`)을 유지**한다. 선택된 포켓몬을 지우는 아이콘 버튼은 `CloseIconButton`(모바일 44px, 데스크톱 36px) 규칙을 따른다. 근거: [WCAG 2.2 — 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

## 5. 기능 정의

### 5.1 사용자 흐름과 선택 규칙

1. 사용자가 계산기 섹션에서 "포켓몬 이름으로 찾기" 입력창을 본다(타입 칩 위).
2. 글자를 입력하고 멈추면(디바운스 500ms) 자동완성 목록이 뜬다. 기본 종과 그 폼이 함께 나온다(예: "라이츄" → 라이츄, 메가라이츄X·Y, 라이츄 알로라의 모습).
3. 목록에서 항목을 탭하면 입력창에 이름이 채워지고 목록이 닫힌다. **칩이 그 폼의 타입으로만 선택**되고 결과가 갱신된다.

**선택 규칙 (2026-10-15 사용자 결정)**

| 상황 | 동작 |
| --- | --- |
| 포켓몬을 고른다 | 기존 칩 선택과 관계없이 **그 포켓몬 타입으로만** 칩을 바꾼다(합치지 않음). 결과는 "상대 한 마리"의 약점이기 때문이다 |
| 이름으로 설정된 상태에서 칩을 직접 누른다 | **이름으로 설정된 칩을 모두 해제**하고, 누른 칩부터 새로 선택한다. 선택 표시줄(5.4)도 사라진다 |
| 다른 포켓몬을 다시 고른다 | 첫 줄과 같다(통째로 교체) |
| "선택 초기화" | 칩과 이름 입력, 선택 표시줄을 모두 비운다 |

### 5.2 데이터 로딩

**결정(2026-10-15, 사용자 결정): 헤더 검색과 같은 `searchPokemonWithAllForms`를 쓰고, 백엔드가 응답에 `types`를 추가한다.** 프론트는 검색 한 번으로 이름과 타입을 함께 받는다.

- **백엔드 선행 작업**: `PokemonFormInfo`에 `types: [PokemonType!]!` 필드 추가, 폼 4종(기본·메가·폼체인지·리전폼)을 결과에 넣을 때 각 행의 `types`를 담는다. 서비스는 이미 행 전체를 읽고 있어 추가 조회가 없다.
- **프론트**: 이 기능 전용 쿼리를 정의해 필요한 필드(`name`, `number`, `index`, `formType`, `types`, 필요 시 `imagePath`)만 고른다. 백엔드 반영 후 `npm run codegen`.
- **디바운스**: 기존 검색 입력과 같은 `src/hooks/useDebounce.ts`의 훅과 기본 간격(500ms)을 쓴다. 헤더 포켓몬 검색(`useSearchPokemon`), 모바일 도감 검색(`ListSearch`), 기술·특성 검색이 모두 이 훅을 쓴다.
- **캐시**: 헤더 검색(`useSearchPokemon`, `cache-and-network`)의 방식을 따른다.
- **참고 사항(백엔드)**: 응답 `id`가 요청마다 `randomUUID()`로 바뀌어 Apollo 캐시 항목이 계속 쌓인다. 기능에는 영향이 없으나, 같은 작업에서 폼 코드 기반 고정 ID로 바꾸는 것을 검토한다.

**운영 API 실측(2026-10-15, `types` 추가 전 쿼리 기준)**

| 검색어 | 결과 | 응답 시간 |
| --- | --- | --- |
| 라이츄 | 라이츄, 메가라이츄X, 메가라이츄Y, 라이츄 알로라의 모습 | 0.06초 |
| 리자몽 | 리자몽, 메가리자몽X, 메가리자몽Y | 0.05초 |
| 나옹 | 나옹, 나옹 가라르의 모습, 나옹 알로라의 모습, 나옹마 | 0.04초 |

**검토 후 채택하지 않은 방식**

| 방식 | 불채택 사유 |
| --- | --- |
| `getPokemonList(filter: { name })` 이름 필터 | 타입은 주지만 **기본 종만** 반환한다. 리전폼·메가를 고를 수 없어 "기본 폼 기준" 배지와 안내가 필요해진다 |
| 검색 후 선택 시점에 폼별 쿼리로 타입을 한 번 더 조회(백엔드 무변경) | 동작은 확인했다(`getPokemonMegaEvolution`·`getPokemonRegionForm`·`getPokemonNormalForm`, 각 0.04~0.07초). 그러나 요청이 두 번이고, ID 체계가 달라(검색은 UUID, 폼은 숫자) **폼 이름으로 짝지어야** 한다. 리전폼 순서도 검색 결과와 폼 쿼리가 서로 달라(나옹: 가라르→알로라 / 알로라→가라르) 순번 매칭은 틀린다. 백엔드에 필드 하나를 더하는 편이 단순하다 |
| 페이지에 전체 목록 포함 / 첫 포커스에 전체 목록 조회 | 이름 입력을 쓰지 않는 방문자에게도 데이터를 보내고(전체 105KB), 폼 타입도 없다 |
| 목록을 저장소에 정적 파일로 보관 | 신규 포켓몬·폼 추가 시 소스와 DB가 어긋난다 |

### 5.3 이름 매칭 규칙

매칭은 서버가 한다(기본 종 이름 `contains` 후 폼 펼침). 화면은 디바운스가 끝난 검색어로 받은 결과를 표시한다.

- 정규화: 앞뒤 공백을 제거한 뒤 요청한다. 빈 문자열이면 요청하지 않고 목록을 닫는다(서버도 빈 검색어를 오류로 처리한다). 특수문자가 들어가는 이름(예: 니드런♀, 타입:널 — 실제 데이터 표기는 구현 시 확인)이 입력 가능해야 한다.
- 정렬: 서버는 도감 번호순, 같은 번호 안에서는 기본 → 메가 → 폼체인지 → 리전폼 순으로 준다. 화면은 "이름이 입력으로 시작하는 종"을 앞으로 올리되, 한 종의 폼은 묶어서 순서를 유지한다.
- 한 글자 입력: 쿼리에 개수 제한 인자가 없어 "이"처럼 한 글자는 결과가 많을 수 있다. 화면 노출은 상한(8건 안팎)으로 자르고 목록 영역은 스크롤한다(수치는 UX에서 확정). 최소 입력 글자 수를 둘지는 UX에서 정한다.
- 한글 IME: 조합 중에도 `onChange`가 발생하지만, 디바운스(500ms)가 끝난 값으로만 요청하므로 조합 중간 값 요청은 대부분 걸러진다. 조합 중 Enter로 선택이 일어나지 않게 한다.
- 응답 순서: 이전 검색어의 늦은 응답이 최신 결과를 덮어쓰지 않게 한다(헤더 검색과 같은 처리 방식을 따른다).

### 5.4 선택 후 표시

- 선택된 포켓몬을 입력창 아래 한 줄로 표시한다(예: 폼 이름·타입 태그 + 지우기 버튼). 이 표시는 "지금 결과가 어떤 포켓몬 기준인지"를 알려준다.
- 결과 영역의 제목은 바꾸지 않는다(현재 `selectTypeListKo` 기준). 포켓몬 이름을 결과 제목에 반영하는 것은 후속 개선 후보로만 둔다.

### 5.5 폼 표시와 검색 안내

- 폼은 각자의 실제 타입으로 계산하므로 **"기본 폼 기준" 배지는 두지 않는다**(2026-10-15 사용자 결정).
- 목록에서 같은 종의 폼끼리 구분되도록 폼 이름을 그대로 보여준다(예: "라이츄 알로라의 모습", "메가리자몽X").
- 폼 이름·지역명으로 시작하는 입력("알로라 라이츄", "메가리자몽", "히스이")은 결과가 0건이다. 이때 안내한다: "포켓몬 기본 이름으로 검색하면 메가진화·리전폼도 함께 나와요." (ADR-0022 이후 제거)

### 5.6 특성·도구 효과 안내

이름을 입력하면 사용자는 그 포켓몬의 **특성(예: 부유)** 까지 반영되리라 기대하기 쉽다. 현재 계산은 타입만 본다. 입력 근처 또는 결과 위에 한 줄 안내를 둔다: "특성·지닌 도구 효과는 반영하지 않고 타입만 계산해요."

## 6. UX 요구사항

> 상세 설계는 `ux-designer`에 위임한다(파이프라인: product-planner → ux-designer). 아래는 기획 단계의 요구사항이다.

### 6.1 배치와 가이드 문구

- `TypeCalculator` 섹션 안, 헤더 설명 문구와 "선택 초기화" 버튼 사이 또는 칩 그룹 바로 위에 입력창을 둔다.
- 입력창 레이블은 화면에 보이는 레이블 "포켓몬 이름으로 찾기"(`visuallyHiddenLabel={false}` 형태)를 쓴다. placeholder 예시는 흔한 이름 1개.
- **가이드 문구는 상황에 따라 바꾼다**(2026-10-15 사용자 결정). 예: 아무것도 고르지 않았을 때 "포켓몬 이름을 입력하거나 타입을 직접 선택해주세요", 이름으로 골랐을 때 "○○ 기준으로 계산했어요". 바뀌는 것은 계산기 섹션의 가이드 텍스트뿐이고, 메타 정보·H1·PageHeader 설명은 건드리지 않는다(4.2).

### 6.2 자동완성 목록

- **절대 위치 오버레이**로 띄운다. 문서 흐름에 넣으면 아래의 광고 슬롯(`TypeEffectivenessTopBanner`)과 칩 영역이 밀려 레이아웃 이동(CLS)과 광고 위치 변화가 생긴다.
- 헤더 검색 결과 목록이 모바일에서 `z-[600]`를 쓰고 있다. 같은 화면에 두 목록이 겹치지 않도록 z-index와 열림 상태 충돌을 확인한다(헤더 검색을 열면 이쪽을 닫는 등).
- 각 행에 폼 이름과 타입 태그를 함께 보여준다. 고르기 전에 타입을 확인할 수 있다.
- 행 높이 44px 이상(4.4). 행 간격은 오탭이 없게 한다.
- 로딩(검색 중), 결과 없음, 조회 실패 상태를 각각 정의한다. 조회 실패 시에도 **타입 칩으로 계속 쓸 수 있어야 한다**.

### 6.3 모바일

- 입력창 폭은 전체 폭. 자동 포커스는 하지 않는다. 키보드가 올라오면 칩과 광고를 가리는데, 재방문 사용자 중 칩만 쓰는 층에게 불편을 주지 않기 위해서다.
- `SearchInput`의 글자 크기가 `text-sm`(14px)이다. iOS Safari는 16px 미만 입력에 포커스하면 화면을 확대하는 경향이 있다. **실기기에서 확인**하고, 확대된다면 이 입력에 한해 16px 이상으로 한다(확인 지점 C5). 공식 규격이 아니라 알려진 브라우저 동작이므로 확인 항목으로 둔다.
- 입력창과 선택 표시가 한 화면(스크롤 없이)에서 결과의 첫 부분과 이어지도록 한다.

### 6.4 데스크톱

- 입력창은 전체 폭이 아니라 적정 최대 폭을 둔다. 조정은 `desktop:` 한 값으로만 한다(ADR-0020).

### 6.5 접근성

- ARIA 콤보박스 패턴(입력 `role="combobox"`, 목록 `role="listbox"`, 항목 `role="option"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`)과 키보드(위/아래 이동, Enter 선택, Esc 닫기)를 따른다. 근거: [WAI-ARIA APG — Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/).
- 현재 `SearchInput`은 이 속성들과 ref를 받지 못한다. **DS 원자 확장(또는 래퍼)이 필요**하다. 방식은 구현 착수 시 `structure.md`·ADR-0010(원자 우선)에 따라 확정한다.
- 선택 결과를 스크린리더에 알린다(예: "라이츄 알로라의 모습 선택, 전기·에스퍼 타입이 선택되었습니다" — `aria-live`).

### 6.6 같은 화면의 두 검색창

헤더 검색(상세 페이지로 이동)과 이 입력(타입 자동 선택)은 같은 쿼리를 쓰지만 목적이 다르다. 사용자가 혼동하지 않도록 레이블·placeholder로 구분하고, 필요하면 ux-designer가 시각적 위계를 정한다.

## 7. 재사용 설계 (파티 타입 커버리지 대비)

파티 점검은 보류지만, 입력 컴포넌트는 재사용 가능하게 만든다. 아래를 **요구사항**으로 둔다.

| 요구 | 이유 |
| --- | --- |
| 입력 컴포넌트는 `TypeEffectivenessContext`를 직접 읽지 않는다. 선택 결과를 콜백(`onSelect`)으로만 내보낸다 | 다른 화면(파티 모드 등)은 다른 상태를 쓴다. 계산기 전용 Context에 묶이면 재사용이 불가능하다 |
| 항목 데이터는 `{ number, name, index, formType, types }`로 폼을 식별한다 | 폼 단위 선택이 기본이므로 처음부터 폼 식별자를 갖는다 |
| 제외·비활성 목록(이미 고른 포켓몬) 지정 가능 | 파티에 같은 포켓몬 중복 방지 |
| 선택 후 입력창을 비울지 여부 옵션 | 계산기는 이름을 남기고, 파티는 비우고 다음 입력을 받는다 |
| 이벤트용 `source` 값을 주입받는다 | 같은 컴포넌트의 이벤트를 화면별로 구분해 집계 |
| 데이터 훅(검색 요청·디바운스·캐시)을 컴포넌트와 분리 | 다른 화면에서 같은 훅과 Apollo 캐시를 그대로 쓴다 |
| 계산기 쪽 동작은 별도 연결 코드에 둔다 | 컴포넌트 재사용 시 계산기 규칙(5.1 선택 규칙)이 따라오지 않게 한다 |

계산기 연결에 필요한 상태 변경은 두 가지다. **Context에 "타입 목록을 한 번에 지정하는 액션"**과 **"현재 칩이 이름으로 설정됐는지"를 구분하는 상태**가 필요하다(5.1의 칩 해제 규칙). 배치는 `.claude/conventions/guides/structure.md`에 따라 구현 단계에서 확정한다.

## 8. 확장 단계: 폼 이름으로 시작하는 검색

### 8.1 선행 조건

[ADR-0022](../../decisions/records/ADR-0022-list-search-include-forms.md)(상태 제안)가 승인되고, 백엔드 이름 검색이 폼 이름·지역명까지 매칭하는 것.

### 8.2 확장 범위

- "알로라 라이츄", "메가리자몽", "히스이"처럼 폼 이름·지역명으로 시작하는 입력이 결과를 갖는다. 표시 이름은 "알로라 라이츄" 어순으로 입력해도 찾아지도록 **ADR-0022의 토큰 매칭 규칙**을 따른다.
- 5.5의 0건 안내를 제거한다.
- 응답 형태가 같으면 입력 컴포넌트는 바뀌지 않는다.

### 8.3 이 단계를 앞당기는 신호

첫 배포의 "결과 없음" 이벤트(9)에서 메가·지역명으로 시작하는 입력 비율이 높으면 확장 우선순위를 올린다. (참고: 메가 의도 Search Console 노출 48,480, 리전폼 의도 4,434 — ADR-0022 맥락.)

## 9. 측정 (GA4)

### 9.1 이벤트 정의

이벤트 이름은 소문자 스네이크 케이스 40자 이내, 전송은 [`coding.md` "분석 이벤트 전송"](../../conventions/guides/coding.md) 규칙을 따른다. 이름은 구현 단계 C2에서 최종 확정한다.

| 이벤트(가칭) | 발생 시점 | 핵심 파라미터(가칭) | 쓰임 |
| --- | --- | --- | --- |
| `type_name_search_use` | 한 페이지 로드에서 **처음으로** 이름 입력이 시작될 때 1회 | `source` | 이름 입력 사용률(사용 세션 / 상성 랜딩 세션) |
| `type_name_search_select` | 자동완성 목록에서 포켓몬을 선택했을 때 | `source`, `pokemon_number`, `form_type`, `type_count`, `query_length`, `rank`(목록 내 위치) | 선택 성공 여부, 어떤 포켓몬·폼이 많이 찾히는지, 자동완성 품질 |
| `type_name_search_no_result` | 결과 0건 상태가 입력 멈춤 후 약 1초 유지될 때 | `source`, `query`(길이 제한) | 폼 이름 검색 수요 확인(8.3), 이름 데이터 점검 |
| `type_calc_run` | 계산 결과가 새로 만들어질 때(아래 정의) | `input_method`(chip / name), `type_count`, `types` | **계산 실행 수**(주 성공 지표), 입력 방식별 비교 |

**"계산 실행"의 정의 (2026-10-15 확정).**

- **이름 선택**: 선택 1회 = 1회. 선택 규칙(5.1)상 타입이 한 번에 정해져 중간 상태가 없다.
- **칩 선택**: 결과가 비어 있지 않게 되는 선택 변경을 1회로 센다. 칩을 연속으로 눌러 생기는 중간 상태(1개 → 2개)가 부풀리지 않도록 **같은 페이지 로드 안에서 같은 타입 조합은 1회만** 센다.

### 9.2 구현 요구

- 현재 GA4 이벤트 전송 헬퍼가 코드에 없다(`layout.tsx`의 기본 설정뿐). 전송은 `coding.md` 규칙(`modules/`의 공통 유틸 + 이벤트 타입 정의)을 따른다. 1.62.0의 첫 이벤트 기능이 유틸을 만들고 다른 기능은 이를 쓴다.
- 커스텀 파라미터를 보고서에서 쓰려면 GA4에서 **맞춤 측정기준으로 등록**해야 한다([GA4 맞춤 측정기준](https://support.google.com/analytics/answer/14240153)). 등록은 사용자가 콘솔에서 한다(C6).
- 개인 식별 정보를 보내지 않는다([GA4 PII 정책](https://support.google.com/analytics/answer/6366371)). 입력 원문은 `no_result`에서만, 길이를 제한해 보낸다.
- 이름 입력과 선택은 URL을 바꾸지 않으므로 페이지뷰가 늘지 않는다(4.1). 이벤트로만 측정한다.

### 9.3 성공 지표와 가드레일

기준값은 트래픽 스냅샷(GA4 28일)이다. 새 이벤트는 측정 전이므로 **출시 4주 후를 베이스라인**으로 삼는다.

| 지표 | 현재 값(28일) | 목표 | 해석 |
| --- | --- | --- | --- |
| 이름 입력 사용 세션 비율 | 측정 전 | 4주 후 베이스라인 수립 | 파티 점검 착수 판단의 참고 지표 |
| 계산 실행 수 / 상성 세션 | 측정 전 | 배포 전후 비교(칩만 쓰던 시기 대비) | 주 성공 지표. 입력 방식별로 분리해 본다 |

작업 원칙:

- 코드 수정은 단계별로 나눠서 하고 한 번에 여러 파일을 고치지 않는다.
- 공유 컴포넌트(`SearchInput` 확장 포함)를 고치면 모든 사용처를 확인한다. 헤더·목록 필터·챔피언스 등 `SearchInput` 사용처가 대상이다.
- `searchPokemonWithAllForms`는 헤더 검색도 쓴다. 백엔드 변경 후 헤더 검색이 그대로 동작하는지 확인한다.
- dev 서버는 사용자가 실행한다. dev 서버가 켜진 상태에서 `npm run build`를 하지 않는다.
- 라우팅·메타데이터는 건드리지 않지만, 배포 전에 `/type-effectiveness` 요청이 200이고 HTML 본문·JSON-LD가 변하지 않았는지 curl로 확인한다.

## 11. 결정 사항 (2026-10-15 정리)

1. **데이터 로딩**: `searchPokemonWithAllForms` + 백엔드 `types` 추가(5.2).
2. **초성 검색**: 범위 제외(2.2).
3. **선택 규칙과 "계산 실행" 정의**: 5.1, 9.1.
4. **파티 점검**: 보류. 착수 시점은 별도로 정한다.
5. **가이드 문구**: 상황에 따라 바꾼다. 메타 정보는 바꾸지 않는다(6.1).
6. **"기본 폼 기준" 배지**: 두지 않는다. 폼을 실제 타입으로 계산하기 때문이다(5.5).

## 12. 리스크

| 리스크 | 영향 | 완화 |
| --- | --- | --- |
| 백엔드 변경이 헤더 검색에 영향 | 헤더 검색 오동작 | 필드 추가만 하고 기존 필드는 그대로. 배포 후 헤더 검색 확인(10) |
| 프론트가 백엔드보다 먼저 상용에 배포됨 | 상용에서 이름 검색이 `types` 필드 오류로 실패 | 7단계 순서 고정(백엔드 → 상용 API 확인 → 프론트). 전용 쿼리라 헤더 검색 등 기존 기능에는 영향 없음 |
| 폼 이름으로 시작하는 검색이 0건 | 기대 불일치 | 5.5 안내 문구, 8 확장 |
| 특성 효과를 기대한 사용자의 불만 | 신뢰 하락 | 5.6 안내 문구 |
| 검색 요청 지연·실패 | 이름 입력이 동작하지 않음 | 칩으로 계속 사용 가능, 오류 상태 정의. 실측 응답 0.04~0.06초 |
| 늦게 온 이전 응답이 최신 결과를 덮어씀 | 입력과 다른 목록 표시 | 5.3 응답 순서 처리 |
| 이름 입력이 빠른 조회를 더 빠르게 하여 PV 감소 | 광고 수익 영향 | 9.3 가드레일 |

| iOS 입력 확대 | 화면 흔들림 | C5 실기기 확인 후 글자 크기 조정 |
| 메타 동결 중 다른 변경이 섞임 | 효과 귀속 불가 | 4.2, 별도 SEO 트랙은 2주 후 |
| 헤더 검색과 목록 겹침 | 사용 혼선 | 6.2 열림 상태 충돌 처리 |
