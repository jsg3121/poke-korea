# E2E 검사 스킬

변경 내용에 맞는 E2E spec을 **이번 검사를 위해 작성하고, 실행하고, 지운다.** spec은 저장소에 남기지 않는다(`e2e/`는 gitignore). 작성 규칙은 `.claude/conventions/guides/testing.md`가 권위 원본이다. 애플리케이션 코드는 고치지 않는다.

> **Why 매번 작성하고 지우는가:** spec을 쌓아 두면 이후 검사에서 이번 변경과 무관한 이전 테스트까지 함께 돌고, 오래된 기대값이 새 작업을 막는다. 검사마다 그 변경에 필요한 흐름만 검증한다. `e2e/` 작성·삭제는 승인 없이 허용돼 있다(`.claude/settings.json`의 `Edit(e2e/**)`, `Bash(rm -rf e2e)`).

## 1. 사전 확인

E2E는 사용자가 띄운 개발 서버에 붙어서 돈다. 서버를 직접 띄우지 않는다(`npm run dev`·`npm run build` 금지 — 개발 서버는 사용자가 관리하고, 빌드는 실행 중인 서버를 죽인다).

```bash
curl -s -o /dev/null -w "%{http_code}" --max-time 15 http://localhost:3000/
curl -s -o /dev/null -w "%{http_code}" --max-time 15 -X POST \
  -H 'content-type: application/json' -d '{"query":"{__typename}"}' \
  http://localhost:4000/graphql
```

둘 중 하나라도 200이 아니면 **spec을 쓰지 않고 "실행 불가"로 보고**한다. 통과로 처리하지 않는다. 보고에 "개발 서버(`npm run dev`)와 GraphQL 서버를 띄운 뒤 다시 실행"을 안내한다.

## 2. 검증할 흐름 도출

변경 파일 목록(호출자가 넘겨준 것, 없으면 `git diff {대상 브랜치}...HEAD --name-only`)과 diff, 커밋 메시지를 읽고 **영향받는 사용자 흐름**을 목록으로 만든다.

| 변경                                                         | 도출할 흐름                                                                      |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 라우트·컨테이너·컴포넌트(`app/`, `containers/`, `components/`, `views/`) | 그 화면에서 바뀐 입력·클릭에 따른 URL·화면 상태 변화                             |
| 공용 코드(`hooks/`, `modules/`, `utils/`, `context/`, 헤더·푸터) | 바뀐 파일을 import하는 곳을 `grep`으로 찾아, **사용처마다** 대표 흐름 하나 이상 |
| 버그 수정 커밋                                                | 그 버그의 재현 시나리오                                                          |
| URL 쿼리를 함께 쓰는 컴포넌트                                 | 다른 파라미터가 유지되는지(경계)                                                 |
| 문서(`.md`)·스타일만 변경                                     | 없음 → 실행하지 않고 스킵 사유 보고                                              |

흐름마다 실제 화면 코드를 읽어 **접근 가능한 이름**(버튼 텍스트, 라벨, `aria-label`, `role`)을 확인한다. 추측한 이름으로 쓰지 않는다. 헤더·푸터는 User-Agent로 갈리므로 디바이스별 요소 차이도 확인한다.

## 3. spec 작성

```bash
rm -rf e2e
```

이전 검사의 잔여물을 지운 뒤 `e2e/{라우트}/{흐름}.spec.ts`로 작성한다. `testing.md`의 선택자·대기·디바이스 규칙을 따른다. 헬퍼는 spec 파일 안에 둔다.

## 4. 실행

```bash
npx playwright test --reporter=list
```

두 프로젝트(`mobile`, `desktop`)가 모두 돈다. 테스트별 통과·실패, 실패 위치, 기대값·실제값을 수집한다.

## 5. 실패 분류

먼저 **테스트 자체의 오류인지** 본다. 요소를 찾지 못함(locator 타임아웃)·문법 오류처럼 spec을 잘못 쓴 경우에는 화면 코드를 다시 읽고 선택자만 고쳐 다시 실행한다(최대 2회). **기대 동작(기대값)은 바꾸지 않는다.** 기대가 맞는지 확신이 없으면 고치지 말고 그 판단을 보고한다.

남은 실패는 그 테스트만 **한 번** 다시 실행한다.

```bash
npx playwright test {spec}:{라인} --project={프로젝트} --reporter=list
```

| 분류      | 기준                                                                              | 등급      |
| --------- | --------------------------------------------------------------------------------- | --------- |
| 회귀      | 다시 실행해도 같은 동작 검증에서 실패                                             | 🔴        |
| 불안정    | 다시 실행하면 통과                                                                | 🟡        |
| 환경 문제 | 서버 응답 없음·타임아웃·컴파일 에러 화면·GraphQL 에러 등 테스트 대상과 무관한 원인 | 실행 불가 |

회귀로 판정하면 테스트 이름·조작 순서·기대값·실제값과 관련 변경 파일을 연결해 원인 후보를 적는다. spec이 지워져도 재현할 수 있도록 **조작 순서를 보고에 남긴다.**

## 6. 정리

결과와 상관없이(실패해도) 마지막에 지운다.

```bash
rm -rf e2e
```

## 7. 결과 보고

```markdown
## E2E 검사 결과

### 요약

- 검증한 흐름: {N}개 ({테스트 N개} × 프로젝트 2)
- 결과: ✅ 통과 {N} · 🔴 회귀 {N} · 🟡 불안정 {N} · ⏭️ 실행 불가 {N}
- 도출 근거: {변경 파일 → 흐름}
- spec 정리: 완료

### 검증한 흐름

| 흐름 | mobile | desktop |
| ---- | ------ | ------- |
| {테스트 이름} | ✅ | ✅ |

### 🔴 회귀

#### {테스트 이름} `{프로젝트}`

- **조작**: {goto URL → 입력/클릭 순서}
- **기대**: {기대값} / **실제**: {실제값}
- **관련 변경**: {파일}
- **원인 후보**: {설명}

### 🟡 불안정

- {테스트 이름} — 재실행에서 통과

### 실행 불가 · 스킵

- {사유 — 서버 미기동, 문서만 변경 등}
```

## 하지 않는 것

- 개발 서버·GraphQL 서버 기동, `npm run build`
- 애플리케이션 코드 수정, 실패한 테스트의 기대값 변경
- spec을 남겨 두거나 커밋
- 실행 불가·스킵을 통과로 보고
- 화면 캡처로 시각 판정
