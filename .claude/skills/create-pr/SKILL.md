# PR 생성 스킬

사용자가 선택한 검증 옵션에 따라 조건부로 품질 검증을 수행하고 PR을 생성한다.

## 전체 플로우

```
┌─────────────────────────────────────────────────────────────┐
│                       create-pr                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 현재 상태 확인 (브랜치, 변경 사항)                         │
│                     ▼                                       │
│  2. 대상 브랜치 확인                                         │
│                     ▼                                       │
│  3. 검증 옵션 선택 (사용자 확인)                              │
│     ┌─────────────────────────────────────────┐             │
│     │ □ QA 종합 검증 (qa-orchestrator)       │             │
│     │ □ 정적 분석만 (lint, format, type)     │             │
│     │ □ E2E 테스트 (Playwright)              │             │
│     └─────────────────────────────────────────┘             │
│                     ▼                                       │
│  4. [선택 시] 해당 검증 실행                                 │
│                     ▼                                       │
│  5. [이슈 발견 시] 보고 + 계속 여부 확인                      │
│                     ▼                                       │
│  6. PR 본문 작성 + 생성                                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

## Phase 1: 상태 확인

### 1.1 현재 상태 확인

```bash
git branch --show-current
git status
git log --oneline -10
```

### 1.2 대상 브랜치 확인

사용자에게 어느 브랜치로 머지할 것인지 확인한다.

- 작업 브랜치(`feature/{version}-{작업명}`) → 버전 루트(`feature/{version}`): 세부 기능 단위 PR
- 버전 루트(`feature/{version}`) → `main`: 릴리즈 PR

---

## Phase 2: 검증 옵션 선택

### 2.1 AskUserQuestion으로 검증 옵션 선택받기

`AskUserQuestion` 도구를 사용하여 체크박스 형태로 검증 옵션을 선택받는다.

```json
{
  "questions": [
    {
      "question": "PR 생성 전 어떤 검증을 실행할까요?",
      "header": "검증 옵션",
      "multiSelect": true,
      "options": [
        {
          "label": "QA 종합 검증",
          "description": "qa-orchestrator가 변경 파일을 분석해 필요한 검사(린트·코드리뷰·접근성·SEO)만 병렬 실행하고 통합 판정합니다"
        },
        {
          "label": "정적 분석만",
          "description": "ESLint, Prettier, TypeScript 타입 검사만 빠르게 실행합니다"
        },
        {
          "label": "E2E 테스트",
          "description": "Playwright로 E2E 테스트를 실행합니다 (빌드 포함)"
        }
      ]
    }
  ]
}
```

### 2.2 기본값 정책

| 대상 브랜치 | 기본 선택                       | 이유             |
| ----------- | ------------------------------- | ---------------- |
| `main`      | QA 종합 검증 권장               | 릴리즈 품질 보장 |
| 그 외       | 모두 미선택 (검증 없이 바로 PR) | 빠른 피드백 루프 |

**main 머지 시 안내 메시지:**

> "main 브랜치로 머지하는 PR입니다. QA 종합 검증을 권장합니다."

**그 외 브랜치 머지 시:**

> "검증 없이 바로 PR을 생성하거나, 필요한 검증을 선택하세요."

### 2.3 사용자가 "Other"를 선택한 경우

사용자 입력에 따라 유연하게 대응한다:

- "린트만" → 정적 분석만 실행
- "전체" / "다" → QA 종합 검증 + E2E 테스트
- "스킵" / "없음" → 검증 없이 PR 생성

---

## Phase 3: 조건부 검증 실행

사용자가 선택한 옵션에 따라 해당 검증만 실행한다.

### 3.1 QA 종합 검증 (선택 시)

`qa-orchestrator` 에이전트에 위임한다. 검사 선별·병렬 실행·통합 판정을 에이전트가 수행한다.

```
Agent({
  subagent_type: "qa-orchestrator",
  prompt: "대상 브랜치 {대상 브랜치} 기준으로 QA 검증을 수행하세요."
})
```

**판정별 처리:**

| 판정 | 처리 |
| ---- | ---- |
| ⛔ 수정 필요 | 차단 항목을 보고하고 **PR 생성을 중단**한다 |
| ⚠️ 조건부 진행 | 권장 항목을 보고하고 계속 여부를 사용자에게 확인 |
| ✅ 진행 가능 | 바로 Phase 4로 진행 |

> **Why 위임하는가:** 검사 절차를 이 스킬에 중복해서 적어두면 스킬 문서(`lint-check` 등)와 이중 관리가 되어 한쪽만 고쳤을 때 어긋난다. 검사 방법은 각 스킬 문서가, 조율은 qa-orchestrator가 단일 권위를 갖는다.

### 3.2 정적 분석만 (선택 시)

빠른 확인이 필요할 때 사용한다. 변경된 파일을 대상으로 직접 실행한다:

```bash
# 변경된 파일 목록
git diff {대상 브랜치}...HEAD --name-only --diff-filter=ACMR

# 린트·포맷 검사는 프로젝트 script 우선
npm run lint

# TypeScript 타입 검사
npx tsc --noEmit
```

**이슈 발견 시:**

- 에러 목록을 보고한다
- 자동 수정 가능 여부를 안내한다
- **에러(error)가 있으면 PR 생성을 중단**한다. 경고(warn)는 사용자 판단에 맡긴다

### 3.3 E2E 테스트 (선택 시)

```bash
npm run build && npx playwright test
```

**실패 시:**

- 실패한 테스트 목록을 보고
- 계속 여부를 사용자에게 확인 (main 머지 시에는 중단 권고)

### 3.4 검증 결과 요약

모든 선택된 검증이 완료되면 요약을 보고한다:

```markdown
## 검증 결과 요약

| 검증 항목    | 결과            | 상세                        |
| ------------ | --------------- | --------------------------- |
| QA 종합 검증 | ⚠️ 조건부 진행  | 🔴 0 · 🟡 3 (seo-audit 스킵) |
| 정적 분석만  | -               | 미선택                      |
| E2E 테스트   | -               | 미선택                      |
```

## Phase 4: PR 생성

### 4.1 변경 사항 분석

```bash
git diff {대상 브랜치}...HEAD --stat
git log {대상 브랜치}...HEAD --oneline
```

### 4.2 PR 본문 작성

`.claude/skills/create-pr/templates/pr-template.md` 템플릿을 기반으로 작성한다.

**작업 유형 체크 규칙:**

- 변경 사항에 해당하는 작업 유형은 `[x]`로 체크한다
- **해당하지 않는 작업 유형도 삭제하지 않고** `[ ]` 상태로 유지한다

```markdown
## 📋 작업 유형

- [x] ✨ 새 기능 (New Feature)
- [ ] 🐛 버그 수정 (Bug Fix)
- [ ] 🚨 핫픽스 (Hotfix)
- [x] 🔧 리팩토링 (Refactoring)
- [ ] 🚀 성능 개선 (Performance)
- [ ] 🔍 SEO 개선 (SEO)
- [ ] 🎨 디자인 변경 (Design)
- [ ] 📝 문서 (Documentation)
- [ ] 🔨 Breaking Changes
```

### 4.3 PR 라벨 매핑

체크된 작업 유형에 맞는 라벨을 부여한다:

| 작업 유형           | 라벨              |
| ------------------- | ----------------- |
| ✨ 새 기능          | `feature`         |
| 🐛 버그 수정        | `bug`             |
| 🚨 핫픽스           | `hotfix`          |
| 🔧 리팩토링         | `refactoring`     |
| 🚀 성능 개선        | `performance`     |
| 🔍 SEO 개선         | `seo`             |
| 🎨 디자인 변경      | `design`          |
| 📝 문서             | `documentation`   |
| 🔨 Breaking Changes | `breaking-change` |

### 4.4 PR 제목

Conventional Commits 형식을 따른다:

```
feat: 포켓몬 상세 페이지 타입 상성 표 추가
fix: 도감 검색 시 다른 쿼리 파라미터가 유실되는 문제 수정
```

### 4.5 PR 생성 실행

사용자에게 제목, 본문, 라벨, 대상 브랜치를 보여주고 확인을 받은 후 실행한다:

```bash
gh pr create \
  --base {대상 브랜치} \
  --title "{PR 제목}" \
  --body "$(cat <<'EOF'
{PR 본문}
EOF
)" \
  --label "{라벨1}" --label "{라벨2}"
```

### 4.6 완료 후

생성된 PR URL을 사용자에게 전달한다.

## 검증 옵션별 토큰 비용

| 옵션          | 실행 방식              | 토큰 비용 | 소요 시간         |
| ------------- | ---------------------- | --------- | ----------------- |
| 정적 분석만   | Bash 직접 실행         | 낮음      | ~10초             |
| QA 종합 검증  | 에이전트 + 병렬 서브   | 높음      | ~60초 (병렬)      |
| E2E 테스트    | Bash 직접 실행         | 중간      | ~60초 (빌드 포함) |

**토큰 절약 팁:**

- 단순 버그 수정, 스타일 변경: 검증 없이 바로 PR
- 로직 변경이 있는 기능: 정적 분석만
- 릴리즈 PR·범위가 큰 변경: QA 종합 검증 권장

QA 종합 검증은 변경 파일에 따라 불필요한 검사를 스킵하므로, 검사 4종을 개별 실행하는 것보다 저렴하다.
