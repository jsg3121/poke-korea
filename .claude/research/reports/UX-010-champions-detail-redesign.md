## 0. 실캡처 재검증 — 사용자 제보 문제의 실제 원인

메인 세션이 제공한 4장(기본폼 desktop/mobile, 메가폼 desktop/mobile)을 직접 확인했다. 제보된 문제는 모두 재현되며, 코드 대조 결과 원인은 다음과 같다.

**모바일 우측 메타 컬럼 붕괴는 "모바일 코드 버그"가 아니라 "UA 분기 구조 자체의 결함"이다.**

- `src/container/mobile/champions/ChampionsDetail.container.tsx`를 읽으면 실제로는 `<ChampionsFormTab>` → 그라데이션 카드(세로) → 능력치 카드(세로) → `<ChampionsMetaSectionMobile>`(세로, 탭 4개) 순서의 **완전한 세로 스택**이다. 이 컴포넌트 자체에는 2단 그리드가 없다.
- 그런데 캡처된 모바일 화면은 명백히 2단(좁은 좌/우 컬럼)이다. 이는 `src/container/desktop/champions/ChampionsDetail.container.tsx`의 `<div className="flex gap-8"><aside className="w-[420px] flex-shrink-0">...</aside><section className="flex-1">...</section></div>` 구조가 그대로 렌더된 것과 일치한다.
- `renderChampionsDetail.tsx`는 `headers().get('user-agent')`를 `detectUserAgent`로 판별해 데스크톱/모바일 컨테이너를 **서버에서 완전히 다른 컴포넌트**로 분기한다(`isMobile ? <ChampionsDetailMobile/> : <ChampionsDetailDesktop/>`). 캡처 도구(Playwright 등)가 데스크톱 UA로 뷰포트만 375px로 줄여 캡처했다면, 서버는 데스크톱 컨테이너를 내려주고 그 결과 `w-[420px]` 고정폭 aside가 375px 화면에 찌그러져 들어간다.
- **이것이 바로 ADR-0007이 UA 분기를 제거하려는 근거의 실증 사례**다 — "뷰포트가 아니라 서버 UA로 레이아웃이 결정되면, 실제 브라우저 폭과 무관하게 레이아웃이 깨질 수 있다." 진짜 모바일 UA(iOS Safari 등)로 접속했다면 이 특정 붕괴는 나타나지 않았을 것이나, **UA 문자열 위장·데스크톱 브라우저의 반응형 모드·태블릿 등 UA 판별 경계의 모든 기기**에서 상시 재현 가능한 구조적 결함이다. `detectUserAgent` 휴리스틱이 커버하지 못하는 UA는 항상 이 위험에 노출된다.
- 파트너/도구 이름의 세로 쪼개짐(`한카리아스`→"한카/리아/스", `먹다남은음식`→"먹다남은음/식")도 동일 원인 — `flex-1`이 420px 폭 대비 극단적으로 좁아진 컬럼 안에서 `ChampionsPartnerList`/`ChampionsMetaList`의 텍스트가 `break-keep` 없이 강제 개행된다(코드 확인: 두 컴포넌트 모두 `word-break` 제어 없음, 이는 UX-006 C1이 지적한 `MoveCard` 세로 쪼개짐과 동일 패턴).
- **결론**: 진짜 모바일 컨테이너(mobile container) 코드는 세로 스택으로 이미 안전하지만, **UA 분기 구조 자체가 리스크**이므로 이번 반응형 단일화로 근본 해결한다. 아래 §1 비평은 "진짜 모바일 컨테이너 코드"와 "데스크톱 컨테이너 코드"를 각각 분석 대상으로 삼는다.

**폼탭 가로 스크롤은 이미 구현되어 있으나 발견 가능성이 낮다.**

- `ChampionsFormTab.component.tsx`는 `overflow-x-auto` + `[&::-webkit-scrollbar]:hidden`로 가로 스크롤을 이미 구현했다(각 탭 `min-w-[10rem]` `shrink-0`). 메가라이츄 모바일 캡처에서 "메가라이츄X"까지만 보이고 현재 선택된 "메가라이츄Y"·"라이츄(알로라의 모습)"가 잘려 보이는 것은 **기능 결함이 아니라 스크롤 인디케이터 부재로 인한 발견 가능성 문제**다. 스크롤바를 의도적으로 숨겼기 때문에(`hidden`) 사용자가 "더 있다"는 단서를 받지 못한다. 게다가 활성 탭(Y)이 자동으로 뷰 안에 스크롤되지 않아, 현재 보고 있는 폼이 화면 밖에 있을 수 있다(`scrollIntoView` 부재).

## 1. 기존 화면 4축 비평

### 🔴 Critical

**C1. UA 분기가 뷰포트와 무관하게 레이아웃을 고정 — 반응형 실패의 근본 원인 (ADR-0007 위반)**
- 문제: `renderChampionsDetail.tsx`가 서버 UA로 desktop/mobile 컨테이너 자체를 분기한다. §0에서 실증했듯, UA 판별이 실제 렌더 폭과 어긋나는 모든 경우(위장 UA, 반응형 뷰 모드, 판별 실패 기기) 레이아웃이 붕괴한다.
- 근거: [ADR-0007](../../decisions/records/ADR-0007-responsive-rendering-strategy.md) "신규 UA 기반 분기 금지", WCAG 1.4.10(Reflow) — 뷰포트 320~1280px 어디서든 콘텐츠 손실·가로 스크롤 없이 재구성되어야 함. 현재 구조는 이 요구를 "서버가 맞춘 UA일 때만" 우연히 만족한다.
- 개선안: §2 IA로 컨테이너 1벌 + Tailwind `desktop:`(769px) 반응형 단일화. `container/desktop`·`container/mobile` 2벌(각 약 150줄, 8개 하위 컴포넌트 포함 약 300줄 중복) 통합.

**C2. 데스크톱 2단 그리드가 모바일 폭에서 찌그러지면 텍스트가 읽기 불가능한 상태까지 붕괴 (실캡처 확정)**
- 문제: 좁은 폭에서 `aside w-[420px]`/`flex-1` 2단이 유지되면 우측 컬럼이 극단적으로 좁아지고, 그 안의 파트너명·도구명이 글자 단위로 세로 개행된다(캡처: "한카리아스"→"한카/리아/스").
- 근거: WCAG 1.4.10(Reflow) — 텍스트가 읽을 수 없는 상태는 정보 손실이며 Critical 등급. UX-006 C1(동일 패턴, `MoveCard` dt/dd flex-wrap 폭 붕괴)과 판례 일치.
- 개선안: §2 — 모바일 base는 완전 세로 스택(1열), 2단은 `desktop:` 이상에서만 적용. 텍스트 컨테이너에는 `break-keep` 명시(한국어 단어 단위 줄바꿈 보장, 현재 두 리스트 컴포넌트 모두 누락).

**C3. 능력치 시각화가 canvas 레이더 단독 — 접근성 차단 (UX-005 C3와 동일 결함, champions는 아직 미해결)**
- 문제: `StatChartComponent`(Chart.js Radar, canvas)가 유일한 스탯 표현이다. 개별 수치는 canvas 내부 `pointLabels`로만 그려지고, DOM에는 스크린리더가 읽을 개별 수치 텍스트가 없다(`aria-label="포켓몬 능력치 차트 그래프"` 하나뿐, 라벨-값 대응이 전달되지 않음).
- 근거: WCAG 1.1.1(Non-text Content). RES-003 벤치마크(5곳) 레이더 사용 0곳. 상세 3호(UX-005 §6-1)는 이미 이 이유로 StatBar 전환을 완료해 서비스 내 두 가지 시각 언어가 공존 중이다.
- 개선안: §3 결정 2 — StatBar로 통일(적극 권고).

### 🟡 Major

**M1. 폼탭 스크롤 가능 영역의 발견 가능성 부재 + 활성 탭 자동 스크롤 없음 (실캡처 확정, 메가폼)**
- 문제: `overflow-x-auto`가 스크롤바를 CSS로 숨기고(`[&::-webkit-scrollbar]:hidden`), 진입 시 현재 선택된 폼(Y)이 스크롤 뷰 밖에 있어도 자동으로 보이지 않는다. 메가라이츄Y 진입 캡처에서 활성 탭 "메가라이츄Y"가 화면 밖(가려짐)이었다.
- 근거: Nielsen Norman Group "Scroll cue" — 스크롤 가능 콘텐츠는 시각적 단서(페이드 그라데이션, 화살표, 부분적으로 잘린 다음 항목)가 있어야 발견된다. 완전히 숨긴 스크롤바는 이 단서를 제거한다. 또한 "시스템 상태 가시성"(현재 선택된 폼이 안 보임) 위반.
- 개선안: (1) 좌우 끝에 `pointer-events-none` 그라데이션 페이드로 "더 있음" 단서 제공. (2) 마운트 시 활성 탭으로 `scrollIntoView({ inline: 'center', behavior: 'instant' })`. (3) 탭 4개 이하인 경우가 대부분이므로 스크롤바 자체를 얇게 노출하는 것도 대안(과다 은닉 지양).

**M2. 파트너/기술/도구 리스트에 `break-keep` 부재로 좁은 폭에서 텍스트 붕괴 위험 상존** — C2로 이미 확정 재현했지만, 반응형 전환 후에도 최소 폭(예: 320px 초소형 기기, 2단 그리드 유지 시 좌측 카드 등)에서 재발 가능한 구조적 결함이다. 개선: `ChampionsMetaList`·`ChampionsPartnerList` 텍스트에 `break-keep` 명시(상세 3호 `MoveTable`이 이미 `break-keep` 적용 — 동일 방어 적용).

**M3. 헤더 구조가 E-1(홈/티어/도감)과 완전히 다른 패턴 — 챔피언스 3+1화면 중 상세만 이질적** — E-1은 `PageHeaderComponent`(제목+설명, `border-b`) + `ChampionsFormatIntro`(포맷탭+캡션)를 페이지 상단 공통 헤더로 쓴다. 상세는 자체 그라데이션 히어로 카드(타입색 배경 + 이미지 + 브레드크럼 + 메타요약)로 완전히 다른 문법이다. 근거: NN/g 일관성 원칙 — 같은 섹션(챔피언스) 안에서 상단 구조 문법이 라우트마다 다르면 "지금 챔피언스 안에 있다"는 위치 감각이 약해진다. 개선: §3 결정 5 — 완전 통일은 부적절(상세는 포맷 토글이 필요 없고 히어로가 필수)하나, 브레드크럼 스타일·타이포 스케일은 정합.

**M4. 챔피언스 메타 바 시각화(`ChampionsMetaList`)가 상세 3호 `StatBar`/`MoveTable`과 시각 언어 불일치** — `ChampionsMetaList`는 `bg-primary-3/30` 카드 배경 + `bg-primary-1` 단색 바, `StatBar`는 `bg-primary-1/10` 트랙 + 최고/최저 강조 색 분기. 동일 "막대 그래프로 비율 표현" 패턴인데 배경톤·바 색·트랙 스타일이 다르다. 근거: 디자인 시스템 일관성(컨벤션 styling.md — 토큰 우선, 신규 임의값 금지 원칙에 부분 저촉: `bg-primary-3/30`, `bg-gray-50`류 하드코딩). 개선: §3 결정 3.

**M5. 승률 없음(`-`) 상태의 의미가 불명확 (실캡처 확정, 메가라이츄Y)** — 메가폼 캡처에서 "승률: −"로 표시되는데, 이게 "데이터 없음"인지 "0%"인지 "집계 제외"인지 구분되지 않는다. 근거: NN/g "Visibility of system status" — 빈 상태는 원인을 설명해야 한다. 개선: 툴팁 또는 캡션으로 "표본 부족으로 미집계" 등 원인 명시(정확한 사유는 백엔드 데이터 계약 확인 필요, seo-specialist/백엔드 협의 아닌 콘텐츠 문구 이슈).

**M6. 구 `Tag.component`(전역 CSS 클래스 `type-tag`/`chip-type-*`) 사용 — 상세 3호가 만든 신규 `tag/Tag.component`(토큰 기반)와 불일치** — champions 상세(desktop/mobile 컨테이너 모두)는 `~/components/Tag.component`를 import한다. 반면 상세 3호(UX-005 결과물)는 `~/components/tag/Tag.component`로 완전히 새로 만들어졌고(모바일 퍼스트 2단계 토큰, `text-2xs`→`desktop:text-xs`), champions 리스트 카드(`ChampionsPokemonCard`, E-1)는 이미 신 태그 계열(`PokemonCardShell` 내부에서 `tag/Tag.component` 사용)로 갈아탔다. 상세만 구버전에 남아있다. 근거: DS 정합성(컨벤션 — 컴포넌트 재사용/단일 소스). 개선: 신규 `TagComponent`(`tag/Tag.component`)로 교체(마이그레이션 비용 거의 없음 — props 동일, `type: PokemonType`).

**M7. UA 분기 2벌 렌더로 ISR 무의미화** — `revalidate` 설정과 무관하게 `headers()` UA 감지가 caching을 사실상 동적으로 만든다(UX-005 M5와 동일 패턴). 개선: C1과 함께 해소.

### 🟢 Minor

**m1. 파트너 리스트가 텍스트 나열 — PokemonCardShell/카드 어포던스 없음** — `ChampionsPartnerList`는 `Link`로 감싸긴 했으나 순수 `hover:bg-primary-3/50` 텍스트 행으로, 클릭 가능성이 약하게 드러난다. UX-001 문제 D(2026-04)에서 이미 지적된 사항이 아직 해소되지 않음. 개선: §3 결정 4(카드화는 과잉, 행 내 화살표 아이콘 등 최소 어포던스 추가 권고).

**m2. "출처: Smogon Stats" 캡션이 최하단에 작게(`text-xs text-gray-400`) 고립** — 데이터 신뢰도 정보가 시각적으로 거의 안 보임. 개선: 유지하되 톤 토큰화(`text-gray-400`→`text-primary-3` 등 등록 토큰).

**m3. isStale 배너가 액션 없이 경고만** — UX-001 문제 H와 동일, 아직 미해결. 우선순위 낮음(sTale 발생 빈도 낮음 추정).

**m4. "↗ 도감 보기" 링크가 데스크톱은 우상단, 모바일은 최하단으로 위치가 상이** — 동일 기능의 위치 일관성 약함. 개선: 반응형 단일화 시 위치 통일(§2).

## 3. 핵심 논점 판단 (사용자 위임 항목)

### 결정 1 — 데스크톱 2단 구조 유지 여부: **"완화된 2단" 유지, sticky 폐기**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 2단 유지(폭 재조정) | champions 메타 정보량(기술+도구+특성+파트너 4블록)이 일반 상세보다 많아 좌측에 "포켓몬 정체성" 고정 시 우측 스캔에 집중 가능. 기존 사용자 멘탈모델 유지 | ADR-0003 근거(sticky) 폐기 필요, `aside` 폭이 곧 콘텐츠 붕괴 원인이었으므로 세심한 폭 설계 필요 |
| B. 1단 세로 스택(상세 3호 방식) | 반응형 붕괴 리스크 원천 차단, 코드 단순, 시각 언어 완전 통일 | champions는 기술/도구/특성/파트너 4블록+능력치까지 있어 세로 스크롤이 상세 3호보다 훨씬 길어짐(체감 페이지 길이 2배 이상 추정) |

**판단: A(완화된 2단) 채택, 단 ADR-0003의 "좌측 sticky" 조항은 폐기 — 새 ADR로 대체 필요.**

- 근거 1(정보량): champions 상세는 일반 상세(기본정보+특성+기술+상성+진화, 5블록)와 달리 이미 메타 4블록(기술/도구/특성/파트너)+능력치+요약바로 구성되어 정보 밀도가 높다. UX-005 §5 결정 1에서도 "일반 상세는 1단 스택"으로 정리했지만, 그 근거(RES-003 벤치마크 5곳 중 다수가 단일 컬럼)는 champions처럼 "메타 통계 도구" 성격이 강한 페이지에는 그대로 적용되지 않는다 — Pikalytics·Smogon(UX-001 벤치마크)도 좌우 분할 구조를 쓴다.
- 근거 2(sticky 폐기): 현재 코드에도 `sticky` 클래스가 실제로 없다(ADR-0003 문서와 코드가 이미 괴리). ADR-0003 채택 당시(2026-04) "이중 스크롤 방지"를 이유로 우측 `overflow-y:auto`를 제거하고 "좌측 sticky"만 남기기로 했으나, 현재 구현에는 sticky도 빠져있어 사실상 정적 2단이 되어 있었다. sticky를 되살리는 것은 반응형 전환의 우선순위가 아니며(모바일에서는 어차피 1단이라 무관), 데스크톱에서도 능력치 카드가 화면 높이보다 작아 sticky 이득이 제한적이다(2026-07 기준 능력치 카드는 총합+6행으로 약 300~360px, 우측 메타 4블록은 800px+로 훨씬 김 — sticky 시 좌측이 계속 보이는 이득은 있으나, 이번 개편에서는 **1차로 반응형 안정화에 집중하고 sticky 재도입은 후속 트랙으로 분리**를 권고).
- 결론: **ADR-0003을 대체하는 새 ADR 필요**. 핵심 변경점은 (1) sticky 조항 제거(후속 트랙 분리), (2) 좌측 컬럼 폭을 고정 `w-[420px]`에서 데스크톱 그리드 비율(`desktop:w-80`~`w-96`, 전체 1280px 컨테이너 대비 적정 비율)로 재조정, (3) 반응형 전환(모바일 1단/데스크톱 2단)을 명문화.

### 결정 2 — 능력치 시각화: **StatBar로 교체 (강력 권고)**

- 근거: RES-003(5곳 중 레이더 0곳) + 상세 3호 이미 전환 완료 + WCAG 1.1.1(C3, canvas 수치 미접근) — 이 세 근거는 UX-005에서 결론 난 것과 완전히 동일하며, champions에 한정해 다른 결론을 낼 근거가 없다.
- "champions 고유성" 트레이드오프 검토: champions는 "메타 통계 데이터 페이지"이지 "포켓몬 도감 정체성 페이지"가 아니다. 레이더 차트가 서비스 전체의 브랜드 아이덴티티였다면 고유성 논거가 성립하겠으나, 이미 상세 3호가 전환을 마쳐 "레이더=포케코리아 브랜드"라는 전제 자체가 깨졌다. 오히려 지금처럼 상세와 champions가 다른 시각 언어를 쓰는 것이 "같은 서비스 안에서 같은 데이터(종족값)가 다르게 보이는" 일관성 위반이다.
- 추가 근거: champions는 폼별로 스탯이 달라지는 경우가 흔한데(메가진화 등, 실제로 메가라이츄Y 캡처에서 확인), StatBar의 "최고/최저 강조 + 카운트업" 모션은 폼 전환 시 변화를 시각적으로 부각하는 데 유리하다(레이더는 도형 전체가 바뀌어 어느 스탯이 변했는지 즉시 식별이 어려움).
- **채택**: `StatBarComponent`를 champions 상세에 그대로 재사용(props 동일 — `StatBarItem[]`). `pokemon.stats`를 `[{label:'체력', value: stats.hp}, ...]` 형태로 매핑만 하면 된다. 신규 컴포넌트 불필요.

### 결정 3 — 챔피언스 메타 바(`ChampionsMetaList`) 시각 언어 정합: **자체 유지 + 토큰만 정합, MoveTable 대체는 부적절**

- `ChampionsMetaList`(인기 기술/도구/특성)와 `MoveTable`은 데이터 형태가 다르다 — MoveTable은 "기술 1건 = 습득조건+타입+분류+위력+명중+PP" 풀 스펙 표인 반면, champions 메타는 "이름+사용률(%)" 단 2필드의 순위 막대 목록이다. MoveTable을 억지로 끌어오면 없는 필드(타입·위력 등)를 위한 빈 셀이 생겨 과잉이다.
- 대신 **`ChampionsMetaList`/`ChampionsPartnerList`를 StatBar와 같은 토큰 계열로 재도장**한다: `bg-primary-3/30` 카드 배경 → StatBar가 쓰는 `bg-primary-1/10` 트랙 톤과 정렬, 바 색상은 사용률 성격(순위/채택률)이므로 StatBar의 "최고/최저 강조"가 아니라 **1위 항목만 강조**(막대 색을 `bg-primary-1`→ 1위는 `bg-type-grass` 등 포인트 색, 2위 이하는 중립색)하는 규칙으로 통일. `bg-gray-50`류 미등록 색은 전부 제거하고 `primary-*`/`grade-*` 토큰으로 교체.
- 파트너 리스트는 이미지가 있어 순수 막대 목록과 다르므로 별도 톤 유지하되 카드 배경 톤만 정합.
- **결론**: 신규 컴포넌트 생성 없이 기존 `ChampionsMetaList`/`ChampionsPartnerList`의 색 토큰만 개정(코드 수정 범위: className만).

### 결정 4 — 폼탭(ChampionsFormTab) 반응형 처리: **가로 스크롤 유지 + 발견 가능성 보강**

- 메가폼처럼 형제 폼이 4개 이상인 경우(라이츄: 기본/메가X/메가Y/알로라)는 모바일 375px에서 물리적으로 한 줄에 다 들어갈 수 없다(각 `min-w-[10rem]`=160px × 4 = 640px). 가로 스크롤 자체는 유지가 맞다(탭을 세로로 쌓거나 드롭다운으로 바꾸면 "지금 어떤 폼들이 있는지" 한눈에 스캔 불가 — 오히려 발견성이 나빠짐).
- **보강**: (1) 좌우 페이드 그라데이션(`before:`/`after:` 의사요소 또는 래퍼 div, `pointer-events-none`)으로 스크롤 가능함을 시각적으로 암시. (2) 마운트 시 활성 탭을 뷰 중앙으로 `scrollIntoView`. (3) 폼 4개 이하인 경우(전체 종의 대다수)는 375px에서도 대부분 수용 가능(`min-w-[10rem]`을 `min-w-[8.5rem]`로 소폭 축소하면 375px에 2.2개 표시 → 스크롤 여지가 더 명확히 보임, 폭 축소는 터치타겟 44px 유지 조건 하에 가능).
- 신규 컴포넌트 불필요 — 기존 `ChampionsFormTab`에 스크롤 단서(CSS)와 `useRef`+`scrollIntoView`(useEffect) 추가.

### 결정 5 — 헤더 정합: **PageHeaderComponent 직접 이식 안 함, 브레드크럼/여백 토큰만 정합**

- PageHeaderComponent는 "제목+설명 텍스트"만 있는 목적 페이지 헤더(도감/티어/홈처럼 "이 페이지가 뭔지" 소개하는 역할)다. 상세 페이지는 진입 목적이 다르다 — 사용자는 이미 특정 포켓몬을 찾아온 것이고, 필요한 건 "제목 설명"이 아니라 "이 포켓몬이 누구인지"(이미지+타입+메타요약) 즉시 인지다. E-1 세 화면(홈/티어/도감)이 목적 페이지인 반면 상세는 개체 페이지로 성격이 다르므로, **PageHeaderComponent를 그대로 이식하지 않는 것이 맞다**(일반 상세 UX-005도 동일 판단으로 PageHeader류를 쓰지 않고 히어로 직행).
- 다만 M3(이질감)는 실재하므로, **정합시킬 요소를 좁혀 지정**한다:
  1. 브레드크럼 스타일(폰트 크기·색 토큰)을 E-1 페이지들과 동일 토큰으로 통일(현재 이미 유사하나 `text-black-2/70` vs E-1 페이지의 브레드크럼 부재 — champions 상세만 브레드크럼이 있어 오히려 상세가 더 친절한 상태, 유지).
  2. 상단 여백 리듬(섹션 간 `mb-6 desktop:mb-8`)을 PageHeaderComponent의 `mb-6 desktop:mb-8`과 동일 스케일로 맞춰 "같은 챔피언스 섹션 안에 있다"는 리듬감을 준다.
  3. 폼탭 UI가 사실상 상세의 "ChampionsFormatIntro 대응물" 역할을 하므로, 폼탭 컨테이너 상하 여백을 `ChampionsFormatIntro`와 동일 토큰(`mb-4 desktop:mb-6`)으로 정합.

## 6. 다음 단계 안내 (ui-publisher 시안 제작자용 체크리스트)

1. **모바일(base, 375px 기준) 목업**: 브레드크럼 → 폼탭(스크롤 단서 포함) → 히어로 카드(그라데이션+이미지+타입+메타요약 2×2 그리드) → 능력치 StatBar 카드 → 메타 상세 4블록(기술/도구/특성/파트너 순차 스택, 탭 UI 유지 여부는 시안 단계에서 사용자 재확인 권장 — 본 문서는 탭 UI 존치를 전제로 토큰만 정합했으나, 세로 스크롤 총량이 상당히 길어지므로 탭 유지가 맞는지 시안에서 실측 검증 필요) → 출처 캡션 → 도감 링크.
2. **데스크톱(desktop:, 1280px 기준) 목업**: 브레드크럼+도감보기(우측) 한 행 → 폼탭 → 히어로 카드(가로 배치 유지) → 2단 그리드(좌측 능력치 StatBar 카드 폭 `desktop:w-80`~`w-96` 범위에서 실측 후 확정, 우측 `flex-1` 메타 4블록) → 출처 캡션.
3. **폭 회귀 테스트 필수 구간**: 320px(최소 지원 폭), 375px, 430px(대형 모바일), 768px(브레이크포인트 직전 — 여기서 2단이 아직 아님을 확인), 769px(브레이크포인트 직후 — 2단 전환 시 붕괴 없음을 확인), 1024px, 1280px+. §0에서 확인된 붕괴가 769px 이상 어느 폭에서도 재발하지 않는지 특히 확인.
4. **폼 전환 시나리오**: 형제 폼 1개(탭 미노출)/2개/4개 이상(스크롤 발생) 각각 캡처해 탭 UI 검증.
5. **메가/거다이맥스 폼처럼 스탯이 크게 변하는 케이스**: StatBar 최고/최저 마커가 폼별로 올바르게 재계산되는지 확인(막대 최댓값도 폼마다 동적 재계산 — `barMax = max(stats)+20`).
